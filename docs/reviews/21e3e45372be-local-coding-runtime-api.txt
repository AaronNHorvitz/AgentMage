## Review of the claims

**Dedicated service, production construction.** Production builds only `LinuxRuntimeIpcClient::new(channel)`
over the authenticated `connect_development()` session (`coding_runtime_api.rs:103-114`). The trait object is
only used to substitute the synthetic peer in `#[cfg(test)]`; there is no production fake factory. Adding
`agentmage-host` as a dependency brings in no other defaults, because its features only gate code
(`shells/host/Cargo.toml [features]` are all `[]` or engine passthroughs that are not selected). Cargo.lock adds
exactly four dependency edges; the audit confirms registry name, version, source and checksum tuples are equal.

**Fixed selection, exact JSON, no injected authority.** `PrepareRun`, `Start`, `Binding`, `Advance`, `Control`
and `Artifact` are `deny_unknown_fields`, and every body goes through `decode_exact`. That decoder refuses
duplicates through `UniqueMembers` and arrays-as-structs through the re-encode comparison. `prepare` hardcodes
`record_session:false`, `slow_subscriber_probe:false`, `preauthorization:None`, `engineering_session_id:None`
and `recipe:None`; profile, entry digest, workspace id and root come only from startup selection (`:203-215`).
Unit tests cover extra `preauthorization` or `workspace_root` members, an array body, a duplicate `prompt` and
an array job-control request.

**Control-only, route isolation.** `handle_runtime` refuses `!req.control` before anything else (`:287`). In a
runtime service, `lib.rs` default-denies everything except exact `GET /v1/status` and `GET /v1/activity`
(`lib.rs:1056-1065`). Combined with exact route matching in `dispatch`, encoded or `..` path variants end in
404 or 409, never in a manual effect route. My probe (row 11) confirms the ordinary-service side. Activity
records carry only fixed labels.

**Job control and scope.** HTTP calls only `control_job`; the synthetic peer panics if direct `cancel` or
`revoke_session_preauthorization` is ever called. The production IPC client refuses `cancel`. The host side
derives `client_scope` from kernel-observed peer credentials (`runtime_ipc.rs:625-640`), not from the request.
The terminal sends the observed `revision` and a fresh `getrandom` request ID (`coding_cli_runtime.rs:143-161`).

**Terminal approvals.** The approval challenge is verified by `verify_runtime_approval_challenge` and bound to
the run. The terminal displays the re-serialized, verified struct plus decoded `arguments_json`, through
`safe()` (all non-ASCII and control characters escaped) on `/dev/tty`. The typed answer must exactly match
`allow <challenge_sha256>`. Denial sends `grant_id: null`. A stdin that is not a terminal refuses. PTY tests
cover approval, denial, a modified challenge, a foreign run and a piped refusal, and check for no ESC bytes.
Prompt-injected tool arguments therefore cannot run without the host-side exact approval, and cannot hide
terminal control sequences in the review text.

**Frame deadline.** One `Instant` deadline per frame covers prefix and payload (`ipc.rs:546-562`, `:574-582`).
Each partial read or write resets the socket timeout to the *remaining* time, so trickle progress cannot renew
it. EINTR is retried and EOF is MalformedFrame. Any failure with a timeout configured sets `frame_failed` and
`shutdown(Both)` (`:536-541`), so a late reply cannot be read as the answer to a later request. Default
sessions (host side, `frame_timeout: None`) keep `read_exact`/`write_all`. A complete host `Error` frame is an
ordinary frame and does not poison the channel. I checked that the 30 s bound cannot trip during normal host
work: `advance` waits at most `CONTROL_WAIT` + `START_WAIT` (≈275 ms) per refresh, and suspension waits are
bounded by `START_WAIT` (`coding_live_runtime.rs:199-201`, `1463-1473`, `1580-1630`).

**Startup, signals and cleanup.** The model must be `muse` or `gpt-oss` (scripted is refused), the address must
be loopback, the activation is validated before launch, and `read_launch_envelope_cancellable(&stop)` is used.
`terminate_and_reap` runs on both the error and the orderly path. `LinuxDevelopmentHostProcess::Drop` also
reaps or quarantines on unwinding. SIGINT, SIGTERM and SIGHUP only set the stop flag; handlers are unregistered
afterwards. Positive HTTP cleanup and recovery is not claimed, which is accurate.

**Evaluation integrity.** The diff touches no `fixtures/`, `scripts/coding_eval*`, `model-profiles/`, `schemas/`,
`supply-chain/` or `architecture/` file. The audit asserts this, and I confirmed it from the file list. Test
content is synthetic (`Fix add`, an existing v5 run-request fixture). No held-out content, score or threshold
change. TASKS statuses and "Current Implementation Truth" are unchanged (audit), and the appended row text is
accurate and non-closing. No new row and no plans-only work (delivery rule satisfied).

**Retained errors.** The builder logs keep the initial manifest-alias error, the Node entry-point error, the
narrow-feature warnings, the aborted root policy scan and the failed first native probe (older prefix). The
evidence labels each correctly and does not count any of them as a pass.

## Findings

No critical, high or medium finding.

- **L1 (low, labelling).** `platforms/local-api/src/coding_runtime_api.rs:97` hardcodes the host development
  scenario `failed-test-repair`. For a real model this still fixes the run contract whatever the HTTP prompt:
  the mutable file set is `["src/calc.py"]` and the only acceptance criterion is "The exact synthetic
  validation passes after the bounded repair" (`shells/host/src/coding_development_runtime.rs:988-1022`).
  Neither the guide nor the evidence names this. They only say "its own source, test, profile and workspace
  restrictions", while the guide's title and workflow read as general task runs.
  Fix: state the fixed scenario, mutable file and acceptance criterion in the guide's Start and Remaining scope
  sections, and expose `"scenario":"failed-test-repair"` in `GET /v1/code/runtime`.
- **L2 (low, test coverage).** The claim "resume asks anew" (`coding_cli_runtime.rs:144-149`) has no test. The
  only terminal job-control test is cancel (`tests/coding_runtime_cli.rs:303-329`).
  Fix: add a PTY case where `resume` confirms and sends the revision, and one where a non-matching answer sends
  nothing.
- **L3 (low, recovery).** After one bounded-frame failure the channel is permanently closed
  (`platforms/linux/src/ipc.rs:536-541`), which is correct. However, the service then keeps running with
  `runtime_attached:true` and answers every runtime route with a generic 409 host code. The sibling host may
  already have exited. Nothing tells the operator that only a restart can recover.
  Fix: on a transport-level failure, report a distinct `code.runtime.channel-closed` (or detach the runtime)
  and stop the service so the owned child is reaped.
- **L4 (low, shutdown).** The orderly stop path force-terminates the host (`coding_runtime_api.rs:127`). It does
  not first try the existing `LinuxRuntimeIpcClient::shutdown` exchange (`shells/host/src/runtime_ipc.rs:320`)
  when no run is active. The guide describes this accurately ("terminate and reap only the owned sibling host").
  Fix: try a bounded IPC shutdown first, then fall back to `terminate_and_reap`.

Prior low findings L1-L3 from `3bd1720d778b` remain backlog, as the builder states.
