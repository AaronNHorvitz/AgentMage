## Review against the claims

**Authorization and consent (the confinement boundary at this layer).**

- Every route uses `control=true` (`coding_cli_endpoint.rs:37,102,184,217,234`). Fixed literal routes
  go through the shared bounded loopback client. It sends no redirect, proxy or model-chosen URL
  (`coding_cli.rs:78-79,151-154`).
- `endpoint-step` / `-approve` / `-deny` / `-release` check `stdin().is_terminal()` before any
  connection (lines 126, 133, 221). `confirm` reads only from `/dev/tty`, takes at most 256 bytes and
  requires an exact typed match.
- Tool allow (`allow <challenge_sha256>`) and disclosure (`share <request_sha256>`) are distinct
  prompts in that order. The POST happens only after both (lines 151-155 and 92-96).
- Deny needs disclosure consent only. That is correct: the advance can send observations upstream.
  The server also refuses `approve_model_context:false` unless cancellation is latched
  (`coding_endpoint_api.rs:215`).
- Tests assert two prompts for allow, one for deny, no POST after an allow-only answer, and no POST
  after a declined disclosure.

**Challenge integrity.**

- The user-supplied challenge is decoded with `decode_exact`. Unknown or repeated members are refused.
- `verify_runtime_approval_challenge` recomputes the digest over the whole challenge, including the
  presentation and argument bytes.
- The client then checks run, task and a visible tool id/version from the freshly fetched, verified
  and pinned request (`check_challenge`, lines 69-84).
- The host compares `challenge_sha256`, `approval_id`, grant and expiry against the original pending
  challenge. So what the user reviewed is hash-bound to what the coordinator will execute.
- The readable projection decodes arguments with `decode_exact` and refuses repeated members. The
  test covers this even with a valid presentation seal.

**Request pinning.**

- `selected` verifies the seal, `process-only`, `fixed-for-service`, `EphemeralReadOnly` and no
  cursor.
- `checked_selection` requires the caller's exact run id and digest. It never repins to a newly
  fetched identity. Tests cover a foreign run, a foreign digest, a substituted model and a tampered
  digest.

**Untrusted reply parsing.**

- Steps are a tagged enum with `deny_unknown_fields`.
- A terminal outcome is checked for schema, run, session, task, digest, terminal state and an empty
  inner `answer_evidence`. The inner field is always `None` for endpoint outcomes
  (`endpoint_outcome.rs:120`).
- An awaiting-approval reply is checked against the pinned request.
- The step is shown under `verification: service-observation-only`. It does not attempt or claim
  claim-based verification, and that wording is accurate.
- Event pages are checked as follows:
  - at most one event per page;
  - `after <= total`;
  - `next == after + len`;
  - `next <= total`;
  - an empty page means `next == total`;
  - `retention == process-only`;
  - per-event `verify_runtime_event` plus run, session, task, policy and sequence equal to `after`.
- The page is labelled `individual-event-hashes-only` and `index_is_resume_cursor: false`. All output
  goes through `safe()`.

**Recovery and interruption.**

- A lost reply (peer close), a 409 refusal and a malformed terminal reply each produce exactly one
  advance POST and no retry, cancel or release (test `..._never_retried_or_auto_cancelled`).
- The guide tells users to inspect events after an uncertain reply.

## Findings

No critical, high or medium finding.

- **L1 (low, consent wording / reachability): `platforms/local-api/src/coding_cli_endpoint.rs:86-96`.**
  - After `endpoint-cancel`, the owner keeps the run `StillRunning` until one more advance
    (`coding_endpoint_owner.rs:245-249`). So `endpoint-release` cannot succeed before that.
  - The host already permits that post-cancellation advance with `approve_model_context:false`
    (`coding_endpoint_api.rs:215`). The terminal's only advance path, however, demands typed
    disclosure consent (`share <digest>`), and its warning says the run's task and observations will
    be shared.
  - A user who cancelled specifically to avoid further disclosure must therefore grant disclosure
    consent to reach a releasable state, or stop the service.
  - This errs toward over-consent rather than under-consent. The latched cancellation probe means no
    model call should follow, so this is not a boundary escape.
  - Fix: add a cancelled-run finalization path. One option is an `endpoint-step` variant used only
    after a successful `endpoint-cancel`. It would send `approve_model_context:false` and need no
    disclosure prompt; the host already rejects it unless cancellation is latched. Then cover
    cancel → finalize → release in the actual-HTTP method.
- **L2 (low, review fidelity): `platforms/local-api/src/coding_cli_endpoint.rs:146-153`.**
  - `arguments_json` is a `serde_json::Value` projection. The workspace does not enable
    `arbitrary_precision`, so integers beyond u64/i64 and decimals beyond f64 precision are shown
    normalised. For example, `9007199254740993.0` shows as `9007199254740992.0`.
  - Meanwhile `presentation.arguments.bytes` is shown only as a numeric byte array, so the exact text
    is not readable side by side.
  - The approved bytes stay hash-bound, so this is a display gap only. Typed tool schemas mostly make
    it moot.
  - Fix: also show the exact UTF-8 argument text as an escaped string (`safe()` already escapes it),
    or refuse a projection whose numbers do not round-trip to their source text.

Backlog notes outside this diff, not findings against this commit:

- The older `runtime-approve` path decodes its readable arguments with plain `serde_json::from_slice`
  (`coding_cli_runtime.rs:236-237`). It therefore still collapses repeated members silently, which
  this increment correctly refuses. Align it with `decode_exact`.
- The reviewer sandbox has no Node at all, and the request's fallback loop sets `PATH=":$PATH"`. Fix
  the loop (`PATH="$(dirname "$node_candidate"):$PATH"`), or keep shipping the builder's lint output
  as the stated substitute.
- Pre-existing design: the CLI sends the control bearer to whatever process listens on the given
  loopback port. The server is not authenticated to the client. Consider this before release.
