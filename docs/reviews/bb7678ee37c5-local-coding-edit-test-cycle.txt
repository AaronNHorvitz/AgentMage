## Findings

### M1 (medium, correctness): the new Completion turn invites tool calls it cannot honor and faults the run

`shells/host/src/coding_endpoint_edit_generation.rs:189-214` builds the Completion turn with
`CodingEndpointContext::new(input.request, &linux_coding_endpoint_coding_registry()?, &[], ...)`. That context
(`shells/host/src/coding_endpoint_context.rs:37`, `:150-165`) lists both tools and instructs the model to
return "either {\"tool_call\":...} ... or a completion candidate", and the turn has no `tool_preparation`. A
model that follows the prompt and asks to re-run the test or make one more edit (a plausible step after a
pass) reaches `request_tool`; `CodingEndpointEditBoundary::evaluate_scoped`
(`shells/host/src/coding_endpoint_edit_previews.rs:497-501`) returns `Invalid` for a `Ready` owner, which
`runtime_loop.rs:3506-3516` maps to `RuntimeLoopError::Dependency`. The run gets no recorded refusal and no
terminal outcome. A second advance returns `InvalidBoundaryResult` (reproduced above). This is fail-closed and
has no security effect. But the Completion turn is the only route to verifier acceptance in this composition,
and the shipped prompt steers the model into a fault there. The fixtures never hit it because the completion
fixture's model always returns a completion candidate.
**Fix:** make the Completion turn completion-only. Either build its context from an empty tool list with a
completion-only instruction, or attach a `tool_preparation` that always refuses so the kernel records
`finish_refused_proposal`. Add a test where the Completion-turn model returns a `tool_call` for each tool and
assert a recorded terminal refusal (not an `Err`) with no grant/start/write.
Severity is medium because it blocks closing T-303/T-306 until fixed. It does not affect this non-closing
verdict.

### L1 (low, test coverage): the host-level Command-owner transitions are not executed by any test

`execute_scoped` Command→`Completion`, `permits_failure_observation` Command→`Ready`+feedback+`prior_receipt`,
and the repair-then-retest sequence in `coding_endpoint_edit_previews.rs:450-483`, `:533-557` run in no test in
any environment. The host and API fixtures either hit native preparation refusal or deny the command challenge,
and the repair and completion fixtures enter their phases through `synthetic_observation`, which skips these
transitions. In this lane the native manifest refuses before any test approval, because the sandbox binaries
are not uid 0 (`platforms/linux/src/command_runner.rs:511`, `:534`). So the host/API "admitted → deny" branch is
not exercised here either. I read the transitions and found them correct. The builder discloses this, and it
extends the predecessor's L2. Backlog, same row: cover these transitions with a trusted host-side observation
seam or an environment-qualified run before claiming the composed workflow.

### L2 (low, robustness): repair prompts have no headroom reserved for diagnostics

`take_feedback` consumes the held feedback (`coding_endpoint_edit_generation.rs:144`) before
`prepare_edit_generation_with_feedback` wraps a source context, sized only by `source_budget` (allowed up to
32 KiB, `coding_endpoint_edit_previews.rs:160`), together with the feedback. If the result exceeds the
request's context budget, `freeze_messages`/`for_run` refuses and the repair selection is gone. That is
fail-closed and consistent with the documented "restores no selection". But a host can pick a source budget
that makes every repair fail. Backlog: reserve the feedback size when sizing the repair source context, or
refuse at startup when `source_budget` plus the feedback ceiling exceeds the context budget.

The predecessor's L1–L4 and earlier lows remain same-row backlog unchanged.
