## Security and correctness analysis

- **Authorization source.** `FilesystemApplyAuthorization` has private fields, no derives and a
  single construction site (`filesystem_control.rs:1408`). That site runs after
  `validate_transaction_binding`, `consume_for_execution` and the checkpoint. The borrowed `approval`
  is therefore the exact kernel-checked receipt. Callers cannot construct or substitute it, and
  borrowing it adds no effect authority.
- **History handling in the creation driver** (`coding_repository_create.rs`):
  - Candidate-shape refusals return before `applied_write.take()`, so a pre-dispatch refusal
    preserves history.
  - On dispatch, history moves into the attempt.
  - A non-committed outcome, a dropped driver, an unpublished run, a mismatched completion or a
    proof error never restore it. All of these fail closed.
  - `(Some, None)` retires history. `append` keeps the existing root-equality, 64-transaction and
    8 MiB bounds.
  - `from_native_creation` is `pub(crate)` and is called only from `complete`.
- **Proof checks** (`coding_workspace_creation_proof.rs:20-92`):
  - The approval binding is recomputed with the same serializer and tuple as the kernel's
    `canonical_sha256` (`filesystem_control.rs:1320`).
  - The issued-grant digest, the consumed revision (issued + 1), the receipt chain, the per-receipt
    transaction, grant, kind, absent source, destination, postimage and mode are all checked. Every
    planned operation needs exactly one Verified receipt.
  - The tests mutate each of 13 fields and every mutation refuses.
  - Unsupported shapes (non-source, invalid UTF-8, NUL) return `Ok(None)` only after all integrity
    checks pass.
- **Projection** (`review_packet_creation.rs`):
  - It refuses anything other than Create with SourceCode classification, empty content, NUL or
    invalid UTF-8, and purposes that are wrong, duplicated or missing.
  - Its diff uses the same `{:?}` 5-line format as `exact_diff`, so the history `diff_lines` check
    and composition apply unchanged.
  - The zero preimage is distinct from `sha256("")`, and the test asserts this.
  - `verify_single_change_set` re-checks ordering, hashes and authority. `write_authority` is false.
- **Mode binding.**
  - Capture (`coding_repository_commit_review.rs:69-88`) and the planner (`:231-249`) require

- **L1 (low, backlog), `platforms/linux/src/coding_repository_apply_tests.rs:1760-1773`, with
  `local_commit.rs:132`:** an unpublished native creation leaves the file on disk without lineage.
  - A later ordinary edit then makes that file reviewable as an existing-file edit, with preimage
    `sha256("created\n")`. The new test asserts this behaviour.
  - The candidate planner uses only postimages. A path absent from the Git base can therefore be
    added to a candidate tree while the packet labels it as an edit of existing content.
  - All committed bytes are still shown in the complete diff, and no authority is gained. That is
    why this is low.
  - This behaviour predates this commit; the new test documents it.
  - Fix: when lineage begins at an untracked path, either check the first preimage against the base
    tree, or refuse ordinary edits of paths created by an unpublished native creation.
