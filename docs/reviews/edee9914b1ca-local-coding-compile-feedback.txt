## Findings

No critical, high or medium findings.

**L1 (low, correctness regression, fail-closed): honest Rust libtest runs are refused because of stderr content.**
At `kernel/engine/src/validation_result_text.rs:64-67`, `std::str::from_utf8(&observation.stderr).ok()?` and
the `could not compile` line scan now run before every Rust libtest parse. At the base, this parser read only
stdout (`git show d671b595:kernel/engine/src/validation_result_text.rs:60-64`). Two results change:

- A real passing `cargo test -- --nocapture` whose test prints a `could not compile` line becomes `malformed`
  (real run `pass`).
- A pass or assertion failure whose stderr holds any non-UTF-8 byte becomes `malformed` (own probe).

Neither result is retryable, and the non-UTF-8 case is neither documented nor tested. No false pass is
possible. Fix: enter the compilation branch only when `observation.stdout.is_empty()` and scan stderr
byte-wise (`split(|b| *b == b'\n')`), so a libtest transcript on stdout keeps the base behaviour. Add a
pass-with-non-UTF-8-stderr test. Backlog.

**L2 (low, documentation precision): the guide overstates the diagnostic check.**
`docs/guides/coding-validation.md:103-106` says a "separate rustc error diagnostic" is required. In
`validation_result_text.rs:205-214`, any non-empty `error: …` line qualifies, including Cargo-level errors,
and leading-zero counts are accepted. This is harmless to authority, because the result is still unsuccessful
and still needs approval. Fix one of two ways:

- tighten the code: require `error[E####]: ` or rustc's `error: ` followed by a ` --> ` location line, and
  reject leading zeros in `number`;
- or change the wording to "an `error:` diagnostic line".

Backlog.

**L3 (low, pre-existing, now also reachable from compile output): bidi and C1 characters reach the excerpt unescaped.**
The guide says compiler diagnostics may contain UTF-8. Bidi overrides (U+202E) and C1 controls (U+0085) pass
`has_forbidden_controls` (`validation_result.rs:1056-1060`, bytes < 0x20 only). They also reach the
`failure_excerpt` JSON (`coding_repository_validation.rs:400-412`) unescaped, because serde_json does not
escape them. A terminal or model view could misrender them. Rust stderr was already unchecked for assertion
failures before this batch. Fix: escape or flag U+0080–U+009F and bidi controls in excerpts, either in the
CLI renderer or in `failure_excerpt`. Backlog.

Observation, no finding: with two build jobs, real Cargo integration-test and multi-target compile failures
emit the parallel-jobs notice or several summaries, so in practice they are refused (real runs `integ` and
`both`). This narrows the useful scope mostly to lib, bin and build-script failures. The evidence already
discloses the parallel-notice limit as backlog.
