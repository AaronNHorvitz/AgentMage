## Analysis of the change

- **Identity and admission.**
  - `serve_coding_endpoint` refuses a non-loopback listener or a pre-set stop.
  - It draws 32 bytes each from `getrandom` for the run and session ids, calls the trusted factory
    once and refuses any other identities before admission (tested, `Configuration`).
  - The sealed request is re-verified by the owner, and source snapshots are dropped after
    admission.
  - No wire input reaches the factory, ports, registry, sources or configuration.
- **Authentication.**
  - Every route goes through the shared `request()` parser and then `req.control` (403 for the
    client token), including GET `/request`.
  - Routing happens only after authentication, so unauthenticated callers see 401/403, never
    404 path probing.
- **Binding.** Every POST uses `deny_unknown_fields` and exact run-id/digest equality. Mismatches
  return 409 before any lock or advance.
- **Consent.**
  - `approve_model_context` is a required JSON bool. A missing field or a non-bool value returns
    400.
  - Refusal is checked before taking the lock and dispatches nothing. Rejected approval input does
    not consume the challenge, because `run_until_boundary_impl` verifies the response before
    `advance_until_boundary` and does not set the reconciliation flag.
- **Cancellation.**
  - The latch is an `AtomicBool` that never clears. The cancel route takes no lock, and the probe
    observes it with Acquire ordering.
  - It uses the coordinator's original `correlation_id` (new read-only accessor) and task id.
    Shutdown maps to `CancellationReason::Shutdown` through the same probe.
- **Ownership.** `try_lock` returns 409 for concurrent advance/events/release (tested while
  dispatch is in flight). A poisoned mutex returns 500, and the panicking worker stops the service
  (fail-closed).
- **Events.** At most one event per page. `after <= len` is checked before slicing, `after+1` uses
  `saturating_add`, and an out-of-range index returns 409 without panicking.
- **Errors.** `owner_error` emits only fixed codes. No dependency diagnostics, source text or
  credential reaches the response. The request route exposes the sealed request, whose endpoint
  address cannot contain `@`, `?` or `#` (`validate_endpoint_shape`), so no userinfo credential can
  leak.
- **Worker refactor.** `serve_connections` keeps the four-worker, loopback-peer, stop-on-exit
  behaviour. It now joins workers even if the manual service's `cancel_active` fails, where it
  previously returned early. That is a strict improvement. The manual service's ~2,600 existing
  tests are unchanged and pass identically.
- **Claims.** The evidence and guide state accurately that this is a library entry point with no
  executable, synthetic ports, a deliberately rejecting verifier, no native filesystem or grant
  composition and no model score. No product naming or comparison, no private host path or
  username. The only `/lane/` paths are inside the byte-identical retained predecessor review.
- **Delivery.** No new row or sub-row. The increment runs and is measured by five socket tests.

## Findings

No critical, high or medium findings.

- **L1 (low, documentation precision): `docs/guides/runtime-endpoint-runs.md:490`** ("Each advance
  requires `approve_model_context: true`") **and `docs/evidence/t303-endpoint-http-2026-11-08.md:26`.**
  - Consent is checked once per HTTP advance (`platforms/local-api/src/coding_endpoint_api.rs:215`).
    But one advance runs the coordinator until the next approval boundary or terminal, which can
    include several model turns that disclose new tool results. The builder's own approval test
    performs the second model turn inside the consented approval advance.
  - This is consistent with "per-advance" and is not a bypass: tool effects still need their own
    permission evaluation or approval.
  - Fix: state in the guide/evidence that one consented advance covers every model turn up to the
    next approval challenge or terminal state, so a host UI can word its consent prompt correctly.
- **L2 (low, test coverage): `platforms/local-api/tests/coding_endpoint_http.rs`.**
  - No socket test drives a dependency fault (for example an upstream that refuses the connection
    or returns a malformed stream). So the HTTP mapping of `Coordinator` to `code.endpoint.refused`,
    then `Faulted` to `code.endpoint.faulted`, and "release of faulted private state" (claimed in
    the guide table, line 507) are not asserted at the HTTP layer. The owner-level tests do cover
    them.
  - The new target also has no Host/Origin assertions of its own. They hold by construction through
    the shared `request()` parser, and my probe confirmed them.
  - Fix: add one socket method where the upstream closes without a response, asserting
    advance=409/refused, then faulted, release=200, then not-held, with zero tool executions.
