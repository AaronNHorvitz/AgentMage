**L1 (low) — the guided-refusal method does not pin the refusal reason, and half its "ownership refusal"
cases are consent refusals.**
`platforms/local-api/tests/support/coding_guided_service.rs:66-116`. The test is named
`guided_actual_service_refuses_unowned_workspace_…`, and the evidence and TASKS describe eight
guided ownership refusals "with and without model-context consent". The `eprintln!` label at
`:111` reads "guided ownership refusal". But the only reason assertion is the generic
`"Guided workflow stopped"` message, which `coding_cli_workflow.rs:121` prints for any `Err`. My trace
shows the four `disclose=false` cases stop at the consent check (`coding_cli_workflow.rs:141`)
after one request, so they never reach the ownership check (`:152-156`). The four `disclose=true` cases
do stop at ownership: the trace ends at `GET /v1/code/repository/edit` with a null identity. The behaviour
fails closed and the "no generation, no prompt, no effect" claims hold. However, a regression that let
guided runs continue past a missing owner identity in the no-consent configuration, or that moved the
refusal to an earlier unrelated guard, would not be detected.
Fix: in the consent-granted cases, assert a reason-specific observation. For example, make the terminal
emit a stable reason code for the guided stop, or count the API routes the way the synthetic-peer tests
do. Relabel the no-consent cases as consent refusals in the observation line and the evidence.

the evidence presents all three as directly tested original-prepare pins. The mutation probes removed
only the `worktree_root_sha256` and `creation_receipt_sha256` guards. Because both pending inspections
are also substituted, the guard at `coding_cli_workflow.rs:217` is probably the only thing that stops
that case. I infer this from the code and did not run a mutation, as the brief forbids it.
