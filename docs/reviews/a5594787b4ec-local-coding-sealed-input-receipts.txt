## Confinement and integrity checks

- **Who can create a record.** Only the trusted executor puts a record into `CommandPlatformResult`. The model and request
  JSON cannot supply one. `CommandReceipt` gains one `#[serde(default, skip_serializing_if)]` field, and
  `deny_unknown_fields` still applies.
- **Kernel shape checks.**
  - `validate_platform_result` rejects a bad version, bad digests, files > 128, directories outside 1..=256,
    file_bytes > 64 MiB, a byte count with no files, and any record on `LaunchFailed`.
  - `seal_receipt` rejects a record on a non-owned-worktree command. Post-launch it becomes canonical `Uncertain` with no
    receipt or output (tested for both cases).
  - `verify_command_receipt` repeats the same checks, and the receipt digest covers the field (tamper cases 0–7 tested).
  - An absent field keeps the legacy wire bytes and verifies.
- **No authority change.** The permit, manifest, command, environment, seccomp, mount arguments, supervisor and cleanup
  are unchanged. The record is computed before the descriptors move and is not re-derived from the host afterwards.
- **No content disclosure.** `command_history` exposes only content-free receipts: digests, counts and codes. The root
  appears only as a digest. No path or bytes are added.
- **Match flag cannot be forced.** `sealed_input_matches_observation` uses `is_some_and`, so an absent record gives
  `false`. A mismatched observation gives `false` (tested). A source change after capture leaves no binding (tested).
  Later drift flips `matches_current_observation` without changing `command_history` (tested).
  `current_workspace_verified` and `test_suite_verified` stay literally `false`, and both completion verifiers are untouched.
- **Evaluation integrity and delivery.**

    diff.
  - TASKS.md row lines are unchanged, no `#[ignore]` was added, and no row or sub-row was added or closed.
- **Privacy and branding.** The added lines contain no private path, username, hostname, credential or sibling-project

## Findings

### H1 — High (inherited from dc5cb453 H1, still open at this commit; the new claims depend on it): the supervisor refuses every sealed launch with two or more files, so the new native record is never produced for a real worktree

- **Where.**
  - `platforms/linux/src/sandbox_supervision.rs:60`: `Self::Command(_) => ("agentmage-command-", projections <= 1)`.
  - `sandbox_supervision.rs:883`: the cardinality check runs before any spawn and returns `InvalidManifest`.
  - `platforms/linux/src/command_runner.rs:392-397`: one sealed memfd per regular file is passed as `projections`.
  - `command_runner.rs:410` (`map_err(supervision_failure)`) turns the refusal into `CommandExecutionFailure::ExecutionFailed`.
  - `git diff --stat dc5cb453 HEAD -- platforms/linux/src/sandbox_supervision.rs` is empty, so this commit did not fix it.
- **Failure scenario.**
  - A created worktree always holds the `.git` pointer file (it is made by `git worktree add`). With any one source file,
    capture yields at least 2 sealed descriptors.
  - The supervisor refuses before launch, so no command runs and no `CommandPlatformResult` is returned. The new
    `sealed_workspace_input` never reaches a receipt, `command_history` or the workspace binding.
  - The new evidence says "The original native executor now records the complete sealed source projection it hands to the
    original supervisor" and "The record enters the original platform result after native supervision returns". The guide
    says it "describes the descriptors handed to the original supervisor". All of these are vacuous for every tree with two
    or more files.
  - The four new methods pass only because `SealedEnvelope` (`coding_repository_command_tests.rs:2013-2038`) calls
    `capture_input_for_test` and bypasses `LinuxBoundedCommandExecutor::run` and `run_owned`. The wiring at
    `command_runner.rs:389-391` is not exercised by any test.
- **Fix.** Apply the parent review's H1 fix in this row:
  1. Add an explicit sealed-command owner or cardinality accepting exactly the sealed file count (1..=128, plus 0 if empty
     trees stay supported), keeping `Command` at `<= 1`.
  2. Update the ignored cardinality test.
  3. Add a non-ignored admission test (≥2 accepted, 129 refused).
  4. Add a host-gated end-to-end sealed launch test on a worktree with two or more files. It should also assert that the
     returned `CommandPlatformResult.sealed_workspace_input` equals the capture's `input_record()`.
  5. Until then, qualify the three new or edited documents.

### M1 — Medium (published contract broken): the repository's own closed command-receipt schema rejects every extended receipt, yet it is still the declared output schema of the command tools that now emit them

- **Where.**
  - `schemas/runtime/command-receipt.schema.json:6` has `"additionalProperties": false`, with no `sealed_workspace_input`
    property.
  - The schema's hash is the declared `output_schema` (`command-receipt-v1`) of the validation command tool at
    `platforms/linux/src/coding_repository_command.rs:548-553`. That tool's `ExactEffect` is approved for both the direct
    and endpoint validation routes, which use `with_sealed_worktree`.
  - It is also the host's `BOUNDED_COMMAND_OUTPUT_SCHEMA_JSON` (`shells/host/src/coding_tools.rs:50-51`).
  - Neither the schema nor its example/tests are in the diff.
- **Reproduction.** I compiled the schema with the repository's Ajv 2020 (`node_modules/ajv`):
  - `schemas/runtime/examples/command-receipt.valid.json` validates as `true`.
  - The same example plus a well-formed `sealed_workspace_input` (version 1, three 64-hex digests, files 2, directories 3,
    file_bytes 25) validates as `false` with
    `{"keyword":"additionalProperties","params":{"additionalProperty":"sealed_workspace_input"}}`.
  - So every sealed-validation receipt in `command_receipt`, `command_history` and the validation response violates the
    schema its approved tool definition binds.
- **Why it matters.** The decision and guide say "older strict readers cannot consume extended receipts". The strict reader
  here is not an older external client. It is the in-repository published contract, pinned by digest into the approval's
  tool definition. Any consumer that validates against it rejects the new receipts.
- **Fix.**
  1. Add an optional closed `sealed_workspace_input` property to `command-receipt.schema.json`: `schema_version` const 1,
     three `#/$defs/sha256` fields, `files` 0..128, `directories` 1..256, `file_bytes` 0..67108864,
     `additionalProperties: false`. Keep it out of `required`.
  2. Add a valid extended example and an invalid one (unknown nested key, directories 0) to
     `tests/test_planning_schemas.mjs`.
  3. Let the pinned schema hashes follow `include_bytes!`. Check for any literal copy of the old hash.
  4. Reword the "older strict readers" sentence to name this schema as updated.
