## Verified properties (no finding)

- **Explicit three-path setup; marker before pointer.** The marker is checked first: regular file,
  owned by the current user, mode `0600`, one link, at most 4096 bytes, opened `O_NOFOLLOW` and
  matched by dev/ino/mode/len/nlink. Only then does `linked_repository_for_marker` parse it. It
  requires the exact ordinary prefix plus exactly three fields (`git-metadata=`, `git-common=`, and
  a 64-hex `metadata-sha256=`). `LinuxLinkedRepository::verify` compares the workspace `.git`
  pointer with the marker-named path before it opens any external directory. Validation also
  requires the marker bytes to equal the freshly computed contents, including the identity
  digest. A forged marker therefore also needs a real metadata directory whose `gitdir` backlink
  names this workspace.
- **Old marker and command refuse linked layouts.** A prefix-only marker with a `.git` regular file
  returns `MarkerDenied` before any external read, including when the metadata is missing (real-Git
  test). `--coding-development-marker` calls `verify_git_directory` and refuses a `.git` file. The
  executable test confirms this, with empty stdout and no file created.
- **Held and revalidated identities.** The digest binds path, dev, ino, uid and mode of the three
  directories, plus the bytes and object identity of all three pointer files. HEAD contents are
  deliberately not bound. Revalidation happens before scope creation, before and after every
  inventory query, before and after every worker run, and through `activation.revalidate()` after
  inventory. `matches_root` ties the reopened worker root to the held root inode.
- **Marker inventory exception.** `development_inventory_entry_is_admissible` admits Untracked or
  Ignored entries only when the activation is linked, the path is exactly `[MARKER_NAME]` and the
  hint is `WorktreeObject`. Every other path, nested path, kind, staged state or conflicted state
  refuses, and ordinary activation is unchanged (unit test). The map still denies the same
  constant. The `refs/heads/agentmage/tasks/` requirement is unchanged in `OwnedWorktreeRecord`
  (`kernel/engine/src/repository_safety.rs:854,1565`), and the real fixture uses
  `agentmage/tasks/linked-fixture`. No `.agentmage-development-workspace` file exists in any commit
  (`git log --all -- '*.agentmage-development-workspace'` is empty).
- **Early refusal of mutation and preservation.** `collect` returns `PlanDenied` for a linked scope
  before any Git or filesystem read (test with an inert artifact). `LinuxRepositoryExecutor`
  returns `linux.git.linked.read-only`. `LinuxLocalCommitExecutor` and `LinuxCandidateTreeBuilder`
  both call `collect` first, so they also refuse. The host-side `observe_status` is reachable only
  from `collect`. Every inventory query goes through `observe_inventory_optional`, which sends

- **Confinement.** Both new mounts are `--ro-bind-fd` of `O_RDONLY` descriptors. `--unshare-all`

## Findings

### H1 (high, correctness): the shared supervisor refuses every linked worker launch

- `platforms/linux/src/repository_safety.rs:1067-1083` (`linked_inspection_projections`) builds 3
  projections, and `:944` passes them to `run_owned`. But
  `platforms/linux/src/sandbox_supervision.rs:55` admits `LaunchOwner::Git` only when
  `projections == 1`. An existing ignored native test,
  `closed_owners_reject_cross_variant_names_and_projection_cardinalities` (`:1262`), asserts exactly
  that.
- Separately, `observe_linked_inventory` (`repository_safety.rs:598-670`) passes `maximum_bytes`
  as `stdout_limit`. The four `ls-files`/`ls-tree` queries request `MAX_INVENTORY_BYTES` = 32 MiB
  (`platforms/linux/src/repository_inventory.rs:13,140,146,152,164`). `run_owned` requires
  `stdout_limit <= MAX_OUTPUT_BYTES` = 4 MiB (`sandbox_supervision.rs:875`, `sandbox.rs:49`), and
  `run_read_only`'s own 32 MiB precheck does not catch the mismatch.
- Reproduced (R1): `run_owned` returns `InvalidManifest` for both cases before any process starts.
  Consequences:
  - Linked startup inventory cannot complete in any environment, so `build_repository_composition`
    always returns `Repository` for a linked activation.
  - Linked model `git` inspection through `for_linked_worktree` is refused too.
  - The headline capability ("Activate linked worktrees in the existing native coding host";
    Decision 0157:29; guide lines 3 and 61) is unreachable. The surface fails closed.
  - The new argv-shape test (`linked_worker_uses_only_read_only_metadata_projections_and_fixed_git_paths`)
    never passes through admission, so the gate cannot see the defect.
- Fix:
  - Admit exactly 3 projections for a Git owner only when that owner carries the linked binding.
    For example, add a typed `LaunchOwner::LinkedGit` or a flag set only by `for_linked_worktree`,
    and keep 1 for ordinary inspection.
  - Update the ignored cardinality test.
  - Cap linked inventory requests at the supervisor bound and refuse larger repositories
    explicitly. Alternatively, raise the Git owner's bound under a recorded decision.
  - Add a non-native regression that runs the real admission check with the linked projection set
    and every inventory limit.

### H2 (high, correctness): the guest layout cannot resolve HEAD under the pinned Git

- `add_linked_inspection_mounts`/`add_linked_inspection_git_arguments`
  (`repository_safety.rs:1047-1065`) mount the per-worktree metadata at `/metadata/worktree`,
  apart from its common directory. They then rely on `GIT_COMMON_DIR=/metadata/common`. Under the
  worker's own guest Git (2.56.0), that layout reads per-worktree HEAD and the index but resolves
  no shared refs: `for-each-ref` is empty, and `rev-parse --verify HEAD` and `ls-tree … HEAD` exit
  128 (R2). The metadata's `commondir` holds `../..`, which in the guest points to `/`, and Git
  2.56.0's ref resolution does not use the environment override here.
- Even with H1 fixed, `collect_inventory`'s required `rev-parse --verify HEAD` would return `None`
  and startup would refuse. Most model inspection (`log`, `show`) would fail as well.
- Fix: mount only the held common descriptor and pass
  `--git-dir=/metadata/common/worktrees/<verified-name>`, which the alternative layout in R2
  confirms. The per-worktree directory is already inside that mount, so the second projection
  becomes unnecessary; keep the held per-worktree descriptor for revalidation. Otherwise, rebuild
  the `<common>/worktrees/<name>` nesting in the guest. Add a positive inventory test under the
  real worker. It may be `#[ignore]` in this lane under T-301.1, but it must exist and be run
  where native trust is available.

### M1 (medium, honest claims and reachability)

- Decision 0157:29-37, the guide (`docs/guides/coding-linked-worktrees.md:3,54-56,61-73`) and the
  evidence (`docs/evidence/t306-linked-worktree-activation-2026-11-07.md:37-45`) say the native
  host "accepts" a linked worktree. They tell the operator to "use the existing native API and
  terminal workflow" after setup. They also say linked inventory "uses the existing offline Git
  worker" and "retains its per-query byte caps".
- In fact every linked startup refuses, and the claimed 32 MiB caps are inadmissible to the
  worker (H1, H2). The disclosure "no native positive worker" is honest. But the text describes
  a reachable workflow that is not reachable, and the only evidence for it is synthetic argv
  strings.
- Fix: after H1 and H2, either record a real admitted-layout check, or restate the batch as
  activation and marker plumbing whose inventory path is currently refused.

### L1 (low, backlog): duplicated metadata descriptors lack close-on-exec

- `repository_safety.rs:1078` uses `rustix::io::dup`, which clears `FD_CLOEXEC`. Every other
  descriptor in this crate is opened with `CLOEXEC`, or duplicated with `fcntl_dupfd_cloexec`
  (`strict_local.rs:226`).
- The duplicates live from `linked_inspection_projections` until `run_owned` returns. Any process
  the host spawns in that window inherits open directory handles to the workspace's per-worktree
  and common Git metadata. That includes the `systemd-run` client itself and any concurrent host
  child. Sandboxed units are started by the user manager, so they do not inherit them.
- Fix: use `fcntl_dupfd_cloexec(fd, 3)`, or reopen `"."` with `CLOEXEC` from the held descriptor,
  and assert `FD_CLOEXEC` in the projection test.
