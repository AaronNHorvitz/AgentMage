## Findings

### M1-R (medium, correctness): the completion-only guard does not cover every tool-call form the coordinator accepts, so bb7678ee37c5 M1 is still reproducible

`kernel/engine/src/runtime_loop/coordinator_endpoint.rs:650-655` refuses only when the text parses as a
`serde_json::Value` with a top-level `"tool_call"` member. When `completion_only` is set, the original
fallback parser at `coordinator_endpoint.rs:735` (`serde_json::from_str::<EndpointToolProposal>(&text)`)
still runs. `EndpointToolProposal` and `EndpointToolArguments` are serde-derived structs. serde_json's
`deserialize_struct` accepts a JSON array and derived structs implement `visit_seq`. `deny_unknown_fields`
does not apply to that form. So `[["<tool_id>","<version>",{...}]]` is a valid tool proposal that the guard
does not see (`Value::get("tool_call")` on an array is `None`). It then passes `is_closed_json`,
`is_model_proposable` and `validate_arguments` and goes on to permission evaluation.

- Kernel: the documented contract of `completion_only()` (`:131-135`, "Tool-shaped answers terminate with a
  recorded refusal before admission") does not hold. P1 shows permission requested and `AwaitingApproval` in
  both attachment orders.
- Host: the final coding-cycle turn (`shells/host/src/coding_endpoint_edit_generation.rs:196-215`) faults
  exactly as in the original M1 (P2). Model output, possibly steered by untrusted tool output or diagnostics
  in the replayed history, can still take the only route to verifier acceptance into an unrecorded
  `Dependency` fault.
- Evidence and docs overstate the repair. The evidence file says the restriction "records
  `runtime.proposal.completion-only` for tool-shaped answers before interpreter, permission, grant or native
  dispatch". `docs/guides/runtime-endpoint-runs.md:1527-1529` and the TASKS.md paragraph make the same claim.
  These claims are false for this input.

This is not high. All authority checks still apply. The shipped host boundary refuses because its owner is
`Ready`, P2 shows no file effect, and in the kernel any execution would still need the exact approval.

**Fix:** under `completion_only`, refuse with `runtime.proposal.completion-only` whenever the text is
tool-shaped in any form the coordinator accepts. At minimum, also refuse when
`serde_json::from_str::<EndpointToolProposal>(&text).is_ok()`. A stronger option is to skip the `or_else`
fallback at `:735` entirely when `completion_only` is set, so that non-completion text reaches the existing
completion refusal. Add the sequence form (and a nested-sequence `tool_call` variant) to
`endpoint_completion_only_narrows_before_interpretation_and_preserves_verification` and to
`coding_cycle_completion_tool_requests_record_terminal_refusal_without_effects`. Then correct the three
documentation claims if the scope changes.

### L1 (low, backlog): the default tool wire form silently accepts an undocumented positional encoding

This is the root cause of M1-R, and it exists in ordinary turns too (`coordinator_endpoint.rs:340-352`,
`:735`). Every downstream check still applies there, so it has no effect in default turns. Still, the
accepted wire grammar is wider than the documented object form. Consider rejecting non-object top-level
text, or deserializing through a map-only visitor, so the accepted grammar matches the documentation.

### L2 (low, backlog): stale tool wording in the completion-only system context

`shells/host/src/coding_endpoint_context.rs:187` still sends `tool_schema_lookup` text that describes tools
and `input_schemas` in a turn that offers neither. It is inert, but it slightly contradicts "No tools are
offered". Omit it when `completion_only` is set.
