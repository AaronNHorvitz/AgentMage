## Review of the change

- **Shared signal is real.** `CancellationToken` is `Arc<Mutex<CancellationNode>>` with a derived
  `Clone`, so `pending.cancellation.clone()` in `for_pending` (`coding_repository_command.rs:38`)
  shares one node. These all observe that one token: public `command_cancellation` and
  `validation_cancellation`, the default `None` arm of `run_command_with_cancellation`
  (`:359`), and the endpoint bridge's `signal` (`coding_repository_endpoint_command.rs:430`).
- **Fresh roots are unconditional.** The only `PendingCommand` constructor is
  `command_preview` (`coding_repository_command.rs:280-290`), which always builds a new root
  keyed to a new random attempt ID. `validation_preview` calls it and then only rewrites
  `hash` and `preview` before the pending is stored, so a handle can never see a
  pre-refinement hash. A validation retry goes through the same constructor.
- **Stale explicit attachment still refuses.** `verify_command_cancellation` and the explicit arm
  of `run_command_with_cancellation` still compare both the preview hash and the attempt ID.
- **Authority is unchanged.** Cancellation only stops: `cancel` installs the first signal,
  and later calls return that existing signal (`propagation.rs:101-115`).
  `CommandControl::request` signals the same attempt with origin `Shell`, which matches the
  root's boundary, so there is no `OriginMismatch` failure mode. No grant, approval, executor,
  policy or supervisor path is added. `observe_command_cancellation` still treats lock
  contention as `Unavailable`, which fails closed after 8 passive reads. A concurrent `cancel()`
  can now contend with the supervisor poll; the worst case is a fail-closed termination, never
  an uncancelled observation.
- **Confinement is unchanged.** No path, workspace, sandbox, network or environment code is
  touched, and tool arguments cannot reach the cancellation handle (it is a library API only).
  None of the brief's escape classes (path traversal, symlinks, environment leaks, injected tool
  calls) is reachable through this diff, so the earlier command-adapter review's confinement
  results still apply.
- **The docs are accurate.** The guides say cancellation is not revocation, that an issued grant
  stays recorded until expiry, that an acknowledgement is not proof a child stopped, and that
  the handles grant no authority. This matches the code. The evidence labels creation and
  executor observations as SYNTHETIC and claims no native child stop, model workflow, grade or
  score.
- **Privacy and branding:** the added lines contain no host path, username, hostname,
  credential, sibling-project name or third-party product name. Evaluation integrity is
  untouched: no held-out, hidden, task, scorer or threshold change.
- **Delivery:** no new row, sub-row or plan-only row. This is an in-row repair of the earlier
  review's low L1.

## Findings

No critical, high or medium findings.

- **L1 (low, test coverage; backlog):** `platforms/linux/src/coding_repository_endpoint_command_tests.rs:1518`
  and `:1557`. The isolation tests only create a fresh preparation after
  `into_repository()` cleared `command` or after the old pending was consumed. Nothing tests the
  public flow where `prepare_command` or `prepare_validation` replaces an unconsumed pending
  directly: prepare A, take A's handle, prepare B, cancel A, then expect B to be uncancelled.
  Mutant M2 (reuse of the still-pending token) passes every test. The current code is correct
  because the root is created unconditionally, so this is a regression guard, not a defect.
  Fix: add one case that calls `prepare(&mut owner, …)` twice with no abandonment in between,
  cancels the first handle, and asserts that the second handle observes `None` and that the
  second attempt runs.
- **L2 (low, documentation; backlog):** `platforms/linux/src/coding_repository_command.rs:359`
  together with `coding_repository_validation.rs:121-145`. The default direct path is now
  reachable by a pre-handoff cancellation. A validation cancelled before a direct
  `decide_validation` spends one of its three attempts without launching (the share-one-signal
  test asserts `attempts == 1`). The endpoint path cancelled before preflight spends none. Both
  outcomes fail safe, but only the endpoint behaviour is described in the guide. Fix: add one
  sentence to the `docs/guides/coding-commands.md` paragraph saying that a direct validation
  decision with a cancelled attempt records a cancelled, spent attempt.
