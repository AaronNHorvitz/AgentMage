## Review

**Authority and confinement.** `code-worktree` (`coding_cli_workflow.rs`) only sequences existing helpers:
`selection`, `propose` → `edit_prepare` (`read <root>` TTY consent), `edit_decide_bound` (`edit <hash>`)
and `command_decide_observed` (`test <hash>`). On repair it adds `propose`'s `share-failure <hash>`.

- Every consequential step still goes through `confirm`. That function refuses a non-terminal stdin, reads
  only `/dev/tty`, needs an exact challenge built from a digest-validated hash, and uses `safe()` to
  escape all non-ASCII and control characters.
- Stdin terminal checks, argument bounds and definition parsing (closed `PrepareValidation` type,
  duplicate keys refused, `approve_definition` required, `prior_receipt_sha256` null) all happen before
  any credential read or request. The piped and malformed-definition tests assert that zero requests
  are sent.

  `LinuxCodingRepository::decide_edit`. Tests stay with `decide_validation_with_cancellation`, which runs
  the unchanged offline, read-only-worktree command path.
- I confirmed that an approved edit dispatch clears the pending preflight validation
  (`coding_repository_edit.rs:140`, `self.command = None`). That matches the decision's statement that
  edits invalidate pending command approvals, and the client prepares each execution again.

  for status, workspace and ordinary proposals. Edit, validation, repair and settings use the control
  token.

## Findings

No critical, high or medium findings.

- **L1 (low): the edit-preview binding is weaker than claimed, and its client check is untested.**
  - Locations: `coding_cli_workflow.rs:185-191`, `coding_cli.rs:480-494` and `coding_cli.rs:591-592`.
  - The workflow does not bind to the preview returned by `POST /v1/code/repository/edit/prepare`, which
    `edit_prepare` only prints. It reads `GET /v1/code/repository/edit` and checks only the root and
    creation fields, then requires the second GET inside `edit_decide_bound` to equal the first.
  - A preview replaced between preparation and the first GET is therefore not refused. That contradicts
    `docs/guides/coding-guided-worktree.md:60` ("refuses a preview changed between preparation and
    approval") and evidence line 22.
  - No test makes the two GETs differ. My mutation removing the equality check leaves all five methods
    passing.
  - Impact is limited. Only another control-token holder could replace the preview. The person still
    sees the full replaced preview and approves its exact hash, and the server consumes only that hash.
    No confinement boundary depends on this check.
  - Fix: return the prepared preview from `edit_prepare`, pass it as `expected`, and add a case where the
    pending edit differs from the prepare reply (and one where the two GETs differ).
- **L2 (low, backlog): no test drives `code-worktree` against the real local API service.**
  - Location: `tests/support/coding_workflow.rs`.
  - Every observation comes from the recording peer. Compatibility of wire shapes between the client and
    the native owners currently rests on review: I verified it above for this commit. Nothing would
    detect later drift in fields such as `validation.attempt` or the decide `outcome`.
  - This is honestly labelled. Fix: a service-backed case that runs the real API up to the expected
    native-admission refusal at preflight, or further where admission exists.
- **Environment (not a code finding):** markdownlint could not run here (exit 127, Node absent). It is
  recorded as a failure and not waived. Manual and link checks are above, and the builder's retained lint
