## Analysis against the request

- **Conversion checks.** In order, the conversion:
  - re-verifies the complete sealed run digest (`verify_runtime_endpoint_run_request`)
  - requires equality with the startup digest frozen at preparation
  - requires a turn in `1..=max_turns`
  - requires the current borrowed control

  It returns the original `PreparedEndpointChat`, which keeps the original credential owner, frozen
  body and narrowed text ceiling from the predecessor commit. It also returns the context packet
  framed at preparation. No socket is opened; the tests assert `WouldBlock` on the listener after
  all refusals. The unused standalone `RuntimeEndpointModelPhase` is dropped; its usage is never
  read or imported.
- **Coordinator ownership.** The existing coordinator re-frames the descriptor with
  `RuntimeEndpointModelPhase::for_run` against its own request. That check covers endpoint/model
  binding, `request.context == context.messages()` and per-phase ceilings. Before
  `ModelRequested`, the coordinator then reserves input body, model call, response text limit
  (the ≤64 KiB narrowed ceiling) and total timeout against its cumulative ledger. It charges the
  attempt and input before dispatch. Completed output/time are charged only on success, and the
  admitted attempt is rolled back only if `dispatch_attempts == 0`. Continuous control is the
  coordinator's `RuntimePhaseControl`. No new ledger, route, executor, loop or authority is added.
  `CoordinatorDispatch` only maps `TransportError` through the existing content-free
  `transport_failure`.
- **No interpretation.** The returned text follows the existing paths:
  - Tool-call JSON goes through registry, permission and exact-approval checks.
  - Other text goes through a completion claim and the caller's independent verifier.

  No strict-edit parsing or native preview happens in the conversion. A prompt-injected tool call
  from disclosed source text would therefore meet the unchanged registry/permission/approval
  boundary. The fixture exercises exactly this: the model-authored apply-prepared-edit call is
  refused under a stale approval and runs only under the exact one.
- **Regression fidelity.** I checked each case of
  `strict_generation_uses_original_coordinator_ledger_and_never_self_approves` against the kernel
  code; the expected values follow from the kernel rather than from fixture convenience:
  - output reservation: case 1
  - time reservation: case 2
  - model-call turn-start check, `runtime_loop.rs:2251`, giving prepared=1: case 3
  - epoch expiry after the native write: case 4
  - incomplete stream that keeps both attempts with no completed output: case 5
  - transport text overflow that keeps both attempts: case 6
  - cancellation after the edit: case 7

  In case 0, the verifier refuses completion and there is no second write. Each case runs in both
  borrowed and shared forms. The cumulative InputBytes/OutputBytes assertions include the native
  tool arguments/result. The test checks that a stale approval leaves events unchanged and does not
  write, that the exact approval runs the native writer exactly once, and that `one.py` holds
  `first\n` after every terminal. Terminal rereads keep the same events and ledger. The event
  sequence verifies.
