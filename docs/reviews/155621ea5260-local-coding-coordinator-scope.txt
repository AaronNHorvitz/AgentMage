## Analysis

**Confinement and authority.** `RuntimeRunScope` is a tuple struct with a private enum field, so
external code can only build it through `native`/`endpoint`, which run the full shape and digest
verification (`verify_runtime_run_request` / `verify_runtime_endpoint_run_request`). It has no
deserializer or mutable access. The default `evaluate_scoped`/`resolve_scoped`/`execute_scoped`/
`verify_scoped` adapters call `scope.native_request()?` before the legacy method, so an endpoint
scope returns `Invalid` before entry. No production `RuntimeToolBoundary` overrides a scoped method
(the only overrides are the test `ScopedBoundary`/`ScopedVerifier`), so every production tool path
still reaches only the native implementation with the original request. The coordinator builds
scopes only from its private, construction-verified `self.request` (`runtime_loop.rs:1703`), which
is never reassigned, so no endpoint request can reach a tool effect through this commit. The
transactional branches (correctness evaluate/execute/resolve hooks, artifact read/release,
journal/checkpoint/research) still pass `&self.request` natively, as documented. Exact approval
checking is unchanged: the new coordinator test and my probe both show an altered approval gets no
resolution and no effect. The `final.py` whitespace-normalised check confirms the correctness
evaluation branch is unchanged apart from formatting.

**Verifier.** `CodingCompletionVerifier::evaluate` reads only the task objective, workspace and
repository snapshots, work packet and repository snapshot id, all of which the scope exposes. No
model-profile field was used before, so endpoint support adds no weaker path. Native `verify` now
also re-verifies the request digest, which is stricter. Its only production user is the coordinator
harness (`coding_harness.rs`), whose request is already verified, so behaviour is unchanged there.
The candidate is not admitted by any endpoint path in this commit.

**Tests.** The four kernel and two host tests are meaningful, not vacuous. `NativeOnly` and the
`ScopedBoundary`/`ScopedVerifier` legacy methods panic if entered, so a forwarding or selection
regression would fail them. Old test bodies are byte-preserved: `final.py` diffs the predecessor
`runtime_loop_tests.rs` minus the 3-line module hook, and the host test module minus the inserted
helper/tests.

ignore, prompt, dependency, SBOM or status file is touched. The evidence states that the tests are
synthetic and that no model run or coding score exists. The numbers I could trace match my run.

## Findings

No critical, high or medium finding.

- **L1 (low, backlog), `shells/host/src/coding_verifier.rs:303` and test assertion `:680`.** The
  scope keeps the distinct model binding and request digest, but the `VerifierCandidate` it produces
  carries neither. The host test asserts that native and endpoint candidates are byte-equal. That is
  harmless while no endpoint run admits a candidate. Fix: before endpoint candidates reach the
  verifier registry in full composition, make the coordinator or registry bind admission to the
  owning run's request digest or model binding (for example through the proposal's run binding),
  and add a test that a candidate from one request family is refused for the other.
- **L2 (low, backlog), `kernel/engine/src/runtime_loop.rs:2903`, `:3343`, `:3709`, `:3824`.** Every
  scoped call re-runs full request verification (clone plus canonical-JSON SHA-256) on a private
  request that was already verified at construction (`:1703`), so the error branch cannot be
  reached. On the execute path (`:3709`) that branch would also sit after `ToolStarted` was emitted
  (`:3699`). Fix: build the scope once from the construction-verified request (for example with a
  crate-private pre-verified constructor) or before emitting `ToolStarted`.
- The predecessor's L1 (preflight/refusal closure) and L2 (digest-shape/failure-binding/completion
  clocks) and earlier lows remain backlog as stated. The TASKS and evidence summaries of that review
  are faithful to its text.
