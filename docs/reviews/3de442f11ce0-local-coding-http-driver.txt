## Findings

### M1 (medium): consent prompts are written to a non-blocking tty, so large prompts fail and an unseen tool approval is sent as a person's Deny

Location: `platforms/local-api/src/coding_cli_driver.rs:58-77` (`Signals::confirm` opens `/dev/tty` with
`O_NONBLOCK`, then `writeln!(tty, …).and_then(flush)`), together with `:175-181` (`Presentation::decide`
maps every `confirm` error to `Ok(RuntimeApprovalDisposition::Deny)`).

`O_NONBLOCK` was added so the answer read can be interrupted. It also applies to the prompt write. When the
pty output queue fills, `write_all` gets `WouldBlock` and does not retry. `confirm` then returns `Err` after
printing a truncated review without the "Type exactly …" line.

Reproduction 1 (Python, independent of the binary). Open a pty slave with `O_RDWR|O_NONBLOCK` and write
complete buffers while a reader drains the master 4 KiB at a time:

- 16 KiB with a 1 ms reader delay: EAGAIN at 16,383 bytes.
- 64 KiB: EAGAIN at 26,624 bytes even with no delay.

Reproduction 2 (actual `agentmage-code` from this commit). Script:
`/lane/state/tmp/review-3de442f11ce0-logs/ttyrepro/repro.py`. A loopback fake peer answers
`GET /v1/code/runtime` with a valid selection. A pty harness reads 4 KiB per `select` and answers the
prompt when it appears. The command is `runtime-run 30 <task>`:

- Tasks of 3,000–13,000 bytes: the prompt is complete and `POST /v1/code/runtime/prepare` is sent.
- Tasks of 15,000 and 16,000 bytes, both inside the client's accepted 16 KiB task bound: the prompt stops
  after about 12–16 KB with no "Type exactly" line. The client exits 1 having made only the GET, so the
  person is never asked.

Practical impact on the claimed path:

- The start disclosure prints the entire pretty-printed request; the producer fixture alone is about 13.4 KB.
- Each approval prints the whole challenge. Its `presentation.arguments.bytes` is a JSON number array at about
  12 output bytes per payload byte, plus `arguments_json`.
- So ordinary tasks and edit or command approvals with more than roughly 1 KB of arguments can cross the
  threshold, depending on how fast the terminal drains.

The failures differ by step:

- **Inspection or start:** the run is refused. This fails closed, but the feature is unusable.
- **Tool approval:** `decide` returns `Deny`. The driver sends that through `advance` as an exact canonical
  decision, so the durable record shows the operation declined by the person, who never saw it. The run
  then continues on that false decision.

No unauthorised effect results, so this is not high. But the batch's central claim is that "every
consequential tool" gets "a fresh controlling-terminal decision". For realistic prompt sizes that claim is
not reliable, and the tests do not cover it: all tests use small prompts and a 64 KiB `select` reader.

Concrete fix:

1. Write the prompt with a blocking descriptor, or keep `O_NONBLOCK` and loop on `WouldBlock` with `poll(POLLOUT)`
   while checking `stopped()` and the deadline. Only the read needs to be interruptible.
2. Map a terminal I/O failure in `decide` (open, write, EOF) to `Err(CodingClientError::Approval)`, so no
   decision is sent, rather than to `Deny`. Reserve `Deny` for a line the person actually typed.
3. Add an executable pty test with a prompt of at least 64 KiB and a slowly draining reader, covering the
   inspection, start and tool-approval prompts.

### L1 (low, backlog): typed-ahead input can decline the next operation before it is shown

`Signals::confirm` (`coding_cli_driver.rs:78-99`) reads from the existing tty input queue without flushing it.
It also leaves the remainder of an overlong line (`line.len() == 256`) queued. In one connected run, a stray
extra Enter, or a paste with a trailing newline followed by Enter, is consumed by the next prompt and declines
it immediately. A typed-ahead line cannot approve, because each challenge digest is fresh. Fix: run
`tcflush(TCIFLUSH)` after writing each prompt and before reading, and discard the queued line on overflow.

### L2 (low, backlog): all HTTP failures collapse to `RuntimeFailed`

`HttpRuntime::post` and `release` (`coding_cli_driver.rs:194-205, 316-329`) map every client error to
`RuntimeTransportError::RuntimeFailed`. So the shared driver's `RunUnavailable` path, the "released
suspended run" notice in `request_job_control`, is unreachable over HTTP. A host-released suspended run
ends with a generic `cli.runtime.unavailable` error instead of the specific notice. This fails closed. Fix:
carry the API's typed refusal code through to the matching `RuntimeTransportError` variant.

No other high or medium finding. Confinement is unchanged by this batch. The adapter mints no grant, has no
tool, model or filesystem authority and never calls the generic cancel route; `cancel` returns
`RequestDenied` and cancellation uses the revision-bound job ledger (test-verified). There is no
approval resend after a lost reply (test-verified). Terminal text is escaped through `safe`. Evaluation
integrity is untouched: no held-out content, hidden test, fixture, threshold, score or dependency changed.
Prior L2 (resume terminal coverage), L3 (closed-channel recovery) and L4 (graceful shutdown) remain backlog,
as the evidence states. Prior L1 (scenario disclosure) is addressed truthfully.
