## Findings

### M1 (medium): the scoreboard leaves out failure causes that the retained logs show, so the low scores read as poor coding ability

`docs/evidence/coding-scoreboard.md:43-50` (Failure causes) and `:52-73` (terminal outcomes)

The scoreboard reports 76 of 80 failures only as `chat-failed`. It states that the API outcomes "do
not identify a model-internal cause", but never states the cause that its own hash-bound backend log
slices record. I classified every attempt from the retained `server.log` slices; every slice hash
matches its `backend-timing.json`:

| Model | Split | Prompt larger than 8,192-token context (rejected before generation) | Context filled mid-generation (`truncated = 1`) | 4,096 output cap reached | Stopped below limits |
| --- | --- | --- | --- | --- | --- |
| muse | dev | 10 | 9 | 7 | 4 (all 4 passed) |
| muse | held | 5 | 5 | 0 | 0 |
| gpt-oss | dev | 10 | 12 | 6 | 2 (`chat.response.invalid`) |
| gpt-oss | held | 5 | 5 | 0 | 0 |

For example, muse dev-002: `request (11373 tokens) exceeds the available context size (8192 tokens)`.
The held-out prompts that were rejected were 10,093 to 18,578 tokens.

- **No held-out attempt fit.** For both models, not one of the ten held-out attempts produced a
  generation that fit the budget.
- **One third of development never reached a model.** 10 of 30 development requests were rejected
  before any generation.
- **Every muse attempt that fit passed.** All four muse generations that finished within the limits
  passed.

The published 0/10, 0/30 and 4/30 therefore mainly measure the chosen context budget: 8,192 tokens
in total, with 4,096 of them reserved for output including reasoning. They say little about coding
ability. The API messages in the table add to the confusion: the status event says "Check that its
model is ready", and output-cap stops appear as `incomplete`.

Why this is medium:

- **Requirement.** T-311 requires "failure causes", and Decision 0154 §4 requires "failures".
- **Baseline value.** This is the reference later rows will be compared against. A later engine
  given a larger context would show a large gain that comes from context size rather than the
  engine.
- **Not high.** Every published number traces to raw records. No attempt was dropped and nothing
  was tuned.

**Fix (in-row, no model rerun, no held-out reuse):**

1. Derive a per-attempt backend termination class from the already bound log slices. Use these
   classes: `prompt-exceeds-context`, `context-exhausted`, `output-cap`, `stopped`.
2. Publish the class per model and split, and per development task.
3. State plainly at the top of the scoreboard that the 8K / 4K budget stopped 36 of 40 (muse) and
   38 of 40 (gpt-oss) attempts from producing a complete answer, including every held-out attempt.
4. Say that the result is therefore not evidence of relative model quality, and that later
   scoreboards must name a changed context or output budget as a separate variable.
5. Preferably have `scripts/coding_baseline.py` or the aggregate carry that class, so the published
   cause can be re-derived with one command.

### L1 (low): a deeply nested model answer crashes collection

`scripts/coding_baseline.py:51` and `:89`

`apply_edits` calls `json.loads` on model text. `one()` catches only
`OSError, ValueError, SmokeError, HTTPException`. A deeply nested answer, which fits inside 4,096
tokens, raises an uncaught `RecursionError`. Reproduced: `apply_edits(b'x = 1\n', '['*100000+']'*100000)`
gives `UNCAUGHT RecursionError`, while NaN, duplicate keys and huge integers refuse correctly.

The batch would then abort with no `record.json` or `batch.json`, and the rerun refuses
(`candidate-exists`). This fails closed: `scoreboard` refuses an incomplete split. It did not happen
in this campaign. The risk is that it pushes an operator toward a substitute rerun.

**Fix:** catch `RecursionError` and treat it as `edit-refused`, or parse with a depth bound. Add a
synthetic test. Apply the same to the parser that T-303/T-306 will reuse.

### L2 (low): the frozen dev-004 base control has a timing race that can fail the whole verifier

This is seen only at runtime, in the hidden dev-004 SIGINT termination test.

My first complete `verify --purpose row-close` failed only because the dev-004 base control
classified one method as ERROR (`TimeoutExpired` after 10 s) rather than FAIL. The repeat passed.
The base still fails and the reference still passes, so this is not a discrimination failure. But
`expected_base` (`scripts/coding_eval_oracle.py:1030-1048`) requires the exact count profile, so
system load alone can invalidate the receipt that admission requires.

For generated candidates, a correct solution under load could time out and score a false negative.
It can never produce a false pass. It did not affect this baseline: both models failed dev-004 at
the output cap.

**Fix (backlog):** disclose dev-004 as a known timing race next to dev-003 in coverage and attempt
rows. Do not change the hidden test or the threshold.

### L3 (low): the "current 8K chat profile" label describes a mixed configuration

`docs/guides/coding-baseline.md:31-33` and the scoreboard's "Baseline runs" section

The product chat profile `demo/model.json` is 8,192 context with 2,048 output. The baseline instead
ran the development model-lab launcher, used its 4,096 output, and overrode its 32,768 context to
8,192. The private `launch_batch.py` makes that override after `coding_model_lab.load_config()` has
validated "context must be above 8K". The published parameters are accurate. Only the "current
profile" wording overstates the match.

**Fix:** state that the configuration was "8K context (product chat value) with the lab's 4,096
output reservation".

### L4 (low, T-302 backlog): API diagnostics mislabel context overflow and length stops

When upstream rejects an oversized prompt, the API emits `chat.transport.status` with "Check that its
model is ready". Most stops at the output cap surface as `chat.response.incomplete`; only 3 of them
appear as `complete:length`. This misleads users and future scoreboards.

**Fix:** map upstream context-size rejections to a distinct code, and report length terminations
consistently.
