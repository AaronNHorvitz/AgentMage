## Findings

No critical, high or medium finding.

**L1 (low, backlog): a top-level source named after a standard-library module can still change the
trusted project run without being imported by tests.**

- Location: `shells/host/src/coding_development_runtime.rs:446-455`, where `python_source_path_allowed`
  accepts any top-level `*.py`, and `:2276`, where `unittest discover ... -t .` puts the worktree root
  at the front of `sys.path`.
- Reproduction (Python 3.15.0, `-I -B -m unittest discover -s . -t . -v`, in a temp dir with the
  same `src/calc.py`, `src/__init__.py` and failing `test_calc.py` as the new regression):
  1. Without extra files the run ends `FAILED (failures=1)`.
  2. Add a top-level `dataclasses.py` that loads the real stdlib `dataclasses` into `sys.modules`
     and sets `unittest.TestCase.assertEqual = lambda *a, **k: None`. The run now ends
     `Ran 1 test ... OK` with exit 0.
  3. Why it happens: the runner itself imports `dataclasses` lazily, through `_colorize`, after
     discovery has inserted the root into `sys.path`. Neither the test nor `src/calc.py` imports it.

  `python_source_path_allowed(["dataclasses.py"])` returns true, so an existing file with that name
  is admissible through an explicit selection in either layout. Default `src/` selection is not
  affected, because `src/x.py` imports as `src.x`.
- Why it is low:
  - it needs an existing top-level file with a stdlib module name and an explicit user selection;
  - the guides already say other source can alter test behaviour and that only the frozen scorer
    supplies scores;
  - no row closes or score is claimed here.

  The new guide rationale, that initializers are special because they run without being imported by
  tests, applies equally to this case.
- Fix: also refuse top-level sources whose stem is in `sys.stdlib_module_names`, using a pinned list
  for the pinned interpreter, or record this limit next to the initializer note in both guides.
  Track it in this row's backlog before any root-layout success claim.
