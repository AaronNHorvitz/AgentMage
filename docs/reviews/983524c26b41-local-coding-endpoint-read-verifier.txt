## Assessment against the request's claims

- **Construction is inert.** `CodingEndpointReadCheck::new` validates the length bound and a lowercase
  64-hex digest. `for_request` and `read_verifier` read no file, issue no grant, dispatch nothing and
  admit nothing.
- **for_request binding.** It re-verifies the seal and requires all of the following, otherwise it
  refuses:
  - ephemeral read-only mode and no event cursor;
  - one to `max_tool_calls` checks, all in the request's workspace, with no duplicate paths;
  - criteria equal to both `task.acceptance_criteria` and `work_packet.acceptance_checks`, exactly
    and in order;
  - required evidence exactly `[ToolOutput]` and the Observe capability class;
  - no mutable files and no authoritative evidence;
  - visible tools equal to the exact original read-file catalog.
  
  Free text such as "The code is correct" refuses (test mutation 0). The model cannot select checks.
- **Completion.** Native-family `verify` refuses. `verify_completion` checks:
  - the seal again, the stored request hash (so a foreign run, snapshot, policy or model refuses;
    tested, with an assertion that the seal changed), the proposal scope and exact ordered
    postconditions;
  - the original `parse_candidate`, requiring NoOp and an empty `checks_not_run`;
  - unique non-empty receipts, unique call ids and unique evidence ids, with counts equal to the number
    of results;
  - for each result: success, NotChanged, no error or issues, the original output schema and media
    type, the payload hash, `ReadOnlyResult::verify`, not truncated, exactly one file and one item,
    a canonical path, full range and content hash, and one native-shaped evidence item bound to the
    call id, `result_sha256` and the snapshot id, present in the coordinator ledger.
  
  Object-id binding plus unique call ids makes result-to-evidence a bijection. Each postcondition
  passes only if every read of its path matches, so a later conflicting read defeats an earlier good
  one (tested). Its evidence comes only from that path's results.
- **I found no way to obtain NoOp without a coordinator-produced, successful, complete read whose bytes
  equal the trusted digest.** Model output can only affect the claim, and a false claim yields Failed
  (tested). Content from a prompt-injected file cannot change the verifier's decision, because the
  decision depends only on bytes and digests.
- **The production path is reachable.** The socket test drives the production retained owner,
  context, transport and verifier through an exact approval to canonical NoOp (matching bytes) and
  Failed (different bytes), with terminal rereads that do not re-execute, events present, and release.
  Its effect, permission and receipt boundary is a labelled SYNTHETIC wrapper that rewrites evidence to
  the production shape. I confirmed above that this shape matches `CodingEndpointFiles`. Honest
  labelling holds: the guide, evidence document and TASKS.md say there is no native admission, real
  model, worker success or score, and that the verifier does not certify summary meaning, correctness,
  tests or post-read freshness.
- **The confinement surface is unchanged.** The native file, grant and worker code and the guidance

## Findings

No critical, high or medium findings.

- **L1 (low): an unrelated failed read fails the whole run, and the docs do not say so.**
  - Location: coding_endpoint_read_verifier.rs:209-212 and 271. Any result that is unsuccessful,
    truncated, multi-item or missing evidence makes `grounded_reads` return `None`, and then every
    postcondition fails (probe B).
  - Effect: this fails closed, so it is safe. But a real model that first tries a wrong path and then
    reads the right file will get Failed. docs/guides/runtime-endpoint-runs.md only says that every
    *selected* file needs a complete successful read.
  - Fix: either state in the guide that any unsuccessful read in the run fails acceptance, or ignore
    unsuccessful results for paths that no check covers. If you choose the second, keep refusing
    unsuccessful reads of checked paths.
- **L2 (low): `for_request` is public and skips the exclusion check.**
  - Location: coding_endpoint_read_verifier.rs:101. A trusted caller can construct a verifier for an
    excluded path by calling `for_request` directly (probe D). Only `read_verifier` checks the
    compiled exclusions.
  - Effect: this is not exploitable for disclosure, because the native file boundary still refuses
    excluded paths, so such a check can only fail. It does contradict the documented single entry
    point.
  - Fix: make `for_request` `pub(crate)` (tests are in-crate), or have the startup selector be the only
    constructor.
- **L3 (low): checks that can never pass are accepted at construction.**
  - Location: coding_endpoint_read_verifier.rs:101-142. A check whose `byte_len`, plus JSON overhead,
    exceeds `request.limits.max_output_bytes` is accepted (probe E: limit 4096, a 4097-byte file),
    but completion can only ever be Failed.
  - Fix: refuse such checks in `for_request` (for example `byte_len > max_output_bytes`) so that a
    trusted caller learns at selection time rather than after a model run.
- Earlier same-row lows (startup L1–L3, files L1–L3) are unchanged and remain backlog. Case-insensitive
  exclusion matching (files L2) applies equally to the new `read_verifier` exclusion check.
