## What I verified by reading

### Attach (`coding_owned_api.rs:47-120`)

Attach requires:

- the control token (`handle_owned` returns 403 without it);
- a held controlled operation;
- both consents;
- the closed model and scenario lists.

Under the state lock it does the following, in order:

1. Refuses on stop, on an attached runtime, on a missing owner and on a poisoned owner. A poisoned owner
   stays in state.
2. Refuses with "busy" and puts the Arc back if any other reference exists (`Arc::try_unwrap`).
3. `into_runtime_worktree` compares the displayed root SHA before `verify_created`, and returns the
   owner intact on refusal.
4. `build` calls `check_workspace` (an exact `created.path` match plus a held-identity check) **before**
   `CodingDevelopmentActivation::validate` opens any activation path.
5. It then checks the canonical runtime state root against the manual store and both held roots.
6. `factory.attach_owned_worktree` re-checks the workspace.

Further properties:

- The manual `state_root` passed through `LinuxStrictLocalRootInspector` (absolute, no symlinks, no
  `.` or `..`), so the component-wise `starts_with` comparison runs on canonical paths on both sides.
- Every error path in `build` drops the factory before `restore_lease`.
- Stop after construction drops the empty service before restoring the owner.
- No resume flag exists.
- The factory is created with `resume_requested=false`.
- The response says `model_and_tools_approved:false`, and no grant or approval is minted.
- I found no marker, path, receipt or decoded-lease adoption.

### Recover (`:176-215`)

Recover requires:

- consent;
- no manual owner;
- a runtime that exists, is free (`try_lock`) and is owned;
- `service.is_empty()`, meaning every prepared and active run has been released;
- a successful `Arc::try_unwrap`.

It then drops the port (`shutdown` on an empty service, then the factory and its lease clone) before
`try_into_repository`. It never stops a job implicitly. The response says `apply_approved:false` and
`fresh_diff_required:true`. The `prepare_apply` path still requires a root-identity match, lineage, a
full preview and a separate decision.

### Exclusion while attached

### Shutdown (`:582-588`, `:1059-1102`)

1. A cancellation is sent through the passive probe only, once a correlation ID exists.
   `SharedCancellation::request` keeps a different earlier signal.
2. `Stop` is retried until queued, and `results` is drained so a capacity-one publication cannot block.
3. The worker is joined, then the event pump.
4. Drained results are discarded, and sessions that are not terminal leave their chains open.

`job_outcome_event` maps a cancellation without an applied request to `Failed`. So no terminal outcome
or acknowledged cancellation is fabricated. `RuntimePort::Drop` calls `shutdown` only for `Owned`, and
`serve_state` drops `State` only after the HTTP workers have joined.

## Findings

No critical, high or medium finding.

### L1 (low, backlog): a worker detached by a failed start escapes the shutdown join and turns recovery into permanent loss of ownership

- **Code involved.**
  - `LiveCodingSession::Drop` (`shells/host/src/coding_live_runtime.rs:2006-2011`, unchanged) detaches
    a worker whose `busy` flag is set.
  - `LiveCodingRuntimeService::start` drops such a session without inserting it into `active`:
    `session.start()` sets `busy` in `dispatch`, then fails if no event arrives within `START_WAIT`
    (250 ms) or `refresh` fails (`:711`).
  - `continue_from_checkpoint` has comparable post-spawn failure exits.
- **Consequences.**
  - The new `shutdown()` (`:582`) joins only `active` sessions. A detached worker is therefore neither
    joined nor cancelled, which contradicts Decision 0159's "join all workers before returning … must
    not inherit … reliance on process teardown".
  - `is_empty()` is true, so `recover` proceeds. The detached worker's composition still holds a
    boundary lease clone, so `try_into_repository` returns `Err(lease)`.
  - `restore_lease` (`platforms/local-api/src/coding_owned_api.rs:122-125`) discards that lease with
    `map_err(|_| …)` and answers 500 `code.runtime.owner-held`.
  - The state then holds neither a repository nor a runtime. Attach returns 428 and recover returns 428
    until restart.
  - Creation authority and transferable lineage are lost for good. This contradicts the lease's own
    documented contract: "Busy ownership is returned intact for later explicit recovery".
  - Files in the worktree and the original checkout are not touched.
- **Why low.** The trigger is a rare failure path. The loss is fail-closed and the authority is
  process-only. It cannot widen confinement.
- **Fix.**
  - Have `restore_lease` keep an `Err(lease)` in a `State` slot, for example a held-recovery lease
    that a later `recover` retries.
  - In `start` and `continue_from_checkpoint` failure paths (or in an embedded-mode `Drop`), call
    `shutdown_worker()` instead of detaching.
  - Add a host test: the start fails with the worker busy, then `is_empty()`, then shutdown joins.

### L2 (low, backlog): each attach leaks a platform adapter, the profile and a held workspace descriptor

- **Where.** `CodingDevelopmentRuntimeFactory::new` and `build_repository_composition` use `Box::leak`
  (`shells/host/src/coding_development_runtime.rs:438`, `:759`, `:767`). `refresh_repository_composition`
  (`:492`) leaks again on each refresh.
- **What leaks.** The leaked `LinuxCodingWorkspace` holds an open worktree root descriptor.
- **Why this commit makes it worse.** In the separate-process host this was a single leak per process
  plus one per refresh. The new attach/recover cycle repeats it inside the long-lived `serve-coding`
  process. N cycles leave N unreachable workspace descriptors and their allocations behind after
  recovery.
- **Why low.** The descriptors are unreachable, so no authority can use them. Only an authenticated
  control client can trigger the cycle.
- **Fix.** Make the factory own these values (for example `Arc` or owned fields with a self-borrow
  helper) rather than `'static` leaks. At least count the leak, and disclose it in the guide until then.

### L3 (low, backlog): the "attached" exclusion is checked outside the controlled-operation lock

- **Where.** `handle` (`platforms/local-api/src/lib.rs:1064-1071`) checks `runtime.is_some()` under
  one lock acquisition. The chat, workspace and repository handlers later call `begin_scoped`
  (`:786`), which never re-checks `runtime`.
- **How it can be bypassed.** A request that passed the guard before attach started, and whose thread
  stays descheduled until attach has published, can begin a manual operation while the coordinator is
  attached. That is the "simultaneous manual … operations" Decision 0159 excludes.
- **Why low.** Exploiting it needs the single local control client to race its own requests within a
  microsecond window spanning the whole of attach. Any manual worktree write still shows in the later
  full apply diff.
- **Fix.** Refuse in `begin_scoped` when `guard.runtime.is_some()`, except for the runtime and
  ownership operations themselves.
