## Code review

- **Public entry and seams.** `LinuxCandidateTreeBuilder::build` (local_commit.rs:195-209) always calls
  `candidate_build::run` with `NativeSession`. That uses the concrete collector and
  `CandidateSession::new_until`, with the original token and `Instant::now() + 30 s` taken at entry,
  before plan verification. The `Session` trait, `run_with` and `check_at` are private to the module.
  `CandidateSession::new` and `new_with` are now `#[cfg(test)]`, and `new_with_until` is private. A
  caller cannot install a collector, worker or clock. The builder stays dormant (`dead_code` allowances)
  and no API, grant or route is added.
- **One deadline.** Both `collect(deadline)` calls pass the entry deadline to `collect_until`. That
  function takes `min(deadline, now + 30 s)` (repository_safety.rs:367), so a phase can shorten the
  deadline but never renew it. `new_with_until` takes `min(deadline, now + PROCESS_TIMEOUT)`
  (repository_candidate.rs:148) and stores it as the session deadline. Every worker `perform` checks it
  before and after dispatch, and dispatch receives it (repository_candidate.rs:274, 384, 391). The test
  confirms the exact shorter deadline reaches the dispatch seam and that a 300 s outer deadline is
  capped below itself.
- **Setup.** `check()` runs:
  - before plan verification;
  - after the original capture and before `mkdirat`;
  - after the worker capture while `claim.armed` is still true;
  - after the final revalidation, before disarming.
  A stopped entry therefore creates nothing. A stop during capture drops the armed claim. That claim
  removes the directory only after it revalidates and only with `REMOVEDIR`, so a non-empty directory is
  retained. Both cases are tested against real private directories.
- **Ordering and late success.** `run_with` checks:
  - before and after every phase;
  - inside `checked_hash` before, between and after each 64 KiB chunk;
  - after cleanup and after the final collection.
  It unpacks `operation?` only after the last check, so a late worker or a late postflight cannot return
  `Succeeded`. Cleanup is called on every path once `start` has succeeded, including stopped and failed
  ones. Cleanup is not tied to the deadline (repository_candidate.rs:452) and still refuses unknown or
  replaced entries (`cleanup_allowed` and the entry-name checks). When `start` fails there is no session,
  and the setup claim guard handles rollback.
- **Bounds.** A vector-count mismatch is refused before the `BTreeMap` is built. Duplicate IDs are
  caught by `count != map.len()`. The checked total stays at most `MAX_TOTAL_POSTIMAGE_BYTES`. Each plan
  file must be present with an exact SHA-256. Mode, the per-file 64 MiB cap and the blob-ID equality
  checks in the worker are unchanged. The temporary-index path hash check moved from preflight into
  `NativeSession::start`. It still runs before any directory is created, and `new_with_until` checks it a
  second time. The checks that do not depend on scratch (manifest, repository and user-index digests)
  still run before hashing.
- **Confinement.** Worker arguments, environment (`candidate_environment`), sealed stdin, hardened Git
  prefix and descriptor revalidation are unchanged. No network or new process path is introduced. A
  failure after dispatch returns a plain error that carries neither rollback nor retry authority, as the
  decision states.
- **Tests.** The tests use controlled clocks and do not depend on a real-time success window. They cover:
  - every stage under both expiry and cancellation;
  - every phase failure;
  - five malformed-postimage and manifest cases;
  - exclusive expiry (`deadline - 1 ns` is accepted, `deadline` is refused);
  - every hashing checkpoint for lengths 0, 1, 64 Ki, 64 Ki+1 and 192 Ki;
  - a positive result in sha1 and sha256 reconciled through `reconcile_candidate_tree`, with
