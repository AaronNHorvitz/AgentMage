## Analysis

**Correctness of the reservation.** `project` serializes the result with `serde_json::to_vec`, which
is compact, not pretty-printed. `stdout` and `stderr` are `&[u8]` and become JSON number arrays. A
channel of n bytes uses at most 4n+1 bytes: at most three digits plus a comma per byte, minus the
last comma, plus the brackets. So `4*(a+b)` covers both channels apart from +2 bytes, which the
16 KiB allowance absorbs.

Kernel `verify_command_receipt` rejects a receipt whose retained channel bytes exceed the prepared
bounds (`command_runner.rs:629-630`), and `run_command_observed` requires the retained lengths to
equal the receipt's. The reservation therefore bounds the actual channel bytes, not only what the
command declared. The bounds come from the process-held `pending.prepared`, not from wire input, and
`max_output_bytes` comes from the verified sealed request.

Checked add, then multiply, then add cannot wrap. `.is_none_or(...)` refuses on overflow.

**Refusal semantics.** The check sits inside the existing immutable `prepare` closure. It runs after
binding verification and before `seal_runtime_approval_challenge`. Refusal returns `Err((self, error))`
before any grant, challenge or attempt consumption. The test confirms that `inspect`,
`inspect_command` and `inspect_validation` are unchanged, that `issued` is `None` and that there are no
receipts, for both commands and validations.

**Test discrimination.** The fixture bounds are 1024/1024 (`coding_repository_command_tests.rs:135`),
giving a reservation of 24 576. The tests refuse at 24 575 and admit at 24 576 with nothing else
changed, so the new check is the cause; the error code is the bounds-specific
`code.endpoint-command.bounds`. Two mutations would be caught: changing `>` to `>=` fails the
admission case, and changing the multiplier to 3 or less fails the refusal case.

The projection test fills both channels with 1024 × `255`. That is the worst-case three-digit
encoding, and it hits the exact retained ceiling. The test round-trips both channels exactly. For
validations it confirms `validation_passed == false` with `attempt == 1`. It also confirms that a
second `execute` errors and the call counter stays at 1, so there is no replay. The cancellation
handle cancelled on the refused original is observed on the later admitted handoff, so the same
original signal is preserved.

**Confinement.** The change only adds a refusal condition. No native manifest, worker confinement,
authority transaction, parser, retry ceiling or post-dispatch projection check is weakened. The
post-dispatch `bytes.len() > max_output_bytes → Uncertain` check is unchanged.

**Honest labelling.** The evidence, guide, decision and TASKS text all state the following:

- CPU and scratch/disk preflight remain backlog.

## Findings

No critical, high or medium findings.

- **Low (backlog), `platforms/linux/src/coding_repository_endpoint_command.rs:29`.** The fixed
  `COMMAND_PROJECTION_ALLOWANCE` of 16 KiB is not derived from the serialized size of the receipt,
  command receipt and normalized validation receipt. A validation whose parser output exceeds it
  (for example many small failing test records from structured stdout) can still pass admission,
  obtain approval, dispatch a real process and then be refused as `Uncertain` in `project`, after the
  attempt has been spent. This is disclosed in all four documents and is not a confinement bypass,
  because the effect stays confined and is not replayed. Fix: bound the normalized validation receipt
  size in the parser template, for example with maximum test count and name length, and include that
  bound in the reservation; or add a test that measures worst-case metadata at the native channel
  ceilings.
- **Low (backlog), `coding_repository_endpoint_command.rs:173-174`.** Admission compares only against
  the per-result `limits.max_output_bytes`, not against the run's remaining aggregate `OutputBytes`
  budget, so a late command in a run can still be refused after dispatch. This is disclosed. Fix: check
  the coordinator's remaining budget at evaluation time, before the approval prompt.
- **Low (test coverage), `coding_repository_endpoint_command_tests.rs` (overflow test).** The overflow
  method exercises `output_reservation` directly rather than through `into_endpoint_command`. That is
  acceptable, because the native 64 KiB ceilings make overflow unreachable through prepared commands,
  but it proves only the helper. No change is required.
