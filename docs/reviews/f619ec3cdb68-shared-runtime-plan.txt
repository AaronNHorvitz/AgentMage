## Findings

No critical, high or medium findings.

Low (backlog; none blocks this planning record):

- **L-1 (low, permission semantics): the default grant for a consumed MCP tool is unspecified and
  rests on an unstated way of classifying tools as state-changing.**
  docs/decisions/0205-one-runtime-for-model-driven-work.md:22 and CAPABILITY-ROADMAP.md:70 say "a
  tool that changes state asks by default". They do not say what a tool with unknown effects defaults
  to, or that a server's own description or hints (for example a server marking its tool read-only)
  cannot lower that default. Such hints are untrusted text from the other program. If they set the
  default, they would work as a permission, which is the boundary 0205:54-56 forbids.
  Reasoning: a hostile local MCP server marks a file-deleting tool read-only, and a later
  implementation that trusts the hint grants it "allow" without asking.
  Fix: add to 0205 and CAP-44 that every consumed tool starts as "ask each time" (or "off"), and that
  only the user or engine policy, never server-supplied metadata, can make it "allow". Also name tool
  descriptions as untrusted text that T-316's injection cases should include.
- **L-2 (low, determinism wording): the owner's "order, retries and limits are fixed" became
  "recorded".** 0205:39 and CAP-49 bind order, retries and limits in the record but never say that
  model output or tool text cannot change them during a run. Fix: add one sentence saying the flow
  definition and engine policy fix step order, retry policy and limits before a step runs; model
  output may only choose among branches the flow declares; tool, file, page or memory text cannot
  change them.
- **L-3 (low, logging of private content): CAP-49's "record every step's inputs and outputs"
  conflicts with CAP-42's "audit storage is not an excuse to log secrets or raw prompts" without
  saying how the two fit together.** 0205:30-34 sends sensitive content to protected storage but
  allows credentials to be recorded there. Fix: state that brokered credentials (CAP-34) are never
  step inputs and are recorded only as references, and that full prompts in flow records fall under
  the CAP-42 redaction and retention rules (deletion makes exact replay unavailable, which 0205:33-34
  already says).
- **L-4 (low, wording): the TASKS.md preamble (TASKS.md:7-9) lists "untrusted-data boundaries" among
  rules that "apply when interfaces are next touched".** This can read as if that boundary is
  deferred, but it already binds the current kernel (PRD.md:610) and 0205:54-56 states it without
  conditions. Fix: say the untrusted-data rule is already in force, and that only the folder-free and
  CLI-independence checks wait for the next interface change.
- **L-5 (low, stale count): PRD.md:5 ("The 48-capability roadmap"), which is in a changed file, and
  IMPLEMENTATION-AMENDMENT.md:8 ("defines CAP-01 through CAP-48") are now stale.** The same phrase
  appears in README.md:9, AGENTS.md:12 and IMPLEMENTATION-PLAN.md:5. Fix: update the count or drop it
  from the current pointers. Leave TASKS.md:2562, which must stay byte-identical, and the historical
  decision 0081 as they are.

Out of scope (backlog observation, not a finding on this commit): CAPABILITY-ROADMAP.md:18 and :177,
and many older files, still name the Coordinator and Memory sibling projects. The repository presents
them as permissively licensed public engines (CAPABILITY-ROADMAP.md:174-177), and this commit adds no
occurrence; it removes two. I cannot tell from the repository whether the owner counts them as
"private siblings" under the 2026-10-25 decision. The owner should confirm before any public release.
