## Source review

**Identity minting** (`platforms/linux/src/coding_repository_runtime.rs:35-67`).
- `into_runtime_worktree` first checks that the displayed root digest equals the held root and
  verifies creation.
- It then draws 32 bytes from `getrandom`. This is the same rustix idiom the crate already uses at
  `coding_repository.rs:250`; the workspace already enables the `rand` feature, and no dependency or
  lockfile changed.
- Anything short of a full 32-byte read returns `(self, err)` before `pending`, `command`,
  `validation`, `edit` and `apply` are cleared. So a randomness failure returns the owner intact.
- `recovery_sha256 = hash(nonce)` is new for every handoff, so a reattachment of the same root gets a
  different identity. The native test asserts `assert_ne!` and `code.runtime.recovery-stale` for the
  earlier consent.
- The struct fields are private. The only constructors are this function and the busy-return branch
  of `try_into_repository`, which moves the same two strings back. I found no constructor anywhere
  else in the workspace (`grep "LinuxCodingWorktreeLease *{"`). No decoded value can build a lease,
  and `check_recovery_binding` only compares; it never grants anything.
- `#[derive(Clone)]` copies both strings, so clones keep the identity. The lease does not derive
  Debug or Serialize.

**Poison readability.**
- `recovery_binding` reads the plain fields without touching `owner`'s mutex.
- The native poison regression panics while it holds the inner owner. It then asserts that the
  binding is unchanged and that `check_recovery_binding` succeeds. After that, `recover_repository`
  goes through the existing fail-closed branch, which strips creation authority and pending approvals.

**API ordering** (`platforms/local-api/src/coding_owned_api.rs:255-314`).
- Consent and the hex format are checked before any lock is taken. A malformed value gives 400
  `code.runtime.recovery-binding`.
- Pending path: `check_binding` runs under the service `State` guard before `restore_recovery`, and
  `?` returns with `state.recovering` untouched.
- Attached path: `check_binding` runs under the same `State` guard and the runtime `try_lock`, before
  the `recoverable()` check and before `state.runtime.take()`. The `State` guard is held from the check
  through `take`/`try_unwrap`. `RuntimeSession.owner` is assigned only at construction
  (`coding_runtime_api.rs:178,493`; `coding_owned_api.rs:249`) and is never reassigned. A stale
  request therefore cannot extract, drop or recover the current owner.
- The echoed digests in `recovered(&input)` come after a successful equality check, so they equal the
  lease identity.
- The existing release (`recoverable`), exclusivity (`try_unwrap`), poison and `restore_lease`
  invariants are unchanged.

**Owner snapshot** (`coding_owned_api.rs:77-92`, `lib.rs:1068`).
- The new path is routed to `handle_owned`, which refuses non-control tokens with 403 before
  dispatch. The HTTP test confirms this, and POST to the path returns 404 `code.runtime.route`.
- The snapshot returns only fixed fields and the two digests. It opens no path, reads no activation
  or source, and does not lock the inner owner.
- A separately launched runtime has `owner == None` and returns 409 `not-owned`, so the terminal
  refuses.

**Terminal** (`platforms/local-api/src/coding_cli_runtime.rs:100-155`).
- It reads status, then the owner snapshot. It requires `version`, `live_creation_owner`,

- The client sends the digests once and requires both echoed values. The stale-error, missing-echo

## Findings

No critical, high or medium findings.

**L1 (low, backlog): the terminal does not check that the owner snapshot's `recovery_pending`
matches the status it just displayed.**
- Location: `platforms/local-api/src/coding_cli_runtime.rs:121`. It only requires
  `owner["recovery_pending"].is_boolean()`.
- Scenario: between the two GETs, another control client changes the state (attached becomes pending,
  or the reverse). The confirmation then shows a `service_state` that contradicts `worktree_owner`.
- Why it is low: the server compares the exact root and handoff identity under the publication lock,
  so consent can only recover the displayed handoff. The person is shown two inconsistent views, but
  no other owner can be returned.
- Fix: refuse unless `owner["recovery_pending"] == state["runtime_recovery_pending"]`, and add one
  mismatch case to `recovery_refuses_incomplete_identity_before_confirmation_or_post`.

Earlier backlog items stay open and unchanged: lifecycle/continuation, factory allocation, and the
predecessor's standard-library shadowing L1.
