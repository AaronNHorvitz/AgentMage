## Analysis of the change

- **Guard placement and strength.** `authorization.transaction_id().as_str() != self.prepared.plan.commit_transaction_id`
  is inside the pre-launch refusal block. That block comes after the single-entry latch and the dispatch
  clock sample, and before the cancellation check and `executor.execute`. A mismatch sets `ApprovalDenied`
  and returns `EffectLaunch::failed()`, with no permit and no executor access.
  - The comparison is byte-exact, with no normalisation in `AuthorityTransactionId::from_raw`.
  - Both identifier validators accept the same alphabet (alphanumerics and `. _ : -`, at most 128 bytes; the
    authority side also bans `*`, which the plan alphabet never allows). So every valid plan ID is also a
    valid transaction ID and the guard cannot be dodged through validator asymmetry.
- **Composition claim.** Within one canonical store, the first attempt at a plan durably records its
  transaction ID at `PreparedStored`, before consumption or launch. Every later attempt with the same ID is
  refused before consumption. Every attempt with a different ID passes the store but is refused by the
  driver before launch. Changing the plan's ID changes `plan_sha256` (whole-plan canonical hash), which
  breaks the manual approval binding (`approval.commit_plan_sha256`) and the exact request bytes.
  - The new tests reproduce this across success and all six fault points, after a real encrypted reopen with
    the original issuer and coordinator dropped. A genuinely new grant stays `Issued` on same-ID replay and is
    `Consumed` on renamed dispatch, with zero launches. A second reopen preserves `receipts[0]` (the original
    recovery outcome: Succeeded, Uncertain or Failed, as expected per fault) and `receipts[1]` (the refusal).
  - If the first attempt crashed before `PreparedStored` became durable, no history exists and no effect can
    have happened, so a same-ID retry is correctly allowed.
- **Honest limits.** The evidence, guide and TASKS text state the limits plainly:
  - the protection depends on retaining the same canonical store; a fresh or replaced store is not covered;
  - consent, checker and artifact provenance are not authenticated;
  - held objects, approval, clock and Git results are synthetic;
  - native admission, original-owner approval, repository and signer recovery, model measures and approved
    push remain open, and no product route is enabled.

  I found no overclaim. Every number in the evidence (3,090/72/72, 46 targets, 44 = 3 new + 41 controls, the
  timings and the raw SHA `077a2133…982a`) matches the builder's retained `validation-1/result.json` and
  post-commit log. My independent run reproduces the counts and identities.
- **Test-only visibility.** `pub(crate) mod review_preparation_tests` stays under `#[cfg(test)]`
  (local_commit.rs:1883-1885). The `FixedClock` and `SyntheticExecutor` visibility changes are in that test
  module. No production constructor, authority type or public API changed.
- **Older tests rewired to the plan ID.** The fixture's default ID becomes `fixture-commit` in the clock,
  scope, operation, unwind and single-use tests, so those tests still reach their intended checks instead of
  failing on the new guard. The single-use reentry repeats `fixture-commit`, so the latch, not the guard,
  refuses it. The latch mutant above still dies on that test, confirming this. The unwind test's second
  dispatch with `unwind-second` asserts the dispatch clock is untouched (`driver.clock.0.is_empty()`), which
  proves the latch refused it before the transaction guard could.
- **Confinement, secrets and public content.** No sandbox, network, workspace-write or push path changed.
  - Added lines contain no home paths, usernames, hostnames, credentials or personal data; `/lane/state/tmp`
    references follow long-standing repository practice (227 earlier docs).
  - The commit's author metadata is the repository's existing owner identity, not file content.
  - No trademark branding, third-party code or patent material was added.
  - No dependency, Cargo.lock, SBOM, licence, evaluator, held-out or hidden task, scorer, prompt, threshold,
