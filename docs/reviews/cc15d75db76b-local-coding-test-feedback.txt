### Adversarial cases (my own; disposable copy, `cargo test ... --lib reviewer_`)

All four of my tests passed after one correction to my own assumption, described in case 2.

1. **Slot swap across routes.** With a validation preview pending, I replaced the slot with an ordinary
   command preview. `decide_validation` on either digest returned `code.validation.choice-required`, and
   `decide_command` on the validation digest returned `code.command.stale`. With a validation preview back
   in the slot, `decide_command` (approve or deny) returned `code.command.validation-choice-required`, and
   the preview stayed pending. Attempts stayed 0 and there were no canonical receipts. **No crossing.**
2. **Replay and a stale held-aside preview.** I took an attempt-1 preview out of the slot, then prepared and
   admitted another attempt-1 preview (assertion failure). Re-deciding the consumed digest returned
   `choice-required`. Running the held-aside preview through `run_command` returned
   `code.validation.stale` from the consumption-time re-check, before the executor ran (calls = 1,
   attempts = 1, latest retained). There was exactly one canonical receipt. My first draft asserted that
   the receipt JSON contains the outer preview digest. That assertion failed because canonical receipts
   are content-free (IDs and `operation_sha256`), the same as on the existing command route. I traced
   the outer hash instead: `run_command` places it in `ExactEffect.preview_hash` (command.rs:228), which
   becomes the grant/approval `preview_sha256` (coding_repository.rs:616,647,683). Not a finding.
3. **Outer preview binding.** Recomputing SHA-256 over the preview minus `preview_sha256` equals the
   pending hash. The hashed body contains `validation_template`, `prior_receipt_sha256`, `attempt`,
   `maximum_attempts`, the expiry, the root and creation receipt, and the full kernel command preview.
   `operation` is `execute-validation`. The outer digest differs from the inner command preview digest,
   and a changed kind changes `template_sha256`.
4. **Contradictory or hostile envelopes** (all `validation_passed: false`, status `malformed`):
   - exit 0 with `assertion_failed`;
   - exit 0 with `compile_failed`;
   - a failed name containing ESC/CSI and U+202E;
   - `passed` with a non-empty failed-name list;
   - an unknown envelope field;
   - two concatenated envelopes.

   An envelope claiming `u32::MAX` passed tests with exit 0 normalizes to `passed`. This is expected: the
   envelope producer is trusted to describe its own tests, which the guide states plainly ("normalization
   is not independent task grading").

## Assessment against the requested focus

- **Exact outer preview binding** (template, budget, prior, attempt, expiry, root, creation receipt):
  verified by code (validation.rs:152-168) and case 3. The receipt's `approval_sha256` is the outer hash
  (builder test, validation.rs:274 via command.rs:274).
- **Input confirmation vs execution approval.** `approve_definition` must be the literal Boolean `true`
  (a string gives 400, `false` gives 403). Confirmation yields only an inert preview. Execution needs the
  separate exact `decide` plus TTY `test <sha>` consent. `user_input_approval_sha256` is set to the
  deterministic source hash. The guide and the code comment honestly call this a provenance binding,
  not authority.
- **Route separation and single slot overwrite.** Verified (builder tests and case 1). Inspect routes
  filter by preview kind. The CLI refuses when the inspected `operation` mismatches.
- **Denial and expiry vs consumption.** Denial and expiry leave attempts at 0 (builder test). The attempt
  is spent in `run_command` after root and expiry re-checks and before `exact.execute`
  (command.rs:215-219). An authority refusal before launch therefore also spends and blocks; this is
  conservative and documented.
- **Stale or changed definition and prior.** A changed minimum count, kind or template, a foreign or
  absent prior, a pass as prior, a non-assertion prior or an exhausted budget all refuse (builder tests
  and case 2). One immutable template per created worktree: `self.validation` resets only on observed
  native creation success (coding_repository.rs:388).

  latest = null, and every further prepare refuses with `code.validation.uncertain`. In the API, an
  unwind poisons the repository mutex, which fails closed.
- **Reopen without adoption.** Reopen shows no pending, no latest, 0 attempts and `created` = none, with

- **CLI exit.** `validation-run` returns failure when `validation.validation_passed != true`, even with
