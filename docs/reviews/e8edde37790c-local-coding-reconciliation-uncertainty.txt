## Analysis

### Production change (`local_commit.rs:1345-1354`)

Only the `Err` arm after `executor.execute` changes.
- Every refusal before the executor still returns `EffectLaunch::failed()` with an uncrossed boundary:
  reentry latch, clock failure, grant/operation/transaction/held-scope/arguments/packet checks, and
  cancellation.
- I confirmed with m3 that the single-use test now pins this.

The post-executor arm records the original error and returns
`completed(from_redacted_material(Uncertain, error.code(), StateChange::Uncertain))`.
- `error.code()` is a closed set of static strings (`local_commit.rs:49-59`). No executor output, path,
  object id or message reaches the digest, so the material is content-free.
- `reconcile_local_commit` only returns `Ok` when `result.outcome == Succeeded`
  (`local_commit.rs:1023`), so there is no new success path.
- A failure of the `prepared.verify_at` re-check inside reconciliation is now also uncertain. That is
  correct, because the executor has already run.

Coordinator handling (`authority_transaction.rs:791-829`):
- `uncertain` is the OR of state-change and outcome.
- A `Reconciling` checkpoint records the uncertain flag. The grant goes through `mark_execution_uncertain`,
  and the terminal code is `authority.transaction.effect_uncertain`.

Recovery:
- A `WorkerReturned` crash leaves the transaction in `LaunchCommitted`. Recovery marks it
  `recovered_uncertain`.
- A `ResultReconciled` crash leaves `Reconciling` with `uncertain_effect = true`, and recovery preserves it
  (`authority_transaction.rs:893-914`).
- Under the old `failed()` behaviour, the normal and `ResultReconciled` paths both produced a non-uncertain
  `Failed`/`launch_failed` receipt. The new test kills that mutant on the normal path, as m1 confirms.

No panic handler, rollback, retry, authority change or ownership bypass is introduced. The reentry latch
is unchanged, so a second dispatch through the same driver returns `failed()` without a second launch.

### New durable method (`authority_transaction.rs:2704-2915`)

The method runs seven synthetic result failures × three paths = 21 iterations, each in a fresh store
directory. Each iteration exercises the actual commit driver, policy, grant issuance and consumption,
coordinator checkpointing and the encrypted `OperationalStore` / `DurableAuthorityRuntime`.
- Every case asserts that the synthetic ref moved (`task_branch_after != task_branch_before`), so each one
  really is an "effect may have happened" situation.
- The original store, coordinator and issuer are dropped before reopen.
- After reopen the method asserts:
  - one receipt, with outcome `Uncertain` and the original transaction and attempt ids;
  - the transaction is `uncertain_effect` and the grant is `Uncertain`;
  - on the normal path, the recovered receipt equals the original receipt;
  - a replay through a fresh driver is refused with `InvalidIdentity` and zero launches;
  - a second reopen holds exactly the same receipt, grant and transaction state.
- On the normal path it also asserts no local success receipt, the retained error `ResultDenied` and
  exactly one launch.

Everything is synthetic: Git effects, approval, clocks and held objects. The evidence says so plainly.

### Confinement and security boundary

This change narrows rather than widens behaviour: it adds uncertainty and no permission. The driver has
no non-test caller, so no workspace, sandbox or network surface changes.
- Recovery after reconciliation failure is now fail-closed. The grant is marked uncertain and replay is
  refused, so a crash or failed reconciliation cannot be turned into a silent retry.
- No path traversal, symlink, environment or prompt-injection surface is touched.
