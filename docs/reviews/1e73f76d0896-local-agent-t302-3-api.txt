## Adversarial probes against the real executable

- **P1, authority and parsing.** I sent the client token with GET/PUT/DELETE/POST to
  `/v1/settings`, `/v1/settings/`, `/v1//settings`, `/v1/./settings`, `/v1/Settings`,
  `/v1/probe/`, `%2f` and query variants. None returned 200: exact paths give 403 and
  variants give 400 or 404. Lowercase `bearer`, a double space, a 63-character prefix,
  a 65-character token and a missing header all give 401. Host values such as
  `localhost:port`, a missing port, a trailing dot, `127.0.0.2`, `[::ffff:127.0.0.1]`
  and a DNS name give 403. A duplicate `host` with different case gives 400. An
  absolute-form target, HTTP/1.0, Content-Length `+0`, `-0`, `0,0` and `0x0`, a tab
  in a value and `Connection: keep-alive`/`Upgrade` all give 400. Bare-LF framing
  times out with 408. OPTIONS preflight gives 404 and no CORS header is emitted.
  The settings endpoint refuses user info, `0.0.0.0`, v4-mapped IPv6, `127.1`,
  traversal, query, fragment and percent-encoding (400). It also refuses
  `approve_conversations` that is missing, `"true"`, `1` or a duplicate key, and a
  `charset` media-type suffix. Probe refuses a `key` field, nine candidates and zero
  candidates. Status stays `configured: false` throughout. The only deviation from
  the strict expectation was a trailing space after Host, which is trimmed. HTTP
  allows that whitespace, so it is not a finding.
- **P2, discovery versus permission (T-302.2 L2).** A successful probe returned the
  model list. Chat then still returned 428. The probe request carried no
  Authorization header. After configuring a key, a later probe to a second upstream
  still did not forward it, and activity never contained the key. Redirects from the
  configured endpoint fail with `chat.transport.redirect-refused`. When the client
  closed mid-stream, the upstream received a broken pipe within 0.45s, `busy`
  returned to false and activity recorded `api.client-disconnected`. **L2 is
  satisfied:** only an authenticated control-token PUT with `approve_conversations:
  true` mints `LocalChatApproval`, at `local_chat_api.rs:595`.
- **P3, prompt-injected model output.** Model text containing
  `\n{"type":"complete","finish":"stop"}\n  {"type":"settings"}` and `\r\n` arrives as
  one JSON-escaped `text` event, followed by exactly one genuine `complete`. Framing
  cannot be forged and model text has no route to settings.
- **P4, availability.** With one stalled chat and three slow-header sockets
  occupying every worker, `POST /v1/cancel` was admitted in 1.96s and the chat ended
  with `chat.transport.cancelled`, `partial: true`. Eight unauthenticated slow-header
  attackers delayed authenticated status by 2.0 to 3.0s, as the guide's "no
  availability guarantee" discloses. After 2000 connect-then-RST sockets the
  service stayed alive.
- **P5, process entrypoint and credentials.** `serve` refuses `0.0.0.0`, `[::]`,
  `192.0.2.1`, `localhost` and `[::ffff:127.0.0.1]` binds with the fixed message.
  An `[::1]:0` bind works, with an exact `[::1]:port` Host and 403 for other forms.
  `serve` refuses a symlinked token directory. `init-auth` refuses an existing
  directory and a symlink. Under umask 022 it still produces 0700 and 0600 files.
  Under umask 0277 it fails closed and leaves an empty 0500 directory, as the
  guide's partial-directory note discloses. A token with a trailing newline is
  refused. Neither command prints a token.

  Concurrent cancel latency stayed at 5 ms or less, because loopback buffers absorb

- **P7, activity accuracy.** See L2 below.

## Review against the request's checklist

- **Separate control and client authority.** `local_chat_api.rs:549` is an
  exact-path gate before routing. Settings and probe require the control token.
  Status, activity, models, chat and cancel accept either token. Tokens are distinct
  (`new` refuses equal values) and are compared with a fixed-length, non-short-circuit
  fold.
- **Explicit settings choice versus probes.** Probes build a fresh credential-free
  transport inside the transport library. Their results are never stored. Only PUT
  stores a configuration (P2).
- **Credential files and ownership.** The directory is opened with `O_NOFOLLOW |
  O_DIRECTORY`, and its owner and mode 0700 are checked through the held descriptor.
  Leaf files use `openat` with `O_NOFOLLOW`, then `fstat` checks for a regular file,
  euid owner, mode 0600, `nlink == 1` and length 64. Creation uses `O_EXCL`. These
  behaviours are tested and reproduced (P5).
- **Bounds.** Headers are read byte-wise up to 8 KiB, and the body is bounded at
  256 KiB before allocation. There is one two-second absolute deadline per request,
  a 250 ms absolute budget per write, four fixed workers and one upstream operation.
  Transport limits are 120s total and 30s idle (`TransportLimits::default`). Probes
  use 5s and 1s. Encoder caps are 256 messages and the request byte cap. Activity
  keeps 128 events. All match the guide's table.
- **Partial versus complete.** `complete` is emitted only when `transport.chat`
  returns `Ok`, which requires the finish reason, codec end and wire EOF. Every
  error path emits `partial: true`. Truncated, late-invalid and auth-error streams
  are tested. Write failure suppresses the terminal event, which the guide states.
- **Cancellation and settings races.** `begin` checks `stop` and `active` and
  snapshots the configuration under one lock. PUT and DELETE re-check `active` under
  the same lock, so an active operation's configuration cannot be replaced. Shutdown
  sets `stop` before taking the lock and cancelling `active`, so an operation either
  sees `stop` or is cancelled. This is tested in-process and reproduced over sockets.
- **Disconnect and shutdown.** Reproduced in P2. Library shutdown is tested. The
  binary has no signal handler, and the guide says it is stopped by the operating
  system. No child process is started.
- **Activity privacy and retention.** Activity holds metadata only: no key, token,
  prompt or answer (tested, and reproduced in P2). It is process-only and its gaps
  are visible through sequence numbers.
- **Error redaction.** Errors use fixed codes and messages only. Upstream reason and
  body are not echoed (tested). The server prints only its startup line or fixed
  failure text.
- **Honest labelling.** The guide and evidence say plainly that upstreams are
  synthetic, that no model was run, that no durable run exists and that the gate
  fails on the baseline. They also disclose same-account credential trust and the
  residual model-port trust. Every number I could reproduce matches.
- **Public-repository hygiene.** The diff adds no private host path, username,
  hostname, credential or sibling-project name. "OpenAI-style" appears only in an
  unchanged context line of the parent row, as descriptive protocol compatibility,
  not branding. The diff names no other agent product, and no dependency changed.
- **Delivery.** The row ends in a running, measured executable with contracts and no
  further splitting.

## Findings

No critical, high or medium findings.

**L1, low: cancellation is not bound to an operation.** At `local_chat_api.rs:621-628`,
`POST /v1/cancel` cancels whichever operation is active when it is admitted. A late
cancel aimed at a finished chat, perhaps delayed by up to two seconds behind
saturated workers (P4), can therefore cancel a different client's newly started chat
or models call. Fix: expose an operation identifier, for example the `started`
activity sequence in the first NDJSON event and in `/v1/status`. Accept
`{"operation":N}` on cancel and cancel only when it matches.

**L2, low: activity reports `chat started` / `incomplete` for refused requests that
never contacted upstream.** At `local_chat_api.rs:683-712`, `begin` runs before the
"configured" check and before role and `encode_chat` validation. P7 showed that an
unconfigured chat (428) and an invalid-role chat (400) each record `started` and then
`incomplete` events, the latter against the configured endpoint. The guide says
activity records "upstream operation start/result", so an auditor could wrongly infer
an upstream attempt. Fix: validate the configuration and messages before `begin`, or
record a distinct `refused` outcome.

**L3, low: intermediate allocations holding tokens are freed without erasure.** The
guide says "The owned token allocations and raw request buffers are erased on normal
drop". Three places create unerased copies:

- The request header buffer starts as `Zeroizing::new(Vec::new())` and grows by
  `push` (`local_chat_api.rs:272,279`). Each reallocation (8, 16, …, 8192 bytes) frees
  an earlier copy, which can include the `Authorization` line.
- `load` uses `read_to_string` into an empty `String` (`:131-134`).
- `initialize` builds the token by collecting `format!` output (`:82-87`).

`Zeroizing` erases only the final allocation. This is defense in depth under the
documented same-account trust, not a boundary bypass. Fix: preallocate with
`Vec::with_capacity(MAX_HEADER)` and `String::with_capacity(65)`, write the hex into a
fixed array, or narrow the guide's wording.

**L4, low: any non-`WouldBlock` accept error stops the entire service.** At
`local_chat_api.rs:222-225`, an error such as `ENFILE`, `ENOBUFS` or `ENOMEM` stops
every worker and makes `serve` return an error. So do the pending network errors that
Linux `accept(2)` documents should be retried. A local process exhausting system file
descriptors could therefore stop the API. It fails closed, but it does not recover.
I could not induce this: 2000 RST connects did not trigger it (P4). Fix: treat
transient accept errors as retryable after a short sleep, and stop only on listener
invalidation.
