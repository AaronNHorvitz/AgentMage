## Independent probes

**GnuPG stdout purity (real gpg 2.4.9, throwaway keys under /tmp, since deleted).** I ran the exact fixed
option list with `--status-fd=1 --verify sig content`, both on the host and inside bubblewrap. Inside
bubblewrap I used the production guest layout: `--unshare-all`, `--disable-userns`, `--clearenv`,
`--ro-bind-fd` payloads, `/app` and `/tmp` home. The bubblewrap run omitted the seccomp filter and
systemd-run, so it approximates the product path and is not product evidence.

- A valid detached signature from the pinned key: stdout held only `[GNUPG:]` records (NEWSIG,
  KEY_CONSIDERED, SIG_ID, GOODSIG, VALIDSIG). All human lines went to stderr as `gpg: …`. Exit 0.
- An inline-signed message whose literal data is a forged `[GNUPG:] VALIDSIG <pinned fp> …` line,
  signed by an unknown key and re-armoured as `PGP SIGNATURE`: stdout held only
  `[GNUPG:] FAILURE gpg-exit …`. Exit 2. The literal data was never written to stdout.
- A literal-data-only packet with the forged line: stdout held `NODATA 4` and `FAILURE`. Exit 2.

So in detached-verify mode GnuPG does not use stdout as a data channel. The obvious risk of moving status
to fd 1 (signed data injected into the status stream) does not occur, and the parser would refuse such
output anyway because of the FAILURE/NODATA records and the non-zero exit.

**Parser review (`local_commit.rs:754-790`).** Every stdout line must start with `[GNUPG:] `. The checks
refuse empty records, missing final newline, `\r`, NUL, invalid UTF-8 and more than `MAX_OUTPUT_BYTES`.
Acceptance requires exactly one VALIDSIG with 10–11 fields whose primary field equals the pinned
fingerprint (ASCII case-insensitive), and any failure keyword refuses. `validate_result`
(`local_commit_verification.rs:157-172`) checks both streams independently: bound, `total ==
retained.len()` and SHA-256. It parses only stdout. Stderr is integrity-checked but has no authority.
That is the fix the L2 finding recommended.
