## Security and correctness analysis

### Provenance before narrowing
`prepare` checks, in order:
- the original seal (`verify_runtime_endpoint_run_request`);
- the workspace identity;
- the exact visible-tool references;
- ledger snapshot equal to the request snapshot;
- `effective_guidance` (seal, conflicts, stale reads).

Only then does it compile guidance (`coding_endpoint_startup.rs:104-127`). The compiler also refuses
decisions whose scope belongs to another workspace (`coding_guidance.rs:236-241`); my probe confirmed
this. The tests cover corrupt, foreign-snapshot, stale and conflicting ledgers.

### Budget caps before action binding
- `apply_budget_cap` refuses widening and zero values.
- `request.limits` is replaced before `bind_endpoint_coding_policy`, so `build_runtime_policy_envelope`
  binds `maximum_tool_calls` to the reduced value (`:134`, `:145-152`).
- The test shows that `binds_run(..., 2)` holds and `binds_run(..., 4)` does not.

### Disabled tools, stop and validation
- Disabling the sole tool gives `NoTools`.
- A request with `max_tool_calls = 0` gives `NoTools`.
- `Stop` gives `StopRequested`.
- `RequireVerification` gives `ConstraintDenied`, because the file-only entry passes an empty
  template slice (`coding_guidance.rs:185-193`). No synthetic validation registry is built.
- The shared compiler body is unchanged apart from the slice access. The audit asserts this, and a
  new test compares the result to `compile_coding_guidance` with a test validation registry.

### Exclusions
- The excluded scopes reach both the kernel policy (`excluded_scopes` → `excluded_targets`) and
  the source check.
- `check_sources` runs before `CodingEndpointFiles::new` and before `runs.admit` (`:205`).
- It refuses the whole admission. Nothing is filtered out silently.
- Path canonicalization is strict, and the probes above found no bypass.
- The file boundary separately refuses excluded paths, symlinks and `..` at read time; I read its
  test (`coding_endpoint_files_tests.rs:431-445`).

### Confirmation
- Guidance `RequireUserConfirmation` is compiled but not consumed by the boundary.
- I checked the claim that every read already requires exact approval:
  - `EndpointFileGrants::evaluate_file` returns `Ask` (`coding_endpoint_files.rs:312`).
  - `Allow` is produced only inside approval resolution, after a non-Deny response, target
    revalidation and `derive_approved_coding_grant` (`:380-420`).
- So the claim holds for this catalog (see L3).

### Catalog and registry
- `admit` passes a fresh unrestricted `workspace_file_read_runtime_registry()` to
  `CodingEndpointFiles`, and the narrowed registry to the owner.
- This is safe: preparation refuses an empty narrowed catalog, and `EndpointFileGrants::new`
  requires `registry.list_tools() == [ReadText]` and `tools == request.visible_tools` (`:163-183`).

### Re-sealing
- After narrowing, the request is resealed; after binding it is resealed again.
- The owner re-verifies the seal, and `EndpointFileGrants::new` re-checks policy id and digest
  against the request.
- The narrowing digest is pushed into `task.constraints` before the seal. The test checks the exact
  final request equals the expected reseal.

### No effects at preparation or admission
- Preparation performs no I/O on the workspace; the test asserts the directory and sentinel file
  are unchanged.
- Admission issues no grant and dispatches nothing. It constructs the boundary (which revalidates the
  workspace and authority root), builds the endpoint context, and the coordinator then stores the
  run.

### Other checks
- Secrets and logging: error variants carry no content, nothing in the new module logs, and no
  credentials are handled.
- Supply chain: no dependency, Cargo.lock or licence changes.
- Evaluation integrity: no eval, hidden, held-out, scorer, threshold, ignore or scoreboard paths are
  touched; the allowed-path assertion confirms this.
- Public-repository hygiene: no private paths, hostnames, usernames, sibling-project names or

## Findings

No critical, high or medium findings.

- **L1 (low): re-preparing stacks a second digest line** —
  `shells/host/src/coding_endpoint_startup.rs:140-144`.
  - `prepare` accepts a request it already prepared. That request still has a valid seal, a matching
    workspace and the same tools, so `prepare` appends another
    `Trusted repository narrowing policy SHA-256:` line. My probe saw 2 lines.
  - Each preparation rebinds policy from its own ledger, so no authority is widened. However, the
    "complete narrowing identity" in the sealed constraints becomes ambiguous.
  - Fix: refuse any request whose constraints already contain that prefix, or require the unbound
    placeholder policy id.
- **L2 (low, test coverage): `admit` has no executed test** —
  `coding_endpoint_startup.rs:198-235`.
  - The order (source check, then native boundary, then owner) and the error mapping are verified
    only by reading the code. This is because `LinuxSandboxRunner` cannot be constructed in
    component tests, which the documentation acknowledges.
  - Fix: add a refusal-path admission test once a test-constructible admitted runner exists.
- **L3 (low, latent): confirmation constraints are not enforced by the boundary itself** —
  `coding_endpoint_startup.rs:140-142`, `coding_endpoint_files.rs:312`.
  - `guidance.requires_confirmation` is never consulted. Today this is safe only because every file
    read returns `Ask`.
  - If a later catalog or boundary ever allows reads without approval, the trusted confirmation
    constraint would be dropped silently.
  - Fix: at composition, assert that every tool requiring confirmation is served by a boundary that
    always asks, or pass the confirmation set to the boundary.

Notes, not findings:
- Exclusion matching is exact and case-sensitive (`Private/secret` is accepted when `private` is
  excluded). That is correct on Fedora's default case-sensitive btrfs/ext4. Casefolded directories
  (ext4 `+F`) would need inode-level checks, which the file boundary already does at read time.
- Earlier lows remain same-row backlog, as the request states.
