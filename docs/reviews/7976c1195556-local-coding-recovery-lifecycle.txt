## What I verified by reading

### Worker join (`shells/host/src/coding_live_runtime.rs:711-724`, `:948-952`)

- `start` now calls `shutdown_worker()` on a `session.start()` error. That method sends a shutdown
  cancellation only once a correlation ID exists, retries `Stop` until it is queued, drains the
  capacity-one `results` channel, waits for `is_finished`, joins the worker and then shuts down the
  event pump.
- I checked the other post-spawn exits:
  - `begin_job` failure in `start`;
  - `sync_events` and `RuntimeEvidenceDenied` in `continue_from_checkpoint`.

  Each occurs with `busy == false`: `busy` is set only by `dispatch`, and `continue_job` is the first
  dispatch on the continuation path. On those exits the unchanged `Drop` queues `Stop` and joins an
  idle worker, so none of them detaches.
- `continue_job` can fail after `dispatch`, either in its `refresh` or in the Cancelled branch's
  `signal_cancellation`. That exit now also joins.
- `RuntimeEventPublisher::publish` (`kernel/engine/src/runtime_event.rs`) uses `try_send` and drops
  full subscribers. A worker being joined therefore cannot block on an undrained event or on the
  slow-subscriber channel.
- No terminal outcome or acknowledged cancellation is created: the new test shows the ledger still
  `Running` and a duplicate start `RequestDenied`. Registered-session `Drop` semantics are unchanged,
  which keeps the abrupt-restart fixture passing.
- The only fixture change: `GatedCoordinator::advance` now blocks on its gate when `events` is empty.
  Only the new test passes an empty `events`; the six other `gated_live_service` callers pass non-empty
  events. No existing test is weakened.

### Retained recovery (`platforms/linux/src/coding_repository_runtime.rs:55-69`, `platforms/local-api/src/coding_owned_api.rs:122-137`, `:186-231`)

- `recover_repository` takes from an in-memory `Option<LinuxCodingWorktreeLease>` and puts the same
  lease back on `Arc::try_unwrap` failure (`owner-held`). `Recover` has a single
  `approve_recovery: bool` with `deny_unknown_fields`. No path, marker, receipt or serialized owner can
  populate `State::recovering`; only `restore_lease` sets it, with a lease the process already holds.
- Poison: `try_into_repository` still clears `created`, `pending`, `command`, `validation`, `edit` and
  `apply`. The poison test now goes through the slot and still passes.
- `recover` checks in this order:
  1. consent (403);
  2. an existing manual owner (409);
  3. a pending slot, which it retries under the state lock and the held controlled operation;
  4. otherwise the prior runtime path, whose `restore_lease` retains the lease on a busy result.

  Success returns `apply_approved:false, fresh_diff_required:true`. The platform test shows the old
  apply decision refused, the original checkout unchanged until a fresh preview, and then a separate
  decision applying the retained worker write.
- The prior review's lease holders (factory `owned_worktree`, boundary clones) are all owned values.
  None is `Box::leak`ed, so a pending slot can complete once the composition drops.
- The positive pending-recovery branch in the API is not executed by any test, as the evidence says.
  I checked its ordering and retention by reading.

### L2 (low, backlog): the API's pending-recovery wiring is not executed

- **Where.** `platforms/local-api/src/coding_owned_api.rs:122-137` and `:195-198`, and the status field
  at `lib.rs:1554`.
- **Evidence.** The slot semantics are tested at the platform layer (mutant C is caught). Nothing in
  the API runs these steps: `restore_lease` storing a busy lease, the early guard and `begin_scoped`
  refusing while pending, `runtime_recovery_pending:true`, and a consented retry. A regression in that
  wiring would go undetected. The evidence discloses this, hence low.
- **Fix.** A `#[cfg(test)]` unit test that places a lease from the existing platform synthetic-creation
  fixture into `State::recovering`. No production HTTP fixture is needed. Assert, in order:
  1. 403 without consent;
  2. 409 `owner-held` while a clone lives, with status `pending:true` and manual routes 409;
  3. 200 after the clone is dropped;
  4. 428 on a second retry.
