## Findings

No critical, high or medium findings.

- **L1 (low, test strength). kernel/engine/src/runtime_loop_tests.rs:4046-4058.**
  `runtime_model_binding_preserves_the_complete_native_tuple_and_accounting` checks `ExactNative` accounting
  by serialising a hand-built `ModelTokenUsage`. It does not use the usage the fixture run actually produced.
  The assertion therefore proves only the serde wrapper, not that native accounting is "preserved" through a
  run, as the name and evidence suggest. The admission checks are still sound.
  - Fix: assert against the `ModelTokenUsage` taken from the completed run's model result or terminal event,
    or rename the test to match what it checks.
- **L2 (low, API wording). platforms/local-api/src/lib.rs:1103-1112 and docs/guides/coding-proposals.md:142-144.**
  Every refused terminal event carries the literal `"partial":true`. That includes length finishes, rejected
  strict edits and display-limit refusals whose stream completed with `Ok`. Those events now also carry
  `token_accounting`. The guide says "Partial ... responses carry no `token_accounting`". The guide means an
  incomplete transport response, but a client reading the JSON `partial` flag will see accounting on
  `partial:true` events. This is an inspection-only ambiguity and grants no authority.
  - Fix: in the guide, state that `response_complete`, not `partial`, controls whether `token_accounting` is
    present.
- **Observation, not a finding.** `EndpointTokenAccounting::from_completed_provider_report` is public, and
  its "completed response only" precondition is enforced only by its doc comment. The brief and the evidence
  both say this wrapper is inspection-only and verifies nothing. The one current caller passes only `Ok`
  completions. Keep that in mind when an endpoint port is admitted later.

The predecessor's low findings L1 (API raw-byte digest assertion strength) and L2 (preparing transport before
repair receipt consumption) remain backlog. This batch does not change them.
