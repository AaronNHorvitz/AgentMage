## Review of the claims

- **One deadline.** `workflow::run` builds a single `driver::Signals` and sets
  `Client.deadline = controls.deadline()`. Every guided request goes through `Client::call`, which
  uses `min(now+180 s, overall)` and checks the latch before token load, before connect, before
  the header write and before the body write. `read_until` polls the latch every 100 ms read
  timeout. `idle()` goes through `json()` and is therefore covered. Retries reuse the same `Client`,
  so a new attempt cannot renew the deadline. Confirmed.
- **All four approval kinds.** `share-failure` (coding_cli.rs:469), `read` (:557), `edit` (:676) and
  `test` (:1082) now use `Client::confirm`, which delegates to the original driver's nonblocking
  `/dev/tty` confirm when controls are present. Allow is followed by a re-check of the latch;
  `Deny` and `Stopped` both return `Err` and never send `approve:false`. Callers that still use the
  global `confirm` (original-apply, workspace-apply, runtime and endpoint commands) are not
  reachable from `run_steps`. `coding_cli_record::export` builds its own client with `controls:
  None` and is not reachable from the guided path. Confirmed.
- **No new owner or permission path.** The diff only widens visibility of the existing driver's
  `Signals` and `Confirmation` and adds a `deadline()` accessor. No server, kernel, grant, sandbox
  or preview check changed. Stop never becomes an approval, denial, cancellation, release or
  retry. The new tests assert an exact request prefix (`routes[..stop_at]` or `[..=index]`), and my
  probe saw no extra dispatch. Confirmed.
- **Honest limits.** The guide, decision and evidence state that a stop is not cancellation, that
  connect and write calls can take up to 2 s, and that output backpressure and filesystem stalls
  are not bounded. This matches the code: `show()` to stdout and `verify_root` do not poll the
  latch. All model, write and test observations are labelled synthetic, and no native, model,
  GPU or score claim is made.
- **Regression.** `regression-before.log` shows the new default-command test failing original
  production at status -15 against an expected 1, on the existing `code-worktree` command. The
  restored hashes in `regression-fixed-hashes.json` equal the committed sources.
- **Evaluation integrity and scope.** No evaluation, hidden or held-out task, scorer, threshold,
  dependency, Cargo.lock, SBOM, scoreboard, release or push change. No row added or closed, no
  review verdict edited, history linear (predecessor is the parent). No other agent products
  named and no trademark used as branding.
- **Confinement.** This increment does not touch the server-side workspace, worktree, sandbox or
  network boundaries (no server or kernel file in the diff). Those were reproduced in earlier
  reviews and are unchanged here. The client-side consent boundary is the one this diff touches,
  and it was exercised directly: an interrupted or expired prompt never converts into a vote or a
  dispatch.

## Findings

No critical, high or medium findings.

- **L1 (low, test coverage)** — `platforms/local-api/tests/support/coding_workflow.rs:928`. The
  six invalid-budget cases pass only `["code-worktree-bounded", seconds]`. With an empty tail,
  `run_steps` refuses at its argument destructuring even if the 1..3600 range check or parse were
  deleted. So status 1, zero answers and zero requests would still hold, and the test does not
  discriminate the claim "invalid budgets refuse before requests". My probe shows the production
  check works.
  Fix: pass the complete argument list with a valid definition for each invalid budget, and
  assert both no request and the absence of the "Guided workflow stopped" message, which is
  printed only after `run` passes validation.
- **L2 (low, robustness)** — `platforms/local-api/src/coding_cli_driver.rs:57`. While the guided
  command is running, SIGINT, SIGTERM and SIGHUP only set a flag and never escalate. If the client
  is blocked where the latch is not polled (stdout backpressure in `show`, or `verify_root` on a
  stalled filesystem), repeated Ctrl-C or SIGTERM no longer terminates it, unlike the predecessor
  where the default action applied. Only SIGKILL remains. This is disclosed as "not an OS
  watchdog".
  Fix (backlog): consider second-signal escalation, for example by also registering
  `signal_hook::flag::register_conditional_shutdown` on the same signals.
- **L3 (low, wording)** — `coding_cli_driver.rs:141` and `coding_cli_workflow.rs:173`. On Linux,
  `Instant` is `CLOCK_MONOTONIC`, which excludes system suspend, but the transcript field and
  documents call this a "wall" or "elapsed" budget. After a suspend, more real time can pass than
  the budget shows.
  Fix: describe the budget as monotonic running time excluding suspend, or use a boot-time clock.
- **L4 (low, evidence traceability)** — `docs/evidence/t303-workflow-budget-2026-11-08.md:58`.
  The private `focused-inputs.json` records different hashes for `coding_cli.rs`,
  `coding_cli_workflow.rs` and both test files than the committed sources (for example
  `8e9b787d…` against `15d99150…`). The "focused 13 PASS" result and "passed the focused
  fixed-code run" therefore cannot be traced to the committed sources. In substance this is
  covered: the final gate, both the builder's and mine, runs all 13 workflow methods on the frozen
  committed sources.
  Fix: record focused inputs at the time of the run, or cite the final-gate identities instead.
