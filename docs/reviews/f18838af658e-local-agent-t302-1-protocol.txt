## Review of claimed properties

- Effect-free: confirmed. The module uses only `std::net` value types, `serde` and
  `serde_json`. It has no I/O, sockets, files, environment, processes or
  credentials. It is reachable only as a library module (`pub mod local_chat`).
  The row claims no other surface, so that is honest.
- Endpoint parsing: loopback-only, explicit nonzero port, IPv6 brackets enforced,
  no userinfo/query/fragment/percent/backslash/non-ASCII, no `.`/`..` or empty
  segments, `localhost` pinned to 127.0.0.1. Confirmed by the tests and my probes.
- Request bounds: model ≤256 bytes, no control characters; 1–256 nonempty
  messages; last message must be user; 1–32768 tokens; raw-sum and post-escape
  256 KiB ceilings; fixed `stream`, `n: 1`; no tools or hidden prompt. Confirmed.
- Incremental UTF-8 and split framing: lines are split on `0x0A` (never part of
  a multibyte sequence) and validated per line. Every two-way split and
  byte-at-a-time delivery is tested. Confirmed.
- Completion semantics: `Finished` requires a stop/length finish reason, nonzero
  text and `[DONE]`. Any later byte is refused, and `end()` requires completion
  with empty buffers. Every EOF prefix is tested. This is confirmed **except M1**:
  a spec-valid BOM makes a truncated answer complete.
- Poison state: every `feed` error sets `failed`, and `end()` sets it on an
  incomplete stream. Later `feed`/`end` return `Failed`. Confirmed.
- Aggregate limits: per-event (including comments and metadata), whole-body
  (checked before processing) and decoded-text limits are tested at the exact
  boundary. Confirmed.
- Tool rejection: non-null `tool_calls`/`function_call`, non-assistant roles and
  other finish reasons are refused. The codec cannot surface a proposal at all.
  The duplicate-key case is in L1.
- Errors: fixed static codes with no upstream content. Confirmed.
- Transport obligations in the guide are explicit and correctly exclude
  time, framing, redirects, proxies, credentials and destination authorization.

## Findings

### M1 (medium): a leading byte-order mark silently drops the first event and still reports success

Location: `platforms/linux-inference/src/local_chat.rs:297-327` (no BOM handling
before line parsing; the unknown-field arm at line 327 swallows the line).

The event-stream format says one leading U+FEFF is ignored, so a body that
starts with `EF BB BF` is valid. Here the BOM stays in the first line, so the
field name becomes `"\u{feff}data"`. That falls into `_ => {}` and the whole
first event's data is discarded. If that event carried text, later events still
supply text, a finish reason and `[DONE]`. Result: `Finished(Stop)` and
`end() == Ok(())` for an answer that is missing its beginning. My probe got
`Ok([Text("second"), Finished(Stop)])` and lost `"FIRST "`. This directly
contradicts the guide's claim that "No closed connection or partial output can
imply success". It is a silent correctness failure on valid upstream input in
exactly the area this row is accepted for. The transport obligations do not
assign BOM handling elsewhere, and the decoder claims to consume
"HTTP-decoded response body bytes".

Fix: track whether the stream start has been consumed. Strip exactly one leading
`EF BB BF`, even when it is split across fragments of 1–3 bytes. Alternatively,
refuse a leading BOM with `Protocol`; either is acceptable if documented. Add a
test that puts a text-bearing first event after a BOM at every split point and
asserts the full text or a failure, never a shortened `Finished`. Also consider
making the decoder fail closed on any unknown field name that begins with a
non-ASCII-letter byte, so similar framing corruption cannot silently drop data.

### L1 (low): duplicate JSON keys select the last value, so model binding and tool refusal can be sidestepped textually

Location: `local_chat.rs:344` (`serde_json::from_str::<Value>`) and lines 345-347
and 374-377.

`{"model":"other","model":"m",…}` passes the exact-model check, and
`"tool_calls":[{…}],"tool_calls":null` passes tool refusal. Nothing is executed
or surfaced, because the codec only emits `Text`/`Finished`, so there is no
confinement impact today. The guide's "Tool or function proposals … are refused"
is weaker than stated, though, and a future consumer that parses the same bytes
with first-wins semantics would disagree. Fix: refuse events with duplicate keys
at the top level, in `choices[0]` and in `delta` (for example, deserialize into a
map visitor that errors on repeats), or state the last-wins semantics in the guide.
Backlog for T-309.

### L2 (low): `Finished` is not final, and the guide does not say so

Location: `local_chat.rs:298-300`; guide lines 38-42.

Any byte after `[DONE]`, even a blank line that the format treats as a no-op,
turns the stream into `Protocol`. In the same fragment, the already-built
`Finished` is discarded. In a later fragment, the caller has already seen
`Finished` and then gets an error, with `end()` returning `Failed`. Fail-closed is
fine, but the guide should state that only `end() == Ok(())` confirms completion,
and the T-302.2 transport must not mark the answer complete on `Finished` alone.
Optionally, tolerate trailing blank lines and comments after `[DONE]`. Backlog.

### L3 (low): the consumer obligation covers HTML only, not terminal control or bidirectional text

Location: guide lines 44-46; `ChatEvent::Text` at `local_chat.rs:221-224`.

Model text may contain ESC/OSC sequences (for example, clipboard-setting OSC 52),
BEL, NUL and bidirectional overrides; my probe passed them through unchanged.
That is acceptable for a codec, but the obligation should also require control-
and bidirectional-character neutralization for any terminal, log or UI consumer
(T-302.3, T-307). Backlog.

### L4 (low): a pasted full chat URL is accepted as an API base

Location: `local_chat.rs:74-107`.

`http://127.0.0.1:80/v1/chat/completions` yields the chat path
`/v1/chat/completions/chat/completions`. There is no security impact; first-run
testing in T-302.2 will surface it as an HTTP error. Consider refusing a base path
that ends in `chat/completions` or `models` with a clear hint. Backlog.

### L5 (low): `ChatEvent` derives `Debug`, which contradicts the stated no-logging intent for conversation content

Location: `local_chat.rs:220`.

`ChatMessage` deliberately lacks `Debug` "to avoid logs", but `ChatEvent::Text`
(private model output) derives it, so `{:?}` can leak it into logs. Either drop
`Debug` (tests can compare with `PartialEq` and a custom message), or document
that the output must be treated like the input. Backlog.

### Observation (pre-existing tooling, backlog for T-309)

In `scripts/local_agent_fast_gate.py:257-266`, the per-command `--timeout` covers
the time spent waiting in `/tools/build-slot`. Under slot contention, a gate can
report exit 124 for a check that never ran. That happened to `cargo fmt` in my
first run. It fails closed, but it blurs the cause; consider timing only after
the reservation is acquired. This is not attributed to T-302.1.
