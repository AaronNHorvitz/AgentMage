## Findings

### M1 (medium): dev-021 statement does not scope the retained-digest check to the correction case

Location: `scripts/coding_eval_collection.py:156-172` (dev-021 `statement`; the "Add" sentence is at :165).

The statement says: "Correction requires the existing six-tool repair sequence, 8 turns, a verified
artifact and the exact repaired add function … Add "retained-muse-read-arguments": some
tool_requested row must name scripted-invalid-read-paths and arguments_sha256 aa960a42… Denial
requires no completed tools, 1 turn and "terminal-rejection-code" … these checks all affect
passed."

"Add …" is its own sentence, and the denial scenario also issues the invalid read request.
Applying the check to both new cases is therefore a natural reading. The frozen method
`test_read_rejection_requires_exact_bytes_no_authority_and_terminal_denial` (hidden module at
`ad28b5ca`) contradicts that reading:

1. It sets `requested["kind"]["arguments_sha256"] = "0" * 64` during the correction phase.
2. It reuses the same mutated row in the denial fixture.
3. It then asserts `self.assertTrue(verify()["passed"])` for `read-arguments-denied`.

The reference scopes the check with `if case == "read-arguments-correction":`.

Reproduction: `stmt/dev-021/candidate1.py` applies the check to both cases. Graded output in
`stmt/dev-021/out1/tests.json` is `failures=1`, failing at the denial `assertTrue(... passed)`.
`candidate2.py` differs by one line (`if case == "read-arguments-correction":`) and passes
(`out2`).

A statement-faithful candidate fails, so a model result on this task would measure guessing. This
is the same class as T-311.1 M2 and T-311.3 M1, and contradicts the evidence's claim that
statements give exact check keys "where a historical assertion requires them".

Fix, before any model measurement: amend the statement to say "Only the correction case adds
"retained-muse-read-arguments" …; the denial case does not check the request digest". Keep the
hidden bytes, selection, source pins and counts unchanged. Re-pin the collection fingerprint
under a new version, re-run the controls, and retain this failed probe.

### M2 (medium): dev-029 statement omits the `job_state.controls` shape and the notice discriminator key

Location: `scripts/coding_eval_collection.py:382-397` (dev-029 `statement`; the controls clause is at :391).

The statement requires "job.phase completed and controls actions exactly ["suspend","resume"]".
It also refers to notices by name (`run_suspended`, `job_state`, …) without saying which key holds
the notice name.

The frozen method `test_the_suspend_resume_case_requires_one_suspension_and_one_continuation`
(hidden module at `3709eabe`) builds notices keyed by `"type"` and supplies
`"controls": [{"action": "suspend"}, {"action": "resume"}]`. The reference computes
`[control.get("action") for control in states[0].get("controls", [])]`.

No `scripts/*.py` at base `8a3a341e` defines the `job_state` notice or its `controls` shape. I
grepped the projection for `job_state`, `job_control_answer`, `run_suspended`, `run_continued` and
`"controls"`; none occurs in a related form. The parallel clause in the same statement uses dotted
notation for nesting ("decision.decision"), which supports reading "controls actions" as a mapping
`controls["actions"]`.

Reproduction: `stmt/dev-029/candidate1.py` reads `controls["actions"]` and fails with
`'job-completed': False` (`out1/tests.json` `failures=1`). The one-line change in `candidate2.py`
to a list of `{"action"}` objects passes (`out2`). The `"type"` key was guessed correctly from base
convention, but it is not stated.

Fix, before any model measurement: state that each observed notice is a dict whose `"type"` names
it. Also state that `job_state.controls` is a list of objects whose `"action"` values, in order,
are exactly `["suspend","resume"]`. Otherwise keep the same constraints as M1.
