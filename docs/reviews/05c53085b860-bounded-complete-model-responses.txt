## What holds

- **Trusted-only selection.** `response_mode` is a field of the control-only `Settings`. A client token gets 403.
  Invalid, null and duplicate values get 400 and leave settings unchanged. `/v1/chat` and `/v1/code/proposals`
  bodies that carry `response_mode` get 400, and no upstream socket is opened (tested). The default is `Stream`,
  GET reports null when unconfigured, and DELETE clears the mode.
- **Immutability.** The mode is a field of the credential-owning `LocalChatTransport`, set by a consuming builder
  before the transport is installed. Prepared requests (borrowed or `Arc`-shared) encode with, and execute against,
  the same instance, so a later settings change cannot mix framings. The binding hashes the actual `stream:false`
  body (tested against the bytes on the wire).
- **Wire bounds.** Complete mode reuses the same `request`/`headers`/`body`. It requires `application/json`, keeps
  the 4 MiB body and 5 MiB wire ceilings, refuses chunked plus Content-Length together, and requires actual EOF
  after framing. `wire.check()` enforces total, idle, owner stop and cancellation on every read, after EOF and after
  the callback. The text is emitted once, after decode, the 1 MiB check and the narrowed-limit check. Cancelling in
  the callback revokes the completed observation (tested).
- **Decoding.** Typed serde structs reject duplicate critical keys and trailing data. Non-null `tool_calls`,
  `function_call` or `refusal`, a wrong model, more than one choice, a nonzero index, a non-assistant role, null
  content and an unknown `finish_reason` are all refused. Requested usage is validated by the shared
  `parse_chat_usage`; missing usage stays absent; unrequested usage is ignored. `stream_options` is not sent in
  complete mode.
- **Proposals.** An answer over 64 KiB still cancels in the callback and yields `code.proposal.limit` with no
  completion. The strict checker is unchanged.
- **Scope.** No retry or fallback, no new tool, command or file action, no network grant, and no change to native
  launchers. Chat without a folder works. No second runtime, desktop interface or folder-requiring API shape is
  added.
- **Measurement honesty.** 05c53085 records zero model tasks. The receipts show the queue group stopped at the

## Findings

### M1 (medium, protocol parity / measurement integrity): complete mode accepts an empty answer that stream mode refuses

- Location: `platforms/linux-inference/src/local_chat.rs:352-374` (`decode_complete_chat` never checks for empty
  `content`) and `platforms/linux-inference/src/local_chat_transport.rs:667-672` (empty content returns `Ok`). In
  contrast, the stream codec refuses `[DONE]` when `text_bytes == 0` (`local_chat.rs:550-553`, `ChatError::Incomplete`).
- Reproduction: see the output above. A reply whose `message.content` is `""` (here with an ignored
  `reasoning_content`) and whose finish is `stop` or `length` becomes a completed `EndpointModelResult` with 0 bytes.
  The equivalent empty SSE stream returns `Err(Chat(Incomplete))`.
- Why it matters: Decision 0206 and the campaign policy state that the only changed variables are framing and the
  idle budget. This silently changes an acceptance rule, and it does so for exactly the population the change
  targets: A4B attempts that produced no visible answer, possibly because non-answer output used up the token
  budget. In the next development repeat, these attempts would move from "transport refusal, no completed exchange"
  to a completed exchange (`response_complete: true`, usage and attempt accounting kept). On the proposal route
  that means `code.proposal.incomplete` (finish length) or a strict-checker format error (finish stop), see
  lib.rs:1331-1385. Stream-versus-complete comparisons on the scoreboard would then conflate a validation change
  with a framing change. The decision, evidence and API guide list the refused complete-mode cases, but none
  mentions empty content.
- Fix: in `decode_complete_chat`, return `ChatError::Incomplete` when `content.is_empty()`, matching the stream
  rule. Add the empty-`stop` and empty-`length` cases to
  `complete_mode_refuses_bad_envelopes_tools_counts_and_framing_without_emitting_text`. Alternatively, if accepting
  empty answers is intended, state it in Decision 0206, the guide and the campaign policy as an additional changed
  variable and count such attempts separately. Fix this before the queued campaign runs, since source is otherwise
  frozen until then.

### L1 (low, parity): `"error": null` is accepted in complete mode, but any `error` key is refused in stream mode

- `local_chat.rs:338,346` (`error: Option<Value>` treats null as absent), versus `local_chat.rs:557`
  (`event.get("error").is_some()`). Reproduced: `complete error-null: Ok(Stop)`. This is harmless in itself, but it
  is a second, undocumented rule difference. Backlog, or fold it into the M1 fix with a presence check (for example
  `Option<Option<Value>>` with `#[serde(default)]`).

### L2 (low, preflight/dispatch mismatch): `/v1/chat` preflight encodes the stream body, but dispatch encodes the complete body

- `platforms/local-api/src/lib.rs:2090-2097` validates with `encode_chat`/`encode_chat_with_usage` (`stream:true`).
  The transport then encodes `stream:false`, which is one byte longer when usage is not requested. A message whose
  stream encoding is exactly 262,144 bytes passes preflight and returns HTTP 200, then fails in `prepare_chat` with a
  request error event instead of a 400. No connection, exchange or authority results. Proposal bodies are far below
  the ceiling, so `prepare_proposal_messages` (1072-1076) is not affected in practice. Its comment says preflight and
  dispatch share the complete construction, which is no longer strictly true. Backlog: preflight with
  `config.transport`'s mode, or expose a mode-aware encoder.

### L3 (low, private-data hygiene): reallocations of the complete-response buffer are not zeroized

- `local_chat_transport.rs:650-654`: `Zeroizing<Vec<u8>>` grows by `extend_from_slice`, so earlier freed
  allocations keep model output. The stream codec buffers are not zeroized at all, so this is not a regression.
  Backlog: reserve `min(n, MAX_STREAM_BYTES)` for `Framing::Length(n)`, or use a fixed-capacity writer like the
  request side's `PrivateRequestWriter`.

No high or critical finding. Confinement is not affected: the change adds no tool, file, command or network path,
and model output stays untrusted text that cannot grant permissions.
