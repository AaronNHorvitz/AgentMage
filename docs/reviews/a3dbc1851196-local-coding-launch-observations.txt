### L1 (low, claim precision): the sealed request stays readable after release

- Where: docs/decisions/0199-explicit-endpoint-launch-observation-sharing.md:34 ("Released runs remain
  unavailable"), docs/evidence/t303-launch-observations-2026-11-10.md:25 ("Released records remain
  unavailable") and :64 ("release makes the record unavailable").
- What happens: `GET /v1/code/endpoint/request` (coding_endpoint_api.rs:488) returns the captured
  `request` with no check for release. After an exact release, a delegated `client.token` holder can
  still read the complete sealed task through HTTP or MCP `endpoint_request`, for as long as the service
  runs. Only event pages become unavailable.
- Tests: the existing and new tests check only `endpoint_events` after release
  (tests/support/coding_endpoint_mcp.rs:268, :379).
- Why it is low: the same data was already shared before release. The coding-mcp guide wording,
  "Released event records are unavailable", is accurate.
- Fix: limit the decision and evidence wording to event pages. Alternatively, make the request route
  refuse after release and add an `endpoint_request` assertion after release.
