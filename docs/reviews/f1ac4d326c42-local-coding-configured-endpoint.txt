## Assessment

### M1 repair (engine), RESOLVED

`coordinator_endpoint.rs:550-610` checks a model tool response in this order:

1. The response is parsed with closed `deny_unknown_fields` structs that carry only `tool_id`,
   `tool_version` and a plain `serde_json::Value`.
2. The whole text then goes through the original `ClosedJson` duplicate-key check.
3. Next come the budget check, then `is_model_proposable`.
4. The schema comes from `definition.input_schema`. The coordinator encodes the bytes itself
   (`serde_json::to_vec`), hashes them and builds a complete `ToolCall`.
5. `registry.validate_arguments` runs before any `request_tool`. That call includes the envelope
   check, the size check (`MAX_ARGUMENT_BYTES`) and the tool validator.

Any JSON object carrying a `tool_call` key that fails the closed parse also gets
`finish_refused_proposal`. That path transitions to Failed, closes the turn and publishes the
terminal.

The remaining `InvalidBoundaryResult` exits are not model-reachable:

- `get_tool` failing after `is_model_proposable` succeeded.
- `to_vec` on a `Value`.
- The envelope check inside `request_tool`, which now always sees a coordinator-built envelope.

Re-encoding can only shorten or keep the length of escaped input, so size cannot grow past the
check. The strengthened existing test and the new eight-case regression assert the terminal, the
whole-envelope hash, the event chain and repeat-read idempotence. My probe extends that to 14 more
shapes. Native family decoding is untouched, and final.py checks the native validation code
mechanically.

### Configured transport composition (host), SOUND

`ConfiguredCodingEndpoint` (`shells/host/src/coding_endpoint.rs`):

- It borrows the credential-owning `LocalChatTransport` and the exact `LocalChatApproval`.
- Its selection comes from `transport.model_selection`, so no caller-supplied address is accepted.
- `prepare` makes three control checks: before context, after context and after freezing.
- It refuses a mismatched selection before calling the context port.
- It admits the original messages through `RuntimeEndpointContextPacket::from_messages` and freezes
  the same slice through `prepare_chat`, which calls `authorized` before encoding.
- The engine then requires the packet fingerprint to equal the transport's request context
  (`endpoint.rs:112`), so a context divergence cannot pass.
- `ConfiguredDispatch` holds only the single-use `PreparedEndpointChat`. It passes the coordinator
  control into `execute_recorded_controlled`, which checks it before connecting, between socket
  waits and fragments, and after EOF.
- There is no retry, no prompt text, no new dependency and no native identity.
- Transport errors map to content-free port failures.

The six host tests use a real loopback socket. They assert:

- The request path and credential header.
- No tool before approval, and an identical repeated pending challenge.
- The actual read result reaching the second context.
- Grounded NoOp completion with whole-envelope provenance.
- No private text or key in the event metadata.
- Idempotent terminal reads.
- No connection for invalid context, wrong approval, selection or address mismatch, any owner stop,
  a post-context stop or a smaller-than-one-envelope budget. The shared nonblocking listener is
  checked at the end, so even a connect-and-close would be caught.
- A bounded stalled socket with exactly one call and no reconnect.
- That truncated, token-limited and ungrounded responses all fail. ModelCompleted counts are
  asserted per case.

The 2 MiB fixture budget is test input, not a product change. Product defaults for comparable runs
are 1–4 MiB, and the guide states the one-envelope headroom requirement.

### L3 (low, backlog, new): the "no permission evaluation" claim lacks a direct assertion

**Where.** `kernel/engine/src/runtime_loop_endpoint_coordinator_tests.rs:762-784`.

**Problem.** The new regression asserts zero executions and one model call. It never asserts that
no `PermissionRequested` or `PermissionDecided` event occurs, yet the guide claims "no permission
evaluation". The code satisfies the claim by construction, because the refusal returns before
`request_tool`, and my probe confirms it.

**Fix.** In each case, add `assert!(!c.events().iter().any(|e| matches!(e.kind,
RuntimeEventKind::PermissionRequested { .. } | RuntimeEventKind::PermissionDecided { .. })))`.

### Observation, not a finding

Tool attempts that are not valid JSON end as `runtime.verification.failed` rather than
`runtime.proposal.arguments-invalid`. Examples are a Markdown-fenced call, trailing prose, a lone
surrogate and an out-of-range number. These outcomes are terminal and inert, so this is only
diagnostic quality, worth considering when real-model coding runs are measured.
