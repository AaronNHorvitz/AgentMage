## Confinement and escape attempts

- **Path traversal and odd names.** Names come only from held directory listings and pass `WorkspacePath`. The new
  fixtures show that invalid UTF-8 and `:` names refuse the whole capture. An option-like name (`--options data`) goes to
  bwrap as a single literal destination argument; I confirmed this in the nested run.
- **Symlinks, hard links, FIFOs, sockets, setuid/setgid/sticky bits.** All of them refuse the whole capture without a
  prefix (new fixture cases 0, 1, 3, 7 and 8, plus the root-mode check). Pointer targets are never followed.
- **Mutable source.** In sealed mode no root descriptor is opened (`command_runner.rs:259`), and the mount arguments never
  contain `--ro-bind-fd … /work` (asserted by the fixture; confirmed by reading `command_runner.rs:363-372`).
- **Environment and network.** `env_clear`, `--clearenv`, `RestrictAddressFamilies`, `--unshare-all` and seccomp are unchanged.
- **Prompt-injected or model authority.** `with_sealed_worktree` is `pub(crate)` and called only at
  `coding_repository_validation.rs:162` and `coding_repository_endpoint_command.rs:670-689`. Selection is keyed to the
  user-approved pending validation, so the model cannot pick the mode or the projection. Sealed mode is strictly more
  restrictive than the live mount.
- **Approval binding.** `workspace_input` is set before `preview_sha256` is computed (`coding_repository_validation.rs:229-245`),
  so the exact consent digest binds the mode and bounds.
- **Factoring.** With `sealed=None` and `cancellation=None`, `available()` reduces to the original `Instant::now() < deadline`.
  The rest of the scan is identical, so the 699e99 binding, limits and full-tree checks are not weakened. Two of the
  refusals are not separately tested at the exact boundary: 255 directories plus the root succeeding, and depth exactly 16
  succeeding. The code is straightforward there, so this is not a finding.

No confinement escape was found. The defect below fails closed.

## Findings

### H1 — High (correctness; claimed feature unreachable): the original supervisor refuses every sealed launch with two or more files

- Where: `platforms/linux/src/command_runner.rs:389-397` passes
  `projections = SealedWorktree::into_descriptors()`, one sealed memfd per regular file, up to 128, to
  `run_owned` with `owner: LaunchOwner::Command(..)`. The unchanged supervisor admission at
  `platforms/linux/src/sandbox_supervision.rs:60` is `Self::Command(_) => ("agentmage-command-", projections <= 1)`.
  `run_owned` checks it first, before any spawn (`sandbox_supervision.rs:883`), and returns `InvalidManifest`.
  `supervision_failure` maps that to `CommandExecutionFailure::ExecutionFailed` (`command_runner.rs:464-473`).
  `sandbox_supervision.rs` is not in this diff.
- Failure scenario: any created worktree with the `.git` pointer file plus at least one other regular file, which covers
  every realistic project with tests. The user approves `test <preview-sha256>` through the direct route or the retained
  endpoint route. Capture succeeds and the unit identity is reported. Then the supervisor refuses on cardinality (≥2 > 1),
  so no test process ever launches. By Decision 0175 ("A failed admitted attempt stays spent"), each attempt is consumed, and
  three approvals exhaust the validation budget without running a test. Native project validation, which previously
  launched with a single live read-only root descriptor, is now unreachable for every tree except those with 0 or 1 regular
  files.
- Why it escaped: the four new methods stop at real memfds and inert mount arguments. The only cardinality test,
  `closed_owners_reject_cross_variant_names_and_projection_cardinalities`, is ignored, and it actually encodes the rejection:
  `1 => count <= 1` at `sandbox_supervision.rs:1325` asserts that `Command` refuses 2, 3 and 8. No sealed launch ran, real or
  ignored.
- Honest-claims impact: three documents make the same false statement, as does the request text ("Only indexed sealed
  descriptors go to the original supervisor … Retain descriptors with the original cleanup owner"):
  - `docs/evidence/t303-sealed-validation-2026-11-09.md`: "The original supervisor retains the sealed descriptors through
    cleanup and passes them in a fixed indexed order".
  - `docs/guides/coding-validation.md`: "The original supervisor retains these descriptors until cleanup".
  - `docs/decisions/0175-sealed-worktree-validation-inputs.md`: "Pass only sealed source descriptors to the original
    supervisor and native launcher".

  For any tree with two or more files this is false.
- Concrete fix:
  1. Give the closed owner an explicit sealed-command cardinality. For example, add a `LaunchOwner::SealedCommand(manifest,
     expected)` variant, or carry the sealed file count in `Launch`. Accept exactly `expected` descriptors with
     `1..=MAX_SEALED_FILES` (and 0 for an empty tree if it is supported), and keep `Command` at `<= 1` for ordinary commands.
  2. Update the cardinality test.
  3. Add a non-ignored admission test showing that the descriptor count of a ≥2-file sealed capture is accepted and 129 is
     refused.
  4. Add a launch test of the sealed mode, ignored only on unsupported hosts like the existing launch tests. It should run a
     ≥2-file worktree end to end and assert the bytes, the read-only `/work` and `assert_exact_guest_descriptor_table`.
  5. Correct the three documents until that evidence exists.

### L1 — Low: approval bounds are duplicated literals, not the enforced constants

- `coding_repository_validation.rs:229-233` hard-codes 128/256/4096/16/16 MiB/64 MiB/2000 ms. The enforced values live in
  `command_runner_worktree.rs:26-31` and `:54`, and no test asserts the displayed `workspace_input`. If the two drift, the
  user approves bounds that are not the ones enforced.
- Fix: export the constants (or a `SealedWorktree::bounds()` JSON) and build the preview from them. Assert the preview
  fields in a command test.

### L2 — Low: no test pins which paths select sealed mode

- The selection at `coding_repository_validation.rs:162` and `coding_repository_endpoint_command.rs:670-689` is untested. A
  regression back to the live mount, or to sealed mode for ordinary commands, would pass the gate.
- Fix: expose a test-only accessor on the executor flag, or test through the generic seam, and assert sealed mode for
  validation and live mode for ordinary commands. This can be done together with the H1 fix.

Earlier low findings, including 699e99 L1 and L3, remain same-row backlog. The 699e99 L2 qualification in the guide is
accurate.
