## Review by concern

### Authorization and permission

- `endpoint-record` (`coding_cli_endpoint.rs:229-232`) reuses `checked_selection(..., control=true)`. That is the
  `GET /v1/code/endpoint/request` route, with run-id and digest pinning.
- It then calls `event_page(..., control=true)` repeatedly, using only `POST /v1/code/endpoint/events`.
- The recording-peer test asserts that the routes, the bodies and the `after` indexes are exactly these. The refusal
  cases also assert that only events routes follow the selection: no retry, cancel or effect route.
- No advance, approve, deny, cancel or release path is reachable from `export`. `confirm` is never called.

### Untrusted input (server pages, stdin records)

**Export:**

- Every page goes through the existing `event_page` checks:
  - at most one event per page;
  - `next`/`total` consistency;
  - per-event hash verification;
  - scope;
  - `sequence == after`;
  - `retention == "process-only"`.
- Export then adds:
  - exactly one event per page;
  - a stable `total`;
  - `total` no greater than 4096 and no greater than the run's `max_events`;
  - a compact aggregate size below 4 MiB;
  - full-chain `verify`;
  - a check that the deadline has not passed;
  - an escaped-output size of at most 4 MiB, checked before the single `writeln`.
- A refusal emits nothing on stdout. The docs also note that shell redirection may already have created an empty
  file.

**Replay:**

- Replay reads at most 4 MiB + 1 bytes and refuses anything larger.
- `decode_exact` refuses duplicate members, positional structs and trailing data. `deny_unknown_fields` covers unknown
  members.
- `verify` (`coding_cli_record.rs:27-60`) checks:
  - the request seal (`verify_runtime_endpoint_run_request`);
  - version 1, `EphemeralReadOnly` and no event cursor;
  - the event-count bounds;
  - that the first event is `RunStarted` naming this request digest;
  - per-event run/session/task/policy equality with the request;
  - the original `RuntimeEventSequence::push` for every event (hash, sequence, previous digest, duplicate id,
    causation, binding including correlation, timestamps and transitions);
  - a terminal last event with `is_terminal()`.
- I confirmed that `push` rejects any event after a terminal one, so trailing post-terminal events cannot be appended.

**Terminal safety:**

- All output passes through `safe()`. serde_json escapes C0 controls, and `safe` additionally escapes DEL and all
  non-ASCII as `\uXXXX`.
- So a hostile record cannot place raw terminal escapes or bidi overrides on the terminal. The CLI test asserts ASCII
  stdout for a U+202E/emoji objective.

### Confinement and filesystem

- Export writes nothing but stdout, and replay reads nothing but stdin.
- Replay dispatches before `Client::new`, `token()` or any address parsing (`coding_cli.rs:657-659`). The integration
  test runs it with `env_clear()` after the service has stopped and the auth directory has been deleted.
- No path argument is accepted by either command, so there is no traversal or symlink surface.
- No network is used by replay. Export connects only to the validated loopback address.

### Deadline change

- `Client` now carries an optional shared deadline.
- `connect_timeout` and the write timeout are clamped to the remaining time, and `receive_before` enforces the same
  instant.
- For existing callers the per-request deadline is `now + 180 s` taken at send time instead of receive time. That is
  slightly stricter and harmless.
- The test-only `receive` wrapper keeps the existing unit tests unchanged.
- An expired deadline yields `checked_duration_since` → `None` → refusal, and a zero remainder fails
  `connect_timeout`. Both fail closed.

### Secrets and private content

- The record contains the sealed request and digest-only event envelopes. The event kinds carry `*_sha256` digests
  and content-free codes, not model text or tool bodies.
- The request includes the task/work-packet text and the endpoint URL, as the guide states.
- `LocalChatEndpoint::parse` accepts only `http://<loopback-ip|localhost>:port/path`, so URL userinfo (credentials)
  cannot appear.
- No token is serialized. The guide tells callers to treat the record as private and shows `umask 077`.

- **L1 (low, test coverage)**
  - **Location:** `platforms/local-api/tests/support/coding_endpoint_cli.rs:451-452`.
  - **Problem:** the fixture's `limits.max_events` is 2048 (`fixtures/runtime-producer/v5/run-request.json`). Both
    the `total = 4097` case and the `max_events + 1` case are therefore refused by the per-run ceiling. The
    independent `MAX_RECORD_EVENTS` (4096) checks are not discriminated by any test:
    - `coding_cli_record.rs:33` (replay);
    - `coding_cli_record.rs:84` (export).
    Deleting them would leave every test green, because the run ceiling, which the contract allows up to 1 000 000,
    is never set above 4096 in a test.
  - **Fix:** in one case, raise the fixture's `max_events` above 4096 (for example 8192) and re-seal it. Then assert
    that `total = 4097` refuses. Optionally add a replay case with a request whose `max_events` exceeds 4096 and more
    than 4096 events; the 4 MiB cap may also refuse that, so assert only refusal.
