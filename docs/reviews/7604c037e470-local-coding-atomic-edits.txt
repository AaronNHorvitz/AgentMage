## Review

**Correctness of the fix.**
- The first loop computes each final file size from the original length and the sorted, already
  overlap-checked spans. The fold `size - (end - start) + new.len()` cannot underflow, because spans are
  disjoint within the file.
- It rejects any file above `MAX_FILE` and updates the aggregate as `total - len + size`. That cannot
  underflow: `total` starts as the sum over all sources, and paths are unique (`validate_sources`).
- Only after every group has been planned does the code compare the aggregate, including unchanged files,
  against `MAX_SOURCE`. Candidate strings are allocated after that. So peak allocation stays bounded by the
  same 128 KiB final aggregate (plus the ≤64 KiB answer).
- The net-no-op check, strict JSON, unique visible preimage, excerpt containment, overlap and stale checks are
  untouched or run before planning.
- `path: source.path.clone()` is the same string the old code used, because the group key equals the source
  path. Output order is still lexical (BTreeMap).
- The result is more permissive only for the ordering defect. Every final invariant (≤128 KiB per file and in
  aggregate) is unchanged, and so is the error type (`Edit`).

**Tests.**
- The snapshot test is sound. Removing `trimβ`→`β` frees 4 bytes; ` é` adds 3 (L−1) and ` é!` adds 4
  (exactly L). It runs over both lexical growth orders, both source orders and both edit orders, and checks
  full content, both digests and that the inputs are unchanged.
- The negative case makes 3 files, including an untouched one, exactly L+1. That would also catch an
  implementation that counted only edited files.
- Invalid final edits cover a missing path and an overlap (a second `alpha` edit on `z.txt`).
- The HTTP method splits the answer across two SSE chunks through the configured transport. It checks the
