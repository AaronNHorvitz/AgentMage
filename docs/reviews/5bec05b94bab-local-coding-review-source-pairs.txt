## Analysis

**Base bytes are bound to objects.** `collect_with` (`platforms/linux/src/repository_base.rs:111-133`)
keeps exactly the buffer it has already checked against the tree entry's Git object id (sha1/sha256)
and the 128 KiB `MAX_BLOB_BYTES` limit. The SHA-256 is computed over that same buffer. The bounds on
path count, path syntax, duplicates, ancestor kind and replace-objects are unchanged.

**Base bytes are hidden from Debug.** The derived `Debug` is replaced by a manual one
(`repository_base.rs:34-41`) that shows only `sha256` and `mode` and ends with
`finish_non_exhaustive`. `GitObservation`, `LinuxCodingReviewSource` and
`LinuxCodingCandidateReviewEvidence` derive no `Debug` or `Serialize`. `LinuxCodingReviewSource`
has private fields and no `Clone`, `Default`, `From` or public constructor. It is built only in
`capture_candidate_review_sources`.

**Pair construction is sound** (`coding_repository_commit_review.rs:314-367`):
- Current bytes come from the same held `select_created_sources` / `LinuxCodingReadScope::read`
  path that planning already uses. They are hashed and compared with `file.postimage_sha256`.
  The bytes handed to the checker are exactly the bytes hashed, so a swap between read and check
  cannot deliver unbound content. Even a theoretical reader escape could only deliver bytes equal
  to the packet's hashed postimage.
- Base bytes are accepted only when `hash(bytes) == packet preimage == base.sha256`. Absence is
  accepted only for the all-zero preimage, with a required approved `created_mode`. Any missing,
  extra, mismatched or absent-vs-present inconsistency refuses with `code.commit.review-source`.
  `None` and `Some(&[])` stay distinct, because an empty blob hashes to `e3b0…`, not zero.
- The reported mode for existing files is `base.mode`. Planning already requires the candidate mode
  to equal it (`:664-679`). For creations the mode comes from `created_mode`, which planning also
  checks against the live permission bits (`:629-631`). So the reported mode is the candidate mode.
- Every packet file is included regardless of the selected group. Mode filtering by group
  (`:687`) still applies only to the kernel planner.

**Ordering and drift are handled.** The `RefCell` baseline keeps the first complete observation.
Sources are taken from it only after the full `before` plan, including its two observations and
the workspace snapshot recheck, has succeeded. Cancellation is checked on both sides of the capture.
The complete `GitObservation` equality now includes base bytes and is enforced on every pre/post
sample. The post-checker `after` plan, `before != after` and the workspace-snapshot binding are all
unchanged. A checker failure still stops immediately, and success still cannot skip the post-check.

**Confinement and authority are unchanged.** There are no new filesystem, Git, network or
command paths. Reads stay within the existing consented two-root scope and the offline Git worker.
There is no default or product checker, and no API/MCP/terminal route. The docs state clearly
that the bytes are untrusted and that read consent grants no disclosure authority.

**Tests are meaningful.** Hash-only base proofs with empty, different or NUL-suffixed bytes refuse
with the exact `code.commit.review-source` code, never reach the checker, and leave no candidate index.
Direct capture refuses changed postimage, missing, absent, extra and cleared base bytes, and the
original repo file is untouched. The positive checker tests check operation, path, base, current
and mode. The mixed-history test covers absent regular, absent executable and existing pairs, and
three sources for a two-file selected group. The collector tests compare the retained bytes through
`PartialEq` against real Git output.
