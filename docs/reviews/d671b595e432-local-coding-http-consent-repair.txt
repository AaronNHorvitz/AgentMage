## Assessment of the repair against M1

1. **Complete reviews survive backpressure.** `confirm` (`coding_cli_driver.rs:85-99`) now loops on `write`, advancing
   `remaining` by the bytes written, retrying on `Interrupted` and sleeping 10 ms on `WouldBlock`. Any other error or a
   zero-length write returns `Err`. A read starts only after `remaining` is empty, so an answer cannot be read against a
   truncated review. `std::fs::File` writes are unbuffered, so no hidden buffer is lost. The new tests use the real
   binary under a pty and ≥64 KiB inspection, start and tool reviews drained at 1 KiB per 5 ms; they would fail at the
   base, which truncated at ~12–26 KB in my base-review experiments. My item-7 rerun confirms the fix on the original repro.
2. **EOF, terminal failures and overflow send no decision.** A read returning 0 (EOF) or any non-retryable error,
   and a 256-byte line without a newline, return `Err` (`:105-121`). An `Err` from opening `/dev/tty`, a write or
   `safe()` also returns `Err`. In `decide` (`:205-207`) `Err` becomes `CodingClientError::Approval`. The shared driver
   then propagates it before computing a response (`cli_runtime.rs` `decide_with_selection(...).map_err(...)?`), so
   `advance` is never called. The driver's error path makes a best-effort release. In `consent` (`:241-247`) `Err`,
   `Deny` and `Stopped` all refuse inspection/start. The test `…_terminal_eof_and_overflow_send_no_decision` checks EOF at
   inspection, start and tool stages, plus overflow at the tool stage. It asserts the exact call count, no `advance` route
   and `cli.runtime.approval_unavailable` for the tool cases.
3. **The stop path still reaches canonical job control before dispatch.** `stopped()` is latched: an `AtomicBool`
   set only by the signal handlers, or `Instant::elapsed() >= limit`, which is monotonic. `Confirmation::Stopped` from
   either the write or the read phase maps to `Deny` in `decide` (`:212`). But the shared driver calls
   `cancellation.poll` right after `decide`, and that poll must observe the stop. It then either calls `cancel_run`,
   which uses `request_job_control(Cancel)` (revision-bound), or, if a cancellation was already sent, returns
   `Err(Cancellation)`. So the placeholder `Deny` can never reach `advance`. The generic `cancel` port still returns
   `RequestDenied`. The existing `…_interrupt_at_approval_uses_canonical_job_control_and_sends_no_grant` passes, and the
   new stalled-signal/deadline test shows a write blocked by an undrained terminal ends within the deadline with no prepare.
4. **Exact allow and denial are distinguished.** Only a complete line equal to `allow <challenge digest>` gives `Allow`;
   any other complete line gives `Deny`, which the prompt states. The large start/tool test checks that the dispatched
   disposition is exactly `allow` or `deny`, matching what was typed. `consent` treats only `Allow` as consent.
5. **Other boundaries are intact.** The lost-reply no-resend, event/artifact tampering, preparation binding and pipe
   refusal tests are unchanged and pass. The host loop, grants, endpoint, sandbox, run records and permission policy
   are not touched (2 source files changed, both in the API client crate). Other terminal commands keep their blocking
   `/dev/tty` confirm (`coding_cli.rs:286-313`), which does not have the M1 write truncation and is unchanged here.
6. **Evaluation integrity** is not affected: no held-out content, hidden test, fixture, threshold, score, model or
   dependency changed. The evidence makes no score, native-positive or parent-acceptance claim, and its labelling of
   synthetic peers as non-native is accurate.

## Findings

No high or medium findings. Medium M1 from the base review is repaired.

Observations, kept with the existing backlog rather than added as new findings:

- The backpressured-write stop is tested only at the inspection prompt. At the tool prompt it goes through the same
  `Confirmation::Stopped` value as the read-phase stop, which is tested. A future tool-stage stalled-write test would
  close that gap; its absence does not block the repair.
- The longer write window lengthens the typed-ahead exposure that is already low L1 in the base review (input typed
  during a slow review is read afterwards). Typed-ahead text can still never approve, because the digest is fresh for
  each prompt. The overflow case now ends the client instead of leaving the line's remainder queued, which narrows L1
  slightly. L1 and L2 from the base review, and the earlier resume, closed-channel and shutdown findings, remain backlog
  as stated.
