- A symlink root, and a root with a trailing slash through a symlink, both give `400 code.map.boundary`.

## Assessment of the claimed boundaries

- **Metadata consent grants no further scope:** confirmed by code (`lib.rs:857-898` touches neither
  `workspace` nor `pending_change`) and by my probes. The map route is control-only. It reaches no more
  than the existing control-only `select` already could, and it discloses only names, and only to that
  credential holder.
- **No content read; no link, mount, hard-link or special-file traversal:** confirmed. Every fail-closed
  error is content-free.
- **Deadline:** the deadline is cooperative and checked between native calls. The documentation says
  so, and that blocked syscalls can delay it.
- **Revalidation and root replacement:** the CLI verifies the root before and after confirmation. The
  server verifies `expected_root_sha256` before selection and again against the held scope's digest, so
  a replacement between the two checks is still caught. This was confirmed by test and by my PTY probes.
- **Strict JSON request shape:** unknown, duplicate and positional fields refuse, by test and by probe.
- **16-file ceiling:** `take(16)` in the CLI, plus the native `MAX_FILES`, both apply. The 20-file test
  selects exactly 16 paths.
- **Refusal framing (prior L3):** non-200 responses must be 400–599. They need JSON with a
  Content-Length of at most 4096, and streaming is rejected. The body is parsed before display, then
  escaped, printed to stderr only, and the client exits nonzero. There is no retry path: `idle()` only
  polls status, and every effectful call is sent exactly once. **The prior L3 is resolved.**
- **DEL (prior L2):** `safe()` now escapes U+007F. Every server-derived string goes through `show`,
  `confirm` or the refusal print, and all three use `safe()`. A unit test and an executable test cover it.
  **The prior L2 is resolved.**
- **Prior L1 (API-port squatting):** this is now documented in `local-chat-api.md` and

## Findings

No critical, high or medium findings.

- **L1 (low, usability):** `platforms/local-api/src/coding_cli.rs:446-452`. `map-select` takes the first
  16 positive-score paths without excluding entries that native selection is certain to refuse:
  case-fold aliases (`calc.py`/`Calc.py`), and non-UTF-8, binary or oversized files. One such path
  refuses the whole selection with `code.workspace.selection` or `boundary`, and `map-select` offers no
  way to drop a single path. I reproduced this over a PTY. The behaviour is fail-closed and the old scope
  is preserved, so this is not a security issue. Suggested fix: pre-filter case-fold duplicates on the
  client side, or offer per-path exclusion; until then, document that the user should fall back to
  explicit `select-model`.
- **L2 (low, approval display):** `platforms/local-api/src/lib.rs:1182` (behaviour shared with
  `select-model`). A successful `map-select` discards an existing pending write preview, but the
  `share` confirmation does not say that it will. This matches the existing selection contract, but a
  person may not expect it. Suggested fix: include `"pending_preview_discarded": true` in the displayed
  review when a preview exists.
- **L3 (low, diagnosability):** `platforms/linux/src/coding_map.rs:146-152` and `:200`. One unreadable
  subdirectory, non-UTF-8 name or in-tree mount refuses the entire map as `code.map.boundary`, with
  nothing to tell the person which entry is responsible. The refusal is correctly fail-closed and the
  guide says to use a smaller root. Suggested fix: add a content-free reason sub-code, such as
  `unreadable`, `name` or `mount`.
- **L4 (low, wording):** the TASKS.md T-303 row describes this one commit as two consecutive "next"
  batches ("The next batch documents …" followed by "The next [file-map batch] …"). Suggested fix: merge
  them into one sentence.
- **Note (not a finding):** `expected_root_sha256` binds canonical path, device and inode, so an inode
  reused after the root is fully deleted and recreated would pass the binding. Exact native per-file
  checks still run afterwards, so no confinement depends on this binding.
