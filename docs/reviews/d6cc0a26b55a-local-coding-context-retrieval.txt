### L1 (low, backlog): escaped newlines and tabs hide line-initial words from body matching

Location: `shells/host/src/coding_context_retrieval.rs:113` (`matches(&query, &source.bounded_excerpt)`)
together with `shells/host/src/coding_development_runtime.rs:862-868`.

**Cause.** The production repository excerpt is a JSON document (`serde_json::to_string` of
`{"schema_version", "untrusted_repository_source", "path", "content_sha256", "content"}`). In it,
newlines, tabs and carriage returns appear as the two-byte escapes `\n`, `\t` and `\r`. The
backslash acts as a delimiter, but the following `n`, `t` or `r` is alphanumeric and is glued onto
the next word.

**Effect.** The first word of every unindented line becomes `n<word>`, every word directly after a
tab becomes `t<word>`, and neither can match the objective. In tab-indented code this hits the
first word of nearly every line.

**Reproduction.** In the scratch Rust probe `reviewer_probe_line_initial_words_in_production_excerpts`
(objective `refund`, production excerpt shape), the body scores were:

| File content | Body score |
| --- | --- |
| `x = 1\nrefund = 2\n` | 128-0 matches |
| `package c\nfunc F() {\n\trefund := 1\n}\n` | 128-0 matches |
| `x = 1\ny = refund\n` (mid-line use) | 128-1 |
| no `refund` at all | 128-0 |

So a file that defines the relevant name at column 0, or uses it at tab indentation, ranks the same
as an unrelated file.

**Measured extent.** I ran the Python port over this repository's own files, counting distinct
words of 3–64 bytes that become unmatchable:

| Files | Distinct words lost |
| --- | --- |
| `scripts/*.py` (198 files) | 362 of 50,490 (0.7%) |
| `docs/guides/*.md` (74 files) | 905 of 19,747 (4.6%) |
| `shells/host/src/*.rs` (92 files) | 183 of 32,977 |

Path ranking, the dominant key, is unaffected, and nothing crosses an authority or confinement
boundary. It is still a correctness defect in the batch's only behavior.

**Test gap.** All five tests build plain-text excerpts, never the production JSON shape, so the
claim that body matching scores "source words" (guide) / "excerpt words" (evidence) is untested on
the real input.

**Fix.** Score the decoded `content` field, for example by computing body terms in
`build_repository_context_sources` before wrapping, or by parsing the excerpt as JSON inside the
existing owner. Alternatively, treat `\n`, `\t`, `\r`, `\"`, `\\` and `\uXXXX` escape sequences as
delimiters. Add a test that uses the exact production excerpt shape, with relevant words at
column 0 and after a tab. Resolve before any T-311 measurement attributes a change to this ranking.

### L2 (low, pre-existing, backlog): a conflicting identity is reported as a budget failure

Location: `shells/host/src/coding_context.rs:753-763` and
`shells/host/src/coding_context_retrieval_tests.rs:95-105`.

`compose_context` errors, including `ConflictingIdentity`, are mapped to
`RuntimePortFailure::ResourceExhausted`. The new duplicate test asserts that label, so a duplicate
identity reads to a caller as a budget overflow. It is not retried (the `?` exits the loop) and
fails closed. Only the diagnostic is misleading.

Fix: map `ConflictingIdentity` and `InvalidInput` to `RuntimePortFailure::Invalid`, keep
`ResourceExhausted` for `EssentialItemExceedsBudget`, and update the test. This mapping predates
this batch.
