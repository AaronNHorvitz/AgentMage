## Findings

No critical, high or medium finding.

### L1 (low, backlog; extends 1828e7e4eeaa L1): malformed tool-like answers in a completion-only turn become verifier candidates rather than a uniform completion-only refusal

`coordinator_endpoint.rs:650-654` refuses with `runtime.proposal.completion-only` only for text that parses
as `EndpointToolProposal` or has a top-level `tool_call` member. Text that looks like a tool call but does
not parse (P1/P3: extra or missing positional elements, `[{"tool_call":..}]`) falls through to
`RuntimeCompletionClaim::endpoint`. That constructor checks only binding, size and schema identity, not
content. The text then reaches the supplied verifier. That matches the documented contract: the verifier owns
acceptance, and nothing reaches admission because the fallback is closed at `:739-743`. It means the refusal
code depends on the verifier, though, and a lenient verifier receives junk candidates.
**Fix (with L1):** reject non-object top-level completion text before claim construction, or validate the
claim against the completion schema, so the completion-only and ordinary grammars are both object-only.

### L2 (low, backlog, test fidelity): the host "terminal refusal" test's verifier cannot handle completion input

`shells/host/src/coding_endpoint_edit_cycle_tests.rs:28-39`, `NeverVerify`, implements only `verify`. Today
this is correct, because every tested form must refuse before verification. A future regression that let a
tool-shaped answer reach claim construction would show up as `Err(Dependency(Invalid))` from the trait
default, not as a clear verifier-call assertion.
**Fix:** give `NeverVerify` a `verify_completion` that panics with a clear message, as the preview-test
variant at `coding_endpoint_edit_preview_tests.rs:156` does.
