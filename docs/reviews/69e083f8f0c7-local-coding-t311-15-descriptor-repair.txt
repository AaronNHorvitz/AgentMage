## Findings

### M1 (medium): permission repair is quadratic in time and memory on candidate-built deep branching trees; this is unbounded host-side work that can crash the case and leave residue

Location: scripts/coding_eval_oracle.py:281-296.

- Line 281: every deferred sibling is stored as a fresh tuple holding its full component path,
  `components + (name,)`.
- Lines 289-296: each deferred branch is reopened from the root, one component at a time.

For a chain of depth d with one sibling directory per level:

- **Memory:** the pending list holds d tuples of length 1..d, so the memory is Θ(d²).
- **Time:** reopening costs Θ(d²) opens.

The test at tests/test_coding_eval_oracle.py:322-355 uses only 2500 levels with a 60 s timeout, so
it cannot detect this growth.

Reproduction: see the table above. The time quadruples per doubling, both through real `grade` and on
the host, and the memory grows quadratically.

Building the tree costs the candidate about 0.1 s per 8000 levels. The candidate's 90 s timeout and
60 s `RLIMIT_CPU` do not apply to host cleanup. Extrapolating my measurements:

- about 96 000 levels (around 1.5 s to build) would need about 40 minutes and about 55 GB;
- that is beyond the memory available on this 62 GB host.

This is extrapolated, not run. The capped run shows what happens when memory runs out:

- `MemoryError` is not an `OSError`, so `candidate_temporary` (line 371) and `grade` let it escape.
  No report is written and an unchanged `verify` would abort.
- The traceback keeps the repair frame and its pending list alive during the cleanup that follows.
  `remove_case_workspace` therefore writes a **0-byte cleanup.json**, so the private recovery record
  has no workspace path.
- The candidate scratch tree is left behind.

A real kernel OOM kill would skip cleanup entirely. It would also put pressure on everything else on
the shared workstation.

Why medium and not low:

- These are the consequences that review 1 M1 and review 2 M1 were rated medium for: a lost outcome,
  retained residue, and a candidate effect presented as a harness fault. Here they arrive at greater
  depth or under a memory cap.
- This repair introduced the problem. The removal walk it replaces and the walk it adds are linear.
- The evidence (lines 28-31) discloses only "quadratic work". It names candidate quotas as the
  remaining requirement. Neither a candidate disk/memory/time quota nor the L1 scratch quota bounds
  host-side cleanup memory. A modest metadata quota still allows tens of thousands of levels.

It is not high: no confinement escape was found. Generated scoring is disabled. Only frozen controls
and synthetic probes run today, and failed attempts stay counted.

Fix:

1. Make repair linear and bounded. Either:
   - fold repair into `remove_fixture_tree`'s postorder walk: before scanning a directory, chmod it
     through the O_PATH pin and `/proc/self/fd`, then open it for reading; or
   - keep a separate repair walk but ascend through `..` with the same recorded (name, st_dev, st_ino)
     identity checks, instead of reopening from the root.

   Either keeps O(depth) small records and O(1) descriptors.
2. If any non-OSError escapes, drop large structures before outer cleanup runs.
3. Add a regression that checks scaling, not just completion. For example, time repair plus removal on
   branching trees of 10 000 and 20 000 levels, and require a ratio well below 4 together with bounded
   peak memory. Also run one in-sandbox branching case.
4. Correct the evidence's statement about cost and mitigation.
