## Findings

No critical, high or medium finding.

**L1 (low) — selection ignores a concurrent cancellation.** `platforms/local-api/src/lib.rs:824-845`.
`PUT /v1/code/workspace` installs the grant after `LinuxCodingReadScope::select` without checking
`op.cancel.is_cancelled()`. A `/v1/cancel` that answered `cancellation_requested: true` during
selection still leaves a live grant and an `accepted` record. The read and search routes do check
(`:893`). The window is small because selection is bounded and non-blocking, and the control client
still receives a 200. Fix: check cancellation before taking the state lock. If set, return
`409 code.workspace.cancelled` and keep the previous grant. Add a regression test.

**L2 (low) — lease released only after the terminal response is written.** `Operation::drop`
(`lib.rs:577`) runs after `response`/`event` returns, so a strictly sequential client can receive
its answer and then get a spurious `409 api.busy` on the next call. The builder's first driver
failed this way. The guide now tells clients to poll `/v1/status`, but every API consumer
(the future MCP/CLI) inherits the race. Fix: record the outcome and clear `active` before writing
the final response, or release the lease explicitly before the last write.

**L3 (low) — the snapshot route now takes the lease before validating input.**
`lib.rs:792` versus `coding_proposal` (`:652`). Malformed `/v1/code/proposals` requests now take the
single-operation lease, appear in activity, and return 409 instead of 400 while another operation
is active. Previously they were refused before any state change. Content stays private and no
authority changes. Fix: run `prepare_coding_proposal`, the token check and the encoding check
before `begin`, or document the change.

Prior lows: 3aef L1 is addressed (answer-cap, terminal-outcome and settings-refusal regressions
exist and pass). L2 (campaign grade/candidate binding) and L3 (worktree write revalidation) stay
backlog, as stated.
