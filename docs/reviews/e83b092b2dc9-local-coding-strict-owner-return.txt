## Security analysis (confinement and ownership boundary)

- **No wire selection of the return policy.** `return_repository` is a compile-time `bool` passed
  only by the four library entry points (`coding_endpoint_prepared.rs`). The HTTP handlers have no
  field that reaches it. Release still requires the control token: the observation credential gets
  403, which is tested. The exact `run_id`/`request_sha256` binding gets 409 for a foreign digest,
  also tested.
- **Release preconditions.** These are unchanged and shared. `release_with_tool_boundary` refuses
  `Released`, `faulted`, and outcome-less entries (`coding_endpoint_owner.rs:315-344`). Engine
  `try_into_endpoint_tool_boundary` refuses non-terminal, `Uncertain`, unpublished-terminal,
  pending, suspended and reconciliation-required coordinators (`coordinator_endpoint.rs:321-339`).
  The custom-turn returning variant passes `TerminalToolDisposition::Return` into the same
  `serve_admitted_endpoint_inner`, so no separate path exists.
- **Sole-owner extraction** (`coding_endpoint_edit_previews.rs:548-569`):
  - It checks `Arc::strong_count == 1` on an owned `self`.
  - The module creates no `Weak` references, and `CodingEndpointEditBoundary` is not `Clone`, so
    no other reference can appear after the check.
  - A poisoned mutex or an empty `owner` slot (an operation in flight, or a panic while the owner
    was taken) refuses.
  - Port, verifier and completion-check clones are dropped with the consumed coordinator before
    extraction. The checked service test returns `Some` for the cancel, deny and ready-preview
    release cases, which shows they really are dropped.
- **Abandonment** (`coding_repository.rs:170-175`):
  - It clears only the process-local `pending`/`command`/`edit`/`apply` previews. Validation
    commands are previewed through `command`.
  - Uncertainty is recorded in the retained `edit_result`/`apply_result` (`effect: unknown`).
  - Uncertain edits remove their postimage from `created.edits` before dispatch
    (`coding_repository_edit.rs:153-163`), and apply is checked against that lineage plus a
    worktree re-hash (`coding_repository_apply.rs:229-246`). Clearing previews therefore cannot hide
    an uncertain effect or allow a write from an abandoned preview. The Linux apply test confirms
    that the old digest is refused and the original bytes and index are unchanged.
- **Drop on error.** No `Drop` impl for `LinuxCodingRepository` deletes or writes anything, so an
  error that drops the owner loses process-local continuation only. This is documented.
- **No restored authority.** No run, grant, budget, disclosure consent, connection, path adoption
  or durable recovery is restored. A later diff needs fresh read-consent identities
  (`prepare_apply` with root digests), and applying it needs `decide_apply`'s separate approval.
  Nothing commits or pushes.
- **Privacy and branding.** No private host path, username, hostname, credential, personal data,
  private sibling-project name, or other agent product name appears in added lines (`check.py`
  scan plus my own grep). No dependency, lockfile, SBOM, status-model, scoreboard, held-out,
  hidden-test, scorer or threshold change (`check.py` path assertions and my own diff review).
- **Evaluation integrity.** Nothing is touched. No score, model qualification or positive
  original-owner acceptance is claimed. `MustNotCheck` panics if dispatched, and it never is.

## Findings

No critical, high or medium findings.

- **L1 (low, backlog): `released:true` can be followed by owner loss without a client signal.**
  Location: `platforms/local-api/src/coding_endpoint_prepared.rs:379-385`.
  - If `try_into_repository` fails after a successful HTTP release (for example a poisoned strict
    state from a panic that left the run terminal and non-faulted), the service returns
    `ApiError::Configuration` and drops the original owner.
  - The person-facing client has already been told `{"released":true}`.
  - This is documented ("service errors can drop ownership") and loses no data, but no test covers
    this path.
  - Fix: add a test that poisons the strict state before release. Also consider making
    `release_with_tool_boundary` refuse when extraction would fail, so the run stays held for
    inspection instead.
- **L2 (low, backlog): the non-turn returning service lost its direct socket tests.**
  - The `coding_endpoint_tool_return.rs` socket tests now exercise only
    `serve_admitted_coding_endpoint_with_turns_returning_tool`.
  - The older `serve_admitted_coding_endpoint_returning_tool` is a thin wrapper over the same inner
    function and is still exercised through the prepared service
    (`endpoint_prepared_service_native_edit_returns_original_lineage_and_needs_new_approval`
    passes).
  - Its direct fault, uncertainty and no-release socket coverage is now indirect only.
  - Fix: parameterize the tool-return fixture over both entry points.
