## Independent probes

- Predecessor bf27deb3 `parse_response(b"OK\nOK\nOK\nOK\nD (7:sig-val(1:x1:%+1))\nOK\nOK\n")` returns
  `Some(..0x01..)`, which reproduces L-1.
- The pinned commit returns `None` for that input.
- The pinned decoder also refuses each of these: `%+1`, `%-1`, `% 1`, `%1 `, `%+f`, `%0x`, full-width
  digits, `%%25`, a trailing `%2`, a raw CR, an escape split across records (`%2\nD 5`), and a D record
  outside phase 4.
- It decodes `%41` to 0x41 and `%4a%4A` to 0x4a 0x4a.
- Over all 65,536 `%XY` pairs, it accepts exactly 484 (22 × 22). Each accepted pair has two ASCII hex
  digits, and the other 65,052 are refused, matching the claim.
- The fix (`local_commit_signing.rs:295-299`) checks `is_ascii_hexdigit` on both bytes before
  `from_str_radix`, so the parser's optional sign can no longer be reached. The remaining `from_utf8` is
  now redundant but harmless.
- The added protocol case `text.replace("(1:r1:a)", "(1:r1:%+1)")` really substitutes, because
  `response()` contains `(1:r1:a)`; if it did not, the `is_none` assertion would fail on a valid
  response. The `%+1` therefore sits inside otherwise valid signature data, so refusal does not depend
  on the outer prefix.
- L-2 check (`local_commit_signing_tests.rs:562-599`):
  - The signer now uses a real 0700 fixture directory with a 0600 selected key file.
  - A positive `PrivateKey::capture` reads back the exact bytes.
  - `verify_private_keyring` returns the same path, `pinned.verify()` succeeds and the public-key digest
    matches.
  - `check_control` (`local_commit_signing.rs:169`) passes with a fresh token and a 5 s deadline.
  - The executable path is not consulted before the keygrip filter at lines 175-179.
  - So the only remaining cause of refusal is keygrip validity, and the test now pins the kind to
    `ArtifactDenied` for both `None` and `"A\nPKSIGN"`. The evidence correctly says this is not a
    successful native `sign_hash` call.
