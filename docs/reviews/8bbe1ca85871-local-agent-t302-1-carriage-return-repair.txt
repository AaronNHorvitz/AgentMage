## M2 repair: verification

Code at `local_chat.rs:313-319`. After one trailing CR is removed (line 314),
any remaining `b'\r'` in the line returns `ChatError::Protocol`. This happens
before BOM handling, UTF-8 decoding and field dispatch, so neither the comment
branch nor the `_ => {}` metadata arm can see a line that has a CR in it. `feed`
poisons the decoder on any error.

Probe results on the scratch copy of HEAD. Each body was run whole, at every
two-way split and byte-at-a-time:

## Findings

No critical, high or medium finding.

### L7 (low): CR-only framing fails late and is reported as Incomplete or Limit, not Protocol

Location: `local_chat.rs:309-311`. A non-LF byte is appended to `self.line` even
when the previous byte was a CR. A stream framed entirely with CR terminators
(valid in the event-stream format) is never accepted, but it is not refused at
the first lone CR either. Probe: the full answer re-framed with CR returns `Ok`
with no events from `feed`, then `Incomplete` from `end`. A 218,000-byte
CR-only stream was buffered for 65,536 bytes before `Limit`. This fails closed,
so there is no false success and no lost text that could be shown as complete.
However, a user pointing at such a server would see a silent stall and then a
misleading error class, and the guide implies refusal at the CR itself. Fix at
T-309, or with T-302.2's clear-errors work: when pushing a non-LF byte, return
`Protocol` if `self.line.last() == Some(&b'\r')`. Add a CR-only regression test
that asserts `Protocol` before the first LF.

### L8 (low): the regression test does not pin CR refusal on `data` lines

Mutant E survives: exempting `data…` lines from the CR refusal passes all 19
tests. The test's `"data: \r"` case is refused only because the JSON parser
rejects the `"\rdata: …"` it produces. At HEAD, a lone CR at a JSON-whitespace
position (`data: {"model":"m",\r"choices":[]}`) is correctly refused, but no
test asserts that. No text-loss path exists under mutant E, because everything
after the CR stays in the JSON value, so this is a test-strength gap only. Fix:
add that body to `lone_carriage_returns_cannot_hide_text_at_any_fragment_boundary`.
