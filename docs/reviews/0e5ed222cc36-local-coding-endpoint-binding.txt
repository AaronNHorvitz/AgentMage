## Review of claims

- **Body binding:** `prepare_chat` (local_chat_transport.rs:317-355) hashes the same
  `Zeroizing<Vec<u8>>` that `execute` passes to `chat_encoded`. `request()` writes the headers, then
  `write_all(body)` with `Content-Length: body.len()`, and applies no transformation. Headers and
  credentials are excluded. Model, usage option and ceiling come from the binding, so `execute` has no
  way to vary them. The borrow checker enforces that the request is independent of the caller's
  messages: the builder's test clears the prompt after preparation and still compiles.
- **Endpoint:** `parse` accepts only `is_loopback()` IP literals, or `localhost` pinned to 127.0.0.1.
  It requires an explicit non-zero port and brackets for IPv6, and refuses traversal and encoded paths.
  `base_url` formats the numeric `SocketAddr`, so the endpoint is canonical.
- **Limits:**
  - `response_wire_limit_bytes` = `MAX_WIRE` (5 MiB, `Wire::fill`).
  - `response_body_limit_bytes` = `MAX_STREAM_BYTES` (4 MiB). This is now the same constant for
    `wire.body` and the codec (local_chat.rs:390); it was a literal of the same value before.
  - `response_text_limit_bytes` = `MAX_TEXT_BYTES` (1 MiB, codec local_chat.rs:500).
  - The values are unchanged; only the visibility changed to `pub(super)`.
  - `Duration` serializes as `{secs,nanos}`; the 50 ns / 25 ns test confirms there is no rounding.
- **Ordering:** `chat` and `chat_with_usage` still check approval, then cancellation, then encoding,
  before any connection. `execute` and `request()` check cancellation again. Return types are
  unchanged.
- **API:** `coding_proposal_with_feedback` (lib.rs:1029-1075) prepares once. It clones the binding into
  the context event and into every terminal event through `proposal_observation`.
  - `response_complete = completion.is_some()`, and `completion` exists only for `Ok` transport
    results.
  - An oversized answer cancels the transport, so it yields `Err(Cancelled)` and false.
  - Length finishes and invalid strict edits keep `true` and still refuse, as documented.
  - A disconnect (`!writable`) returns before writing any terminal record.
  - Usage is attached only when requested and completed.
  - Snapshot, workspace (lib.rs:900) and repair (coding_repair_api.rs:88) all reach this single path.
    General chat (lib.rs:1843) is unchanged and out of scope.
  - I found no second loop, retry, write or tool grant.
- **Consumers:** the CLI (coding_cli.rs:396), MCP (coding_mcp.rs:341) and measurement collector
  (coding_proposal_measurement.py) check individual fields rather than exact key sets, so the
  additive fields break none of them.
- **Integrity, privacy, IP:**
  - The ten paths match exactly. No evaluation, hidden-test, scorer, threshold, dependency or ledger
    row changes (audit.py confirms the ledger rows are unchanged).
  - No new `#[ignore]`.
  - The added text contains no home path, username, hostname, credential or private sibling name.
  - The `/lane/...` paths occur only in the retained review, as in 87 earlier committed reviews.
  - No third-party product is named or compared; the reviewer attribution is not branding.

## Findings

- **L1 (low, test strength):** platforms/local-api/tests/local_chat_api.rs:241-276 and
  platforms/local-api/src/coding_repair_api.rs:254-276,354.
  - The API-level tests check the binding's `request_body_bytes` against the observed body length.
  - The snapshot test compares the full binding by re-encoding the observed messages. It does not hash
    the raw received bytes, and the repair fixture does not check the digest at all.
  - The raw-byte hash is proven at the transport layer, by the builder's test and my probe. The API
    path uses that same `execute`, so I see no defect.
  - Fix: hash `raw[start..]` and `bytes` directly with `sha2` in both fixtures and compare the hash
    with `model_binding.request_body_sha256`.
- **L2 (low, robustness):** platforms/local-api/src/lib.rs:1029-1040.
  - A `prepare_chat` error returns a bare 400 with a transport code. In the repair route this happens
    after `consume_repair_feedback` (coding_repair_api.rs:77-83).

    `encode_chat[_with_usage]` with the same inputs. `Configuration` mints its approval from the same
    endpoint as its transport (lib.rs:1708-1710).
  - No test covers the branch.
  - Fix: prepare the transport request during preflight, before receipt consumption, or document and
    test the branch as unreachable.
