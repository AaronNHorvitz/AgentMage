## Review

**Correctness of the binding.**
- On the actual service, the edit-prepare reply and the later `pending` are the same object. Native
  `prepare_edit` builds `preview`, stores `preview.clone()` in `PendingEdit` and returns it
  (`coding_repository_edit.rs:80-97`). `inspect_edit` returns `self.edit.preview` unchanged (`:103-113`).
  The API passes the value through unwrapped (`coding_repository_api.rs:354-371`).
- So `edit["pending"] != prepared_edit` (`coding_cli_workflow.rs:203-206`) holds for every legitimate run.
  It cannot spuriously refuse, because nothing in the service mutates the stored preview between prepare
  and decide.
- Errors fail closed. A 409 body would lack `"operation":"edit-worktree"` and is refused at `:197`.
- `edit_decide_bound` now receives `&prepared_edit`. Its own GET is compared by full equality (`:629-636`),
  so the person is prompted only with the original reply.
- A replacement after that last inspection still fails natively. `decide_edit` compares the original
  `preview_sha256` the client sends against the stored hash (`coding_repository_edit.rs:118-121`), then
  checks expiry, scope and creation. Native digest and preimage authority are unchanged.
- The standalone `edit-prepare`, `propose` and `propose-worktree` commands only add `.map(|_| ())`, so
  their output is unchanged.

- **L3 (low, backlog): the original prepare reply's creation and root pin is no longer covered by any test.**
  - **Location:** `platforms/local-api/src/coding_cli_workflow.rs:197-202`, and the `new-creation` case in
    `tests/support/coding_workflow.rs:762-771`.
  - **Cause:** Before this commit, `new-creation` changed only the first pending GET's
    `creation_receipt_sha256`, and the per-field check caught it. Now the full-equality check at `:204`
    catches that case first.
  - **Evidence:** In my mutation probe, deleting the operation/root/creation check on `prepared_edit` left
    all nine guided workflow tests passing.
  - **Impact:** The code is correct today. The native owner still rejects a creation or scope change at
    `decide_edit`, and `verify_root` re-checks the root locally. But a later edit could drop the client's
    binding to the preflight creation without any test failing. The guide's claim that the terminal
    "verifies its worktree root and creation binding" is unpinned.
  - **Fix:** Add a case where the edit-prepare reply and both following pending GETs consistently carry a
    different `creation_receipt_sha256`, and another for `worktree_root_sha256`. Assert a stop at
    `calls.len() == prepare + 1`, `answered == 1`, and no edit decide.
