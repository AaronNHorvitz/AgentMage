**Code reasoning.** I confirmed the following from the code:
- `call_policy` refuses `allow_observation_busy` for anything except the exact combination of
  `POST /v1/code/endpoint/events` with `control == false`.
- `observation_page` is the only caller that enables the policy.
- `call` and `receive_before`, which every effect caller uses, map `ObservationBusy` to `Err`.
  Effect callers therefore keep their no-retry behaviour.
- The 409 exception is evaluated only after the full refusal checks: Content-Length required, no
  streaming, at most 4096 bytes and an exact decode.
- HTTP 200 bodies are returned as `Values` and then fail the typed page checks.

## Confinement and safety assessment

- **Credential.** The watcher calls `token(false)` only, through `protected_directory` and then
  `read_api_token` (O_NOFOLLOW, mode 0600, nlink 1, owner uid). The test replaces `control.token`
  with an invalid symlink, so a control load would fail. The watcher still succeeds, which shows it
  never opens the control credential.
- **Authority.** The server answers 403 to the client credential unless the service started with
  `DelegateObservations`. That check (coding_endpoint_api.rs:472-480) covers only the request and
  events routes. The watcher has no means of enabling delegation.
- **Pinning.** Before any event poll, `checked_selection` requires the exact run id and request
  digest, plus a verified sealed request. Each event poll is checked for:
  - one event per page, with `next`, `total` and retention consistent;
  - matching run, session, task and policy identities;
  - `sequence == after`;
  - a first event that is `RunStarted` with the exact request digest;
  - acceptance by the full kernel `RuntimeEventSequence` (contiguous hashes, unique ids, causation,
    monotonic time and legal transitions);
  - no shrinking total, and no total above min(4096, `max_events`);
  - a terminal event only when `after == total`.
- **Effects.** The watcher has no confirm call, no advance, cancel or release, and no file writes.
  Output goes through `safe()`, which keeps only escaped ASCII with no ESC or DEL, and is
  byte-counted against 4 MiB including the newline. That check happens before each write.
- **Bounds.**
  - The original monotonic `Signals` deadline of 1-3600 s is enforced in `check_running`,
    `call_policy` (the time remaining when connecting) and `read_until`.
  - The loop is capped at 40,096 polls.
  - SIGINT, SIGTERM and SIGHUP set the latch, and the actual signal tests exit 1 with the run held and
    no events.
  - Blocking stdout is outside preemption, which the guide and decision document.
- **Prompt injection.** Event content is only rendered. Nothing in it is parsed into actions, URLs
  or routes.
- **Supply chain and evaluation integrity.** The commit has no Cargo.toml or Cargo.lock change and no
  new dependency. It touches no evaluation, held-out, hidden-test, threshold, scoreboard or prompt
  files (11 paths, all listed in the plan).
- **Privacy.** In the added lines there are no `/home`, `/var/home` or `/Users` paths, no username,
  hostname, email or credential, and no third-party product branding. Lane paths appear only inside
  the byte-identical retained review. The TASKS.md table rows are unchanged, as check.py confirms,
  and the IN-FLIGHT entries and history are preserved.
- **Honest claims.** The guide and evidence say plainly that the watcher's verification is service
  self-consistency only, and that a cancelled or failed terminal state exits 0 without any task
  acceptance. No native, model or task-grade claim is made.

## Findings

No critical, high or medium findings.

- **L1 (low, availability and documentation).** The watcher's 10 Hz polling can briefly hold the
  service session lock.
  - Location: coding_cli_watch.rs:42-49 against coding_endpoint_api.rs:569-573, where the events
    route takes `session.try_lock` and writes the reply while holding it, and :513-517, where
    `advance` and `release` use the same lock.
  - Effect: a concurrent control `advance`, `endpoint-run` step or `release` can get a pre-dispatch
    409 `api.busy`. The probe measured this for 4 of 2376 control reads.
  - Control callers correctly never retry, so the guided flow stops and leaves the run held. The
    user must re-run, or use `endpoint-approve` for a pending challenge.
  - This is safe because it fails closed before dispatch. However, the guide's statement that
    "Original controls remain available in the other terminal" does not mention it.
  - Fix: either document in docs/guides/coding-mcp.md that controls may see a transient `api.busy`
    while a watcher polls, and that it is safe to repeat because it precedes dispatch, or serve
    observation pages from a snapshot that does not hold the coordinator lock while writing the reply.
- **L2 (low, test coverage).** The real-service test covers growth only from total 0 to N, because
  the whole chain appears after one advance. Growth of the total in the middle of a chain
  (`after > 0`) is allowed by the code (`count < total` refuses only shrinkage) but no test exercises
  it.
  - Fix: add a fake-peer case whose total increases between non-empty pages. This can go in the
    existing test; no new sub-row is needed.
- Carried same-row backlog from the parent review is unchanged: native launch-to-service forwarding
  coverage.
