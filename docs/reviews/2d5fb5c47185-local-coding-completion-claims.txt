## Analysis

**Coordinator entry.**
- `runtime_loop.rs:2949` now calls `verify_completion(...into_completion())`.
  `into_completion` wraps the same `&ClosedModelProposal` and moves every other field unchanged.
- Native model/proposal admission, approval, state transitions and `registry.verify(&candidate)`
  are untouched.
- The test `completion_claim_existing_coordinator_calls_model_independent_verifier_with_original_native_proposal`
  shows three things:
  - The verifier's `verify` and `verify_scoped` both panic and are never reached.
  - Pointer identity holds for the proposal id and payload.
  - A tampered approval digest is refused before any effect (executions = 0, calls = 0), and the
    run still completes after a correct approval.

**Default adapter** (`runtime_loop.rs:1192-1213`).
- The order of checks is: `matches_scope` (native profile and codec equal the run's),
  `native_request()?`, then `native_proposal()`, and only then does it delegate to the existing
  `verify_scoped` override.
- Endpoint claims fail at step 1 or step 3 before either legacy method. The panicking
  `LegacyCompletionVerifier` and `NativeOnly` tests prove this.
- Existing `verify_scoped` overrides are still reached through the coordinator. The predecessor's
  scoped coordinator test still passes unchanged.

**Endpoint claim** (`completion_claim.rs:96-160`).
- Construction requires an endpoint `RuntimeRunScope`. That scope's constructor re-verifies the
  complete sealed digest, so binding through `request_sha256` covers the objective, policy and
  limits.
- It also requires all of the following:
  - The turn's private `RuntimeEndpointRunBinding` matches the run id, session, task and digest.
  - The selected endpoint and model are equal.
  - The response length equals the accepted length. This is checked before hashing, so
    caller-supplied text is never hashed unbounded.
  - SHA-256 equality with the accepted response.
  - Text that is non-empty and within `max_output_bytes`.
  - A valid schema reference.
  - `valid_output_payload`.
- The claim `kind` is fixed to `CompletionCandidate` with `has_tool_call` false. Model text can't
  pick the schema, the kind or a tool call, and it is never parsed as instructions.
- `serde_json::to_vec` of the full turn, schema and payload produces the claim digest, and the
  proposal id derives from that digest. The tests check that it is deterministic and
  schema-sensitive.
- `RuntimeEndpointTurnResult` has no public constructor, Clone or Deserialize, so a wire claim
  can't forge an accepted turn.
- `matches_scope` re-binds the claim when it is used. Tests show refusal for changed run id,
  model, `policy_sha256` and objective, each resealed; for a native scope; and for stream text
  with an extra byte or the same length but altered content.
- The prompt-injection surface is limited to the model writing candidate JSON. `parse_candidate`
  still requires the exact coding schema, `application/json`, a payload hash, the objective
  SHA-256 and bounded fields. Success still requires caller-supplied current receipts, ordered
  validation and repository inspection, and the registry. A text-only claim gets `Failed`, as the
  mutation test shows.
