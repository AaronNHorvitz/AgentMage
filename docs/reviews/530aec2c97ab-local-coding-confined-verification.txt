## What the evidence supports

- **No direct verification fallback.** `execute_plan` calls `verification::verify` after
  `verify_raw_commit` and before `update_task_branch` (`local_commit.rs:478-490`). Any error goes to
  `failed_signer_result` and returns before the ref update. The result is Failed with
  `cleanup_verified=false`, or `signer_cleanup_uncertain` when the error is `CleanupUncertain`.
- **Pre-dispatch checks** (`local_commit_verification.rs:121-131`), each tested without dispatch:
  - cancellation and the deadline;
  - sealed-plan validity;
  - an exact signer match and the pin's own seal;
  - public-key bytes that are non-empty, within the bound, and whose digest equals
    `pinned.public_key_sha256`;
  - the raw-commit bound.
- **Signature extraction.** `split_signed_commit` first requires `verify_raw_commit`: exact singleton
  tree, parent, author, committer and format-specific signature header, exact message bytes, and only
  space-continued signature lines. It then removes exactly that header block. My native run and the
  builder's real-key test both confirm the reconstruction is byte-exact in both formats.
- **Sealed public material.** Three sealed memfd payloads hold the retained export, the signature and
  the content. A test confirms that writes to them fail with EPERM.
- **Projection.** Only gpg, the filter and those three payloads are projected (descriptors 3-7).
  - No repository, keyring, home, agent socket or configuration is mounted.
  - `--clearenv`, a private 0700 tmpfs home, `--no-options`, `--no-autostart`,
    `--no-auto-key-retrieve` and `--no-default-keyring --keyring /app/public.gpg`.
  - The existing EPERM socket and connect denylist, unchanged.
  - The same memory, task, CPU, runtime and kill-mode properties as the repository-Git worker.
- **Executables.** systemd-run, systemctl, Bubblewrap and gpg are held and checked to be root-owned with
  root-owned ancestors (`verify_root_owned_path`). The gpg digest must equal the inspected signer
  digest, computed the same way. The artifacts are revalidated before launch and on every supervisor
  control call.
- **Closed owner.** The unit name is a new prefix plus a 24-hex nonce, and exactly three projections
  are admitted. The prefix is added to `unit_name` for observation parsing.
- **Result validation** (`local_commit_verification.rs:146-174`). It requires all of the following, and
  each negative case is tested:
  - an `Ok(Succeeded)` outcome and a successful exit status;
  - complete output;
  - empty stdout;
  - stream totals and digests consistent with the retained bytes;
  - exactly one `VALIDSIG` for the complete pinned fingerprint and no failure statuses;
  - no cancellation and an unexpired session deadline afterwards.
- **Labelling.** The disposable real-key method still covers both formats, both exact keys, three
  message cases, unpinned controls, the wrong key and an unchanged branch. It now also covers altered
  messages, an invalid key and the absence of an agent or private-key directory. It is correctly
  labelled as component cryptography, not native admission.
- Using the retained snapshot export instead of the live keyring does not weaken revocation handling
  in practice. An exact-key `-S<fpr>!` signing step refuses a revoked or expired key before
  verification, and the expiry carried in the snapshot is still evaluated.

## Findings

No critical, high or medium findings.

- **L1 (low, backlog; part of the existing native `run_plan` / native-signature low).**
  `local_commit_verification.rs:60-109`: no test in this lane executes the product dispatch. That covers
  `VerifierManifest::verify`, `run_owned` with `LaunchOwner::CommitVerification`, systemd `OpenFile`
  allocation, the real compiled filter and gpg inside the guest. The only native caller,
  `native_signed_commit_verifies_exact_content_and_only_updates_task_branch`, is an inherited failure.
  It stops at `inspect fixture signer: ArtifactDenied` (`local_commit.rs:1885`) because the lane's
  binaries are not root-owned. The Rust tests check only argv shape and synthetic results. My manual
  reproduction of the guest argv with an approximated filter succeeds and refuses correctly, but it is
  not product evidence. The evidence documents state this honestly, and the adapter is dormant.
  - Fix: when a host with root-owned artifacts runs the native signed-commit test, also record a
    tampered-signature `run_plan` case. Assert `verification_failed` and an unchanged task branch.
- **L2 (low, backlog; defence in depth).** `local_commit_verification.rs:238`: `--status-fd=2` puts
  machine status records on the same stream as GnuPG's human log. `verify_signature_status` then relies
  on human lines never beginning with `[GNUPG:] `. In my run they all began with `gpg: `, and gpg
  sanitizes the strings it prints from signature subpackets. Acceptance also needs exit 0, exactly one
  `VALIDSIG` for the pinned key and no failure status, so I found no exploitable path.
  - Fix: use a dedicated status stream. For example, `--status-fd=1` and validate stdout as pure status
    while ignoring stderr, or add `--quiet` with a separate `--logger-fd`. Update the empty-stdout rule
    to match.

The earlier same-row lows remain backlog unchanged: base L1 native retained-child injection, L2
poisoned-owner diagnostic, native signatures, fixture-agent teardown, usable-key inspection,
