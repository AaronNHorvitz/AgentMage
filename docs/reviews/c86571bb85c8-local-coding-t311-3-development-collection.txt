## Findings

### M1 (medium): dev-014's statement contradicts or omits interfaces that its frozen selected tests require

Location: `scripts/coding_eval.py:416-445` (dev-014 statement). The selected methods are in
pinned `tests/test_sprint_16_linux_worker_evidence.py` at `c16884163206`.

The request asks that every statement be checked against the selected assertions, including
exact errors and refusal cases. For dev-014, three requirements of the frozen tests are absent
from the statement, and one of them contradicts it:

1. **Unavailable commit: exception type contradicts the statement.**
   `test_real_git_closure_covers_child_modules_modes_and_docs` ends with
   `assertRaises(subprocess.CalledProcessError)` for `complete_source_closure("0" * 40)`. The
   statement instead says "Diagnostic contract: use ValueError (or the existing
   WorkerEvidenceError subclass)" and "Refuse … invalid object identities/types". The selected
   `test_changed_or_unavailable_committed_source_fails` also models an unavailable commit as
   `ValueError("missing commit")`. A candidate that follows the statement and refuses the missing
   commit with `WorkerEvidenceError` fails the frozen task. Reproduced by the `wrap-unavailable`
   variant above, a one-line change to the reference.
2. **Undisclosed subprocess call sequence.**
   `test_batch_integrity_refuses_truncation_identity_and_trailing_bytes` patches
   `evidence.subprocess.run` with a fixed side-effect sequence:
   - a type probe whose stdout must be accepted when it is `b"commit\n"`;
   - a long-format inventory with object sizes (`100644 blob <oid>       3\tfile.rs\0`);
   - a `--batch` content call.

   The duplicate-inventory case also requires the message to contain `inventory invalid`.
   The statement never mentions a type probe, the `-l` inventory format or the use of
   `subprocess.run` (as opposed to `check_output`). It also does not limit the number or order
   of calls. A correct implementation that checks the commit with
   `git rev-parse --verify REV^{commit}` fails. Reproduced by the `verify-commit` variant.
   Using `check_output`, or adding any extra call, would also fail: an exhausted mock raises
   `StopIteration`, which is not a `ValueError`.
3. **Call order and first-failure position.**
   `validate_current` and `test_changed_or_unavailable…` use `side_effect=[expected, changed]`
   and then assert on `[0]` of the returned failures. This requires `complete_source_closure` to
   be called exactly twice, for the report's `source_revision` before the local revision. It
   also requires the "historical" and "not equivalent" diagnostics to be the *first* failure.
   The statement says only that the rejection "includes" these substrings.

Impact: dev-014 would score correct, statement-following candidates as failures. This
under-measures model results on a frozen task. The defect is the same class as T-311.1's M2/M2-R,
and the statements must be correct before any model measurement because they cannot change
afterwards. The evidence record's claim that "The statement interface audit covers selected
methods and their helpers" is not supported for dev-014. The automated audit
(`tests/test_coding_eval.py:56-94`) checks only attribute names reached through module aliases.
It cannot see exception types, mock targets or call protocols.

Fix: before any model run, publish a recorded pre-measurement correction of the dev-014
statement only, with no test, selection, pin or threshold change, as v3 did. It should state:

- `complete_source_closure` lets Git's `subprocess.CalledProcessError` propagate for an
  unavailable revision; only `validate_current_source` turns it into a failure.
- It makes exactly three `subprocess.run` calls in order: `git cat-file -t REV`, which must
  return `commit\n`; `git ls-tree -r -l -z --full-tree REV`, the long format with sizes; and
  one `git cat-file --batch`. It reads `.stdout` bytes.
- `validate_current_source` computes the `source_revision` closure before the local one.
- The named diagnostic is the first returned failure.

Alternatively, drop dev-014 in full; do not narrow its selection. In either case, run a
statement-only variant check for each new task, as review 3 of T-311.1 did, and record it.
