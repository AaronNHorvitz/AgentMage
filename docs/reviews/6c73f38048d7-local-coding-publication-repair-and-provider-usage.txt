### Optional endpoint usage

- Codec (`local_chat.rs`): `encode_chat` delegates with `include_usage=false`. Because of
  `skip_serializing_if`, the legacy wire bytes are unchanged, and a test asserts that the opted-in
  request differs only by `stream_options`. `ChatStream::new` keeps `usage_limit=None`, so
  `collect_usage` is a no-op and legacy decoding is unchanged. With `with_usage`, the codec accepts
  one non-null usage, only after the finish reason. That can be on the finish chunk or on the
  existing usage-only empty-choices path. It refuses early reports and duplicates, requires three
  `u64`→`u32` counts (bools, floats, strings and negatives fail), a checked sum and
  `completion_tokens ≤ max_tokens`, and drops extra provider fields. `usage()` returns a value only
  when `ended && !failed`. `ended` is set only by a successful `end()`, and a later `feed` sets
  `failed`, which revokes the value (tested at every split point).
- Transport (`local_chat_transport.rs`): `chat_with_usage` runs the same `authorized(approval)` and
  `cancel.check()` before encoding. The body is `Zeroizing`, and the code shares `chat_encoded` with
  `chat`: same `request`, header framing, 4 MiB body bound, per-event cancellation and
  `codec.end()` then `wire.check()`. The function returns `ChatCompletion` only on the `Ok` path
  after both, with no retry. The socket test shows the wrong-endpoint approval refused with no
  connection, and a 400 status failing with no second connection. Truncated and cancelled streams
  return errors, a missing report gives `None`, and a valid report gives `Some`.
- API (`local-api/src/lib.rs`, `coding_repair_api.rs`): `include_usage` is `#[serde(default)]` on
  `deny_unknown_fields` structs. Defaults go through the original `chat` and emit the original
  events. Opt-in preflight runs the usage encoder before headers on `/v1/chat`, and before receipt
  consumption in repair (`prepare_repair` → `prepare_proposal_messages(..., include_usage)`
  precedes `consume_repair_feedback`). Disclosure, settings and endpoint staleness, created-source
  provenance and the single-use receipt are unchanged. `proposal_usage` attaches usage only when
  requested and the transport returned `Ok`: a strict-edit rejection or a length result keeps
  counts, while transport errors, cancellation and oversized output keep none. Oversized output
  cancels and the next `cancel.check()` fails the transport. A missing report serializes as
  `null`. A usage report never changes `applied:false`/`tested:false` or the strict checker.
- Recorder (`scripts/local_chat_smoke.py`): `--include-usage` is opt-in. Envelope keys must match
  exactly, counts must be `int` (not `bool`) in `0..2^32-1` with a matching sum and completion
  ≤ 1024, and an unrequested usage envelope fails. The aggregate is produced only when every turn
  completes with a non-null report. A failed second turn leaves `tokens: null` and only the
  completed first turn's counts. Without the flag the request and version-1 report shape remain;
  only the human `token_note` string changes.
- Claims: the guides and evidence consistently call counts untrusted provider statements, not
  tokenizer, context, weight, resource or admission facts. No profile, coordinator or model-port
  file is in the diff. The historical pre-M1 run is labelled historical.
- Privacy, IP and integrity: new prose and code contain no private host path, username, hostname,
  credential, personal data, sibling-project name or trademark branding. The `/lane/...` paths and
  reviewer model name occur only inside the byte-identical retained report, as in earlier retained
  reports. No dependency, lockfile, SBOM, evaluation input, hidden or held-out test, threshold,
  ignore, prompt or score changes. Only the T-303 and T-306 ledger lines change, both statuses stay
  `[ ]`, and no row or sub-row is added.

## Findings

No critical, high or medium findings.

**L2 (low, backlog): a strict usage check can discard an otherwise valid opted-in answer.**
`platforms/linux-inference/src/local_chat.rs:274-276` treats a provider whose `total_tokens` is
not exactly `prompt + completion`, or which reports `completion_tokens` above the request ceiling,
as a protocol failure of the whole stream. The visible answer is then partial. This is documented
and conservative, and it only applies after an explicit opt-in. A future option could record the
report as invalid without failing the text.

The existing backlog lows (L1 creation wording, lifecycle/continuation, factory allocation,
standard-library shadowing, terminal status/owner snapshot consistency) are unchanged.
