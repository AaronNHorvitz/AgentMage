## Code review

- **Line expansion (`coding_proposal.rs:236-246`).** Parser ranges are already validated as char-boundary slices
  (`get(start..end)`). `rfind('\n') + 1` and `find('\n') + end + 1` land on ASCII byte boundaries. `end >= 1` holds
  because `start < end`. CRLF is covered because `\r` precedes `\n`. Content before the definition on the same line
  is included verbatim. That is exact source, not invention.
- **Merge (`:317-354`).** The containment skip, then a single ordered pass that absorbs every same-path excerpt
  overlapping or touching the growing range, keeps excerpts disjoint and nonadjacent. Excerpts before the absorbed
  one cannot become touching, because the invariant gives `end_j < start_i`. My randomized check confirmed this.
  The merged text is `content[start..end]`, so no gap bytes are invented. The 64-excerpt cap, the 2048-candidate cap
  and the serialized byte ceiling (`proposed.len() + instruction <= max`) are applied to the whole proposed set
  before acceptance. A candidate that does not fit leaves the previous set untouched. Visibility only grows.
  - Removing the early `break` at 64 means up to 2048 clone, sort and serialize passes of at most 32 KiB. The work is
    bounded and small.
- **Checker.** From `struct ModelProposal` to end of file, the code is byte-identical to d31: the SHA-256 of that
  region is 119eff1d… on both sides. No normalization, fuzzy matching or repair was added. Path validity, the
  edit-must-lie-inside-one-excerpt rule, uniqueness, overlap and stale-digest refusals are unchanged.
- **Instruction.** The fixed constant gained generic exact-whitespace, distinguishing-context and "new must differ"
