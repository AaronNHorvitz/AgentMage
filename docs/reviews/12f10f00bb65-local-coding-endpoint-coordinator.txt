## Assessment

The parts below hold.

- **No second loop.** Endpoint turns go through `run_until_boundary_impl` and
  `advance_until_boundary`, which native-check.py proves mechanically unchanged. There is no nested
  `RuntimeEndpointTurns` and no second orchestration loop.
- **Sealed request.** `CoordinatorRequest` keeps the original sealed request private, and its common
  fields are exposed only through `Deref`, so they are read-only. Every persistence, correctness,
  research and artifact hook still requires `native()?` and refuses endpoint runs. Native admission
  keeps the exact profile and binding checks and the `ModelBinding` category. An endpoint request
  requires EphemeralReadOnly, no cursor, an equal model binding and a port with no native side.
- **Shared clock and ledger.** One clock and `RuntimePhaseControl` bound both preparation and
  dispatch. Input, call, output and time envelopes are checked against a clone before any spend.
  Actual input and calls are spent after `ModelRequested`, and are rolled back only when the phase
  reports zero dispatch attempts. Single use is latched by `RuntimeEndpointModelPhase::execute`,
  which also re-checks `port.request()` against the admitted descriptor.
- **Tool calls.** Model tool calls go through the unchanged `is_model_proposable`, `request_tool`,
  attempt guard, permission challenge and scoped boundary. No production boundary implements endpoint
  scopes, and default `*_scoped` refuses before any legacy entry. So no real workspace tool can run
  under endpoint composition yet, and the evidence honestly records that native tool authority
  remains open.
- **Completion.** Completion builds this coordinator's own `VerifierRegistry` from the current task,
  claim, repository, state revision and postconditions, and passes its own results, receipts and
  evidence.
- **Terminal and accessors.** The terminal seals the whole endpoint envelope. `outcome()` is `None`
  for endpoint instances, and `endpoint_outcome()` requires terminal publication. Native advancement
  refuses endpoint instances and the endpoint method refuses native ones. Errors latch
  `correctness_reconciliation_required`.
- **Rows and claims.** No row is added or closed, no row only adds plans, and there is no score or
  product comparison. Synthetic tests are labelled as synthetic.

## Findings

### M1 (medium, untrusted model output): a bad argument envelope leaves the run without a terminal

**Where.** `kernel/engine/src/runtime_loop/coordinator_endpoint.rs:542-568` passes the parsed
`EndpointToolProposal` arguments straight into `request_tool`. There,
`kernel/engine/src/runtime_loop.rs:3289-3292` maps any `validate_argument_envelope` failure to
`RuntimeLoopError::InvalidBoundaryResult`. `ToolRegistry::validate_argument_envelope` and
`validate_call_shape` (`kernel/engine/src/tooling.rs:218-239, 617-660`) fail on a schema mismatch, a
non-JSON media type, oversize bytes or a wrong digest. The new test codifies the behaviour:
`runtime_loop_endpoint_coordinator_tests.rs:720-724` asserts `is_err()` twice.

**Why it matters.** In the native path, a trusted family decoder builds `ClosedModelProposal`, so the
model never authors the envelope. Envelope errors there really are boundary faults, and schema-invalid
arguments get a correctable `ArgumentsInvalid` rejection. In the endpoint path, the untrusted
response text itself supplies `arguments.{schema, media_type, bytes, sha256}`. Any model output, or
document or web content the model repeats, can name an offered tool with a wrong digest or schema.
That turns an ordinary model mistake into an engine-fault error. The turn is left open, no
RunTerminal is published and the envelope is never available. An ephemeral endpoint run has no
reconciliation path, so the run is simply dead with no canonical record.

**Reachability.** A real model cannot reasonably compute SHA-256 over a byte array it must also emit
as JSON integers. So on a real endpoint this is the most likely result of any tool attempt. The
guide's claim that the coordinator "checks the offered registry and argument envelope" holds only in
the fail-closed sense.

**What is not affected.** No effect occurs (0 executions), so this is not a confinement escape.

**Reproduction.** Run the existing `endpoint_coordinator_denial_and_malformed_tool_never_execute`
test, or my `review_probe_model_controlled_envelope_errors` probe above.

**Concrete fix.** In `run_endpoint_turn`, after the `is_model_proposable` check and before
`request_tool`, give model-authored envelope defects a canonical refusal.

- Preferred: have the model supply only a JSON `arguments` value. The coordinator then builds the
  `ContractPayload` itself from the registered definition's `input_schema`, `application/json`, the
  exact bytes and its own SHA-256. That makes the envelope coordinator-owned and inert, and real
  models can reach it.
- At minimum: compare the supplied schema with the definition's `input_schema` and check the media
  type, size and digest. On failure, call
  `finish_refused_proposal(&turn_id, "runtime.proposal.arguments-envelope-invalid")`, or reuse the
  correctable `ArgumentsInvalid` rejection.

Change the test to require a terminal non-success `RuntimeEndpointOutcome` whose RunTerminal hashes
the whole envelope, with 0 executions and no further dispatch. Keep `InvalidBoundaryResult` for
genuine trusted-port faults.

### L1 (low, backlog): `RuntimeCoordinatorModelPort` is public and unsealed

`coordinator_endpoint.rs:112-130`. Previously `M: RuntimeModelPort` meant the exact-profile check in
`compose` and the dispatch in `run_turn` used the same object by construction. Now an external
implementer can return different objects from `native()`, which is checked at `runtime_loop.rs:1816`,
and `native_mut()`, which is used at `runtime_loop.rs:2513, 2670`. The composer is trusted, so this
is a weakened type-level guarantee rather than an exploitable boundary.

Fix: seal the trait with a private supertrait, so that only the blanket native impl and
`RuntimeEndpointDriver<P>` exist.

### L2 (low, backlog): endpoint read-only catalog refusal is not tested directly

The ten new tests cover non-read-only modes and catalog drift, but not a write, command or network
tool inside an otherwise exact EphemeralReadOnly endpoint catalog. Refusal currently rests on the
shared `catalog_admitted`; my probe confirms `ToolCatalogBinding` for all three. Fix: add that case
to `endpoint_coordinator_refuses_authority_modes_catalog_drift_and_native_entry`.

Predecessor low L1 (pure framing sees supplied counts) remains backlog; the guide now states the
limit.
