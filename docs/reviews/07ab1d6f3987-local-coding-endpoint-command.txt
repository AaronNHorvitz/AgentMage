## Assessment against the request

- **Binding.** `into_endpoint_command` (`coding_repository_endpoint_command.rs:105-203`) binds all of
  the following, and returns the original owner unchanged on refusal:
  - the verified sealed request, ControlledWrite mode, no cursor;
  - the workspace ID and the exact one-tool catalog;
  - the held-root and creation-receipt pins;
  - `issued == None`;
  - canonical call bytes, hash, schema and media type;
  - the run-derived action ID.

  Memory, process count and timeout must fit the sealed request, and a missing budget counts as 0,
  which fails closed.
- **Issue and consume.** `ExactEffect::issue` and `IssuedExactEffect::execute`
  (`coding_repository.rs:611-792`) are a pure split of the previous single path:
  - direct commands and worktree creation call `issue(..)?.execute(..)` with identical inputs;
  - the issued state is private and non-Clone, and lives only in `PendingCommand`;
  - nothing reconstructs it from wire data;
  - execution re-checks the grant's time window and updates only `context.now_epoch_ms`;
  - network, credential and publication scopes stay `deny_all`.
- **Stage discipline.**
  - Every matching call sets `Spent` before control, clock, owner or preflight dependencies.
  - Mismatched scope, definition, call, challenge or response returns before the stage changes.
  - Narrow refuses.
  - Deny consumes the pending command without dispatch and spends no attempt.
  - After Allow, `issued.grant_id == proposed_grant_id`, and `authority_sha256` is the canonical
    digest of the issued grant.
- **Dispatch.** Execution follows this order:
  1. re-checks the clock and `now >= resolved_at`, plus held root, creation receipt and deadline;
  2. takes the pending command, then makes a pre-dispatch cancellation observation;
  3. calls `native_executor` again for the public path;
  4. passes through `run_command_observed`, which consumes the validation attempt and then the issued
     grant through the original driver.

  The native manifest, sandbox and offline worker are unchanged. Command output is retained in
  `last_result`. Output over `max_output_bytes` returns Uncertain and is never re-dispatched.
- **Cancellation bridge.** `CommandControl` turns the original control's Cancelled or TimedOut into
  the command's attempt-scoped signal, with `DeadlineReached` kept for TimedOut. Unavailable and
  Invalid fail closed. A probe signal whose task or correlation does not match returns
  ScopeMismatch. The kernel driver turns any observation error into `CancellationUnavailable` before
  launch.
- **Prompt injection.** Command output is untrusted, response-only data. After one use the boundary
  is `Spent`, so any tool call proposed later by the model, including one injected through command
  output, gets `Invalid`. The catalog has exactly one operation. The test-only preflight and executor
  seams are private methods and have no production hook.

- **Honest labelling.** The creation, endpoint and command observations are labelled SYNTHETIC in the

## Findings

No critical, high or medium findings.

- **L1 (low).** A cancellation handle obtained before handoff is silently disconnected.
  - **Where:** `coding_repository_endpoint_command.rs:422`.
  - **What happens:** `execute_using` creates a new token with
    `LinuxCodingCommandCancellation::for_pending(&pending)`. A handle the caller obtained earlier
    from the public `command_cancellation(digest)` has the same attempt ID but a different token. Its
    `cancel()` returns Ok, yet the command still dispatches (probe 4).
  - **Why it is only low:** no claim covers that handle. The `command_cancellation` docs say a handle
    connects only through `decide_*_with_cancellation`, and the documented endpoint stop paths (run
    control and probe) work.
  - **Wording issue:** the evidence phrase "through the command's attempt-scoped cancellation handle"
    could be read as covering this handle.
  - **Fix:** do one of the following:
    - accept an optional `&LinuxCodingCommandCancellation` in `into_boundary`, verify it with
      `verify_command_cancellation`, and reuse its token in the bridge;
    - make `command_cancellation` refuse once `issued` is Some or the owner has been handed off, and
      document in the guide that pre-handoff handles are not connected.
- **L2 (low).** The output, CPU and disk ceilings are not checked before dispatch.
  - **Where:** `coding_repository_endpoint_command.rs:146-162`.
  - **What happens:** construction checks memory, task count and timeout against the sealed request.
    It does not check `max_output_bytes` against the fixed projection overhead (about 2.8 KB with
    empty output, per probe 5) plus `stdout_bytes + stderr_bytes`. It also does not check CPU or
    `DiskBytes`. A sealed run with a small output budget can therefore be approved and dispatch a
    real offline process whose result is certain to be refused as Uncertain.
  - **Why it is only low:** this fails closed with no confinement impact, and the
    post-dispatch-refusal behaviour is documented.
  - **Fix:** refuse at construction when `stdout_bytes + stderr_bytes + a fixed projection allowance`
    exceeds `request.limits.max_output_bytes`, and add a test case.

The predecessor's L1 and L2 remain backlog as stated. I saw nothing new on them: errors before
dispatch still map conservatively to Uncertain (`execute_using`, line 445).
