## Findings

No critical, high or medium findings.

**L1 (low, backlog): concurrent cancel can collide with the passive `try_lock` poll and surface as
`cancellation-unavailable` instead of `cancelled`; the new live test can flake for the same reason.**
`EffectCancellationObservation for CancellationToken` (kernel/engine/src/propagation.rs, `try_lock` in
`observe_effect_cancellation`) returns `Unavailable` if another thread holds the node mutex.
`LinuxCodingCommandCancellation::request` (platforms/linux/src/coding_repository_command.rs:47-64) locks that
mutex twice inside `CancellationToken::cancel`. Before this batch the command token was never signalled
concurrently; `/v1/cancel` and shutdown now do so while the supervisor polls
(sandbox_supervision.rs:668 and 698, `is_cancelled()?`). On a collision the run ends through the existing
fail-closed path (`CommandExecutionFailure::CancellationUnavailable`, `failed_command_effect`). The child is
still terminated by the existing cleanup path, the attempt is spent and nothing passes, so this is safe, but the
person sees a "cancellation unavailable" failure rather than a cancelled receipt. The new synthetic executor in
`coding_repository_command_tests.rs` (`CancelDuringExecution::execute`, the `observe_effect_cancellation().unwrap()`
loop) polls the same way while another thread calls `shutdown()`/`cancel()`, so a collision would panic the test.
The window is microseconds against a 1 ms poll, so this is rare but not impossible. Fix: give the command handle
an observer that retries `try_lock` a bounded number of times before reporting `Unavailable`, or have the
synthetic test tolerate `Err(Unavailable)` by retrying. In either case, document that a collision fails closed.

**L2 (low, backlog): the client token can now cancel a control-approved command or validation and spend one of
its three attempts.** `/v1/cancel` keeps its "client or control" authentication (`lib.rs`, `("POST", "/v1/cancel")`;
documented in `docs/guides/local-chat-api.md:84`). With `active_command` armed, an ordinary conversation-client
token holder can now interrupt an approved validation. That spends an attempt (`MAX_ATTEMPTS = 3`,
coding_repository_validation.rs:41), and repeating it exhausts the series and forces a new worktree.
Cancellation is fail-safe and the permission model stays visible, but this widens what the lower-privilege
token can affect, and the guide does not state it. Fix: either require the control token to cancel
control-approved effects, or state the cross-token reach explicitly in coding-commands.md and local-chat-api.md.

**L3 (low, backlog): one stale sentence in the repair guide.** `docs/guides/coding-model-repair.md:110-115` says
native command cancellation is "now connected", then lists "cancellation during native effects" as remaining
open. Fix: say "cancellation of worktree creation and write effects" (the non-interruptible ones) or remove it.

The retained earlier lows stay open as backlog, unchanged by this batch: 33cd39e2 L1 exact repair-message
pre-encoding; native positive HTTP admission and child termination (still not demonstrable here, and the new
API latch in `arm_command_cancellation` is therefore exercised only by reasoning and the State-level unit tests,
not by a positive HTTP run); shared error prefixes; refused-edit latest-result; the same-user window; and
unsupported runner and compile-failure retries.
