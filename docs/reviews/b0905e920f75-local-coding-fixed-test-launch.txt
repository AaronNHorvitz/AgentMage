## Review findings by area

- `Validation` is a private struct under `deny_unknown_fields`. It is read
  only from the private launch file through the existing `private_bytes`
  reader (no alias, mode check). `CodingEndpointValidation` has no
  `Deserialize`, so no HTTP or model path can construct it.
- `into_native` runs `CommandSpec::verify`. This re-checks the shape
  (`grant_required`, `!interactive`, `!network`, `!inherit_environment`,
  environment allowlist `LANG/LC_ALL/NO_COLOR/TZ`, prohibited shell
  executable names, bounds) and the canonical digest. It also requires
  `OwnedWorktree`, a test kind and a positive minimum, and rejects
  `ProcessExitV1`.
- The order inside the factory is correct:
  `load → prepare (catalog/kind) → into_native → ApprovalInput → LinuxCodingRepository::open/prepare`.
  So refusal happens before any state write or native inspection. The
  executable test confirms this for `minimum_test_count: 0`: no
  `code.endpoint.edit-startup` stderr, empty state and owned directories, and
  no model connection.
- Exact combined-catalog enforcement holds at two layers: `prepare` with
  `EditAndTest` (tested by the wrong-catalog case) and the predecessor
  `new_inner` `visible_tools` equality.
- Native executable trust, manifest and resource admission, per-test exact
  approval, the stdin creation decision and delayed credential reads are
  unchanged.
- The legacy edit-only path refuses any `validation` key, including `null`.
  The `as_object().unwrap()` cannot panic, because a non-object top level has
  already been refused by the `shape["request"].is_object()` check and by
