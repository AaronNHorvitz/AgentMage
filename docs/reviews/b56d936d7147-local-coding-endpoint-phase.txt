## Source review

- **Phase framing before consent.** `prepare_endpoint_coding_proposal` (lib.rs:1082) builds
  `RuntimeEndpointModelPhase::new` from the transport-produced binding. On the repair route it is called
  inside `prepare_repair` (coding_repair_api.rs:143), and `admit_repair_proposal` only runs `consume()` after
  `prepared?` succeeds (coding_repair_api.rs:98-104). A framing refusal therefore cannot spend the receipt.
  Confirmed.
- **No new destination or rebuild.** The closure calls the same `request.execute_recorded_controlled(&op.cancel,
  control, display_text)` on the originally prepared `PreparedEndpointChat`. No credential, endpoint, tool,
  write, retry or native profile is added. The phase owns only a cloned `EndpointModelRequest` descriptor.
  Confinement surfaces (workspace writes, command sandbox, network enablement) are not touched by this diff.
  For that reason I ran no new path-traversal, symlink or environment-leak attempts. The only network
  effect is the pre-existing single dispatch to the already approved endpoint.
- **Single use.** `attempted` latches before any control or dependency observation (endpoint.rs:87-89).
  Re-entry returns ResourceExhausted without calling the port (tested for success, pre-stop,
  post-stop and dependency-failure paths).
- **Result checks.** The whole request must be equal: selection, context, body and limits (derived
  PartialEq on the contract struct). The text hash must be well-formed, and elapsed time must be at most
  total_timeout. Output and elapsed budgets are consumed on a cloned ledger and committed only after both
  succeed (endpoint.rs:117-127), and the tests assert zero durable output/elapsed after a refusal. The
  rounded elapsed time cannot exceed the ceil(total) budget, so the elapsed refusal can only come from the
  explicit `>` check.
- **Ledger constructor.** `for_endpoint_model` sets zero ceilings for events, artifacts, retries, denials
  and parser failures, and refuses zero input, output or elapsed budgets. The test confirms that
  `admit_event`, `admit_artifact` and `record_retry` refuse.
- **Error codes.** `runtime.model.result_invalid`, `runtime.budget.exhausted` and `model.operation.*` are
  existing stable codes (runtime_event.rs:2025-2026, runtime_hardening.rs:59, model.rs:590-595). Transport
  errors keep their own codes.
- **Usage honesty.** `RuntimeEndpointPhaseUsage` exposes no token or memory fields. The completed text and
  time fields are `Option` and are null unless `completed`. The API helper asserts no `input_tokens` or
  `peak_memory_bytes` and null completed fields on partial, malformed, late and cancelled terminals
