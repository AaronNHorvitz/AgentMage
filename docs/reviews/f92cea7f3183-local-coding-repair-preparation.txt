## Review of the change

Ordering and single use (`platforms/local-api/src/coding_repair_api.rs:65-86`, `:92-103`, `:105-157`):

- `prepare_repair` runs all of the following before anything can be consumed:
  - the disclosure, settings, scope and receipt-identity checks;
  - `workspace_sources` and `select_created_sources`;
  - `repair_prompt` and `prepare_coding_proposal`;
  - `prepare_endpoint_coding_proposal`, which contains message validation, the token range
    (`1..=4096`), the full encoder and `prepare_chat`'s exact-approval check.
- Only on `Ok` does `admit_repair_proposal` look at the cancelled/stop flag. That flag is evaluated after
  preparation returns, because arguments are evaluated in order.
- Only after that does it call `consume_repair_feedback`. A consumption error drops the prepared request
  and produces a 409.
- The same `PreparedCodingProposal` then goes to `dispatch_coding_proposal`. Nothing rebuilds the context,
  the messages or the body after consumption. `PreparedEndpointChat` has no Clone or Debug, and `execute`
  takes `self`, so the request can run once only.
- `execute` rechecks cancellation before connecting (`local_chat_transport.rs:286-301`). So the guide's
  statement that late cancellation spends the attempt but opens no connection holds.

Credential and approval binding:

- The prepared request borrows the `Configuration` Arc obtained by `begin_controlled`.
- The settings-revision/endpoint check compares against that same Arc. So the approval checked, the
  credential used and the endpoint compared are one object.
- This is slightly stronger than the predecessor, which re-derived the request from the Arc after
  consumption.

Shared path (`platforms/local-api/src/lib.rs:1000-1077`):

- Snapshot and workspace proposals go through the same `prepare_endpoint_coding_proposal` and
  `dispatch_coding_proposal`.
- Status and refusal ordering is unchanged: message validation gives 400, then a missing endpoint gives
  428, then transport preparation gives 400 with the code only in the outcome.
- `message_bytes` is computed exactly as before and is only emitted when feedback is present.
- The repair fixture checks it against the sum of the actually received message bytes.

Tests:

- The refusal test uses a nonblocking listener and a final `accept()` → `WouldBlock`. It covers:
  - missing endpoint, approval mismatch, and 0 and 4097 tokens;
  - pre-consumption cancellation;
  - a stale receipt after successful preparation.
  The callback is never called, and no connection is made.
- The dispatch test covers two cases and makes no second connection in either:
  - In the backend-503 case, the upstream asserts exactly one consumption before it reads the request.
  - In the late-cancellation case, no connection is accepted.
  Both terminals are `error` events with `response_complete:false`, no `token_accounting` and no proposal,
  and their `model_binding` equals the binding in the context event.
- Both API fixtures now hash the raw received body bytes. These are `incoming()` in `local_chat_api.rs`,
  which reads exactly Content-Length bytes, and the repair fixture's `read_exact`. The tests compare those
  hashes with `request_body_sha256`. This addresses endpoint-binding L1.
- The four-case repair fixture (valid/invalid edit × usage on/off) keeps the strict edit, usage and
  accounting assertions.

Guide wording:

- I checked `docs/guides/coding-proposals.md` against `dispatch_coding_proposal`. A `Length` finish or an
  invalid edit gives `completion = Some`, so `token_accounting` is present while the error carries
  `partial:true`. Transport errors and cancellation give `None`, so it is absent. The L2 clarification is
  accurate.
- `docs/guides/coding-model-repair.md` matches the code ordering described above.

Integrity, licences and privacy:

- No hidden, held-out, scorer, threshold, ignore, SBOM, status or ledger-row edits. audit.py verified the
  ledger rows are unchanged.
- No dependency or version change beyond a dev-only use of an already pinned workspace crate.
- Added lines contain no private host path, username, hostname, credential, personal data or trademark

- The evidence labels the consumption callback as synthetic and claims no native receipt, route admission,
