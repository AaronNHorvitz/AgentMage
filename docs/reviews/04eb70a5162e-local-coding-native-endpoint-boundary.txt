## Analysis

**Authority path**

- `approve` (`coding_workspace_write.rs:324-365`) issues the grant through the original
  `issue_write_grant`. It refuses to replace an existing grant. It is `pub(crate)`, and its
  only callers are `resolve_scoped` and `execute`.
- `execute` (`:367-399`) now also checks root, change-set and preview digests before using the
  stored or freshly issued grant. This is stricter than the predecessor. Consumption still goes
  through `execute_write_transaction`, which revalidates and consumes before applying.
- Public `apply` still issues and consumes in one call.
- No grant is built from wire metadata. The Allow evaluation's `grant_id` and
  `authority_sha256` come from the real `WriteApprovalReceipt` (`boundary.rs:213-227`).

**Stage machine**

- Every scoped entry first runs `check()`, which requires the exact sealed request,
  definition and call. Native-family methods return `Invalid`.
- Matching entries set `Stage::Spent` before `running()`, `current()`, native calls or the
  clock (`boundary.rs:147`, `180-181`, `255`). So a stop, error or unwind cannot reopen a stage.
- `Narrow` is refused while the stage stays inert. Converting an already-spent direct handle
  yields `Stage::Spent` (`:49-53`).

**Pre-dispatch checks** (`boundary.rs:256-277`)

- original control;
- cancellation probe: a matching signal gives `Cancelled`, a foreign one gives `Invalid`, an
  error gives `Unavailable`;
- trusted clock not earlier than `resolved_at`;
- `current()`: creation time, challenge expiry, exact pending preview, edit scope and
  creation receipt;
- control again.

Dispatch then goes through the original `decide_edit`, which keeps its own expiry, scope and
receipt checks.

**Result projection**

- The receipt digest is the real last chain entry. `transaction:sequence` is descriptive only.
- The output budget is checked after the write and returns `Uncertain`.
- The coordinator validators accept Succeeded/Changed and Uncertain/Uncertain for
  `WorkspaceWrite` in ControlledWrite (`runtime_loop.rs:6302-6313`).

## Findings

No critical, high or medium findings.

- **L1, low, test coverage.** `platforms/linux/src/coding_repository_endpoint_boundary.rs:335-341`.
  - **Problem:** `project()` maps native `failed_no_change`/`restored` to Failed/NotChanged
    and native `uncertain` to Uncertain/Uncertain. The decision and evidence say known
    reconciled failures and uncertain outcomes "keep their native state semantics", but no
    test exercises either branch. All nine methods reach only `committed`, pre-dispatch
    refusals, or output refusal after commit.
  - **Untested risk:** a Failed result carrying `output: Some` and `evidence` is accepted by
    the coordinator's `complete_tool` path. Nothing in this increment shows that.
  - **Fix:** add a fault-injecting atomic driver (or a recorded native value) for
    KnownFailure with and without applied operations, and for an Uncertain report. Route it
    through `execute_scoped` and the coordinator, and assert the projected outcome and
    state_change plus coordinator acceptance.
- **L2, low, failure classification.**
  - **Location:** `boundary.rs:281-285` together with `write_transaction.rs:357-363`.
  - **Problem:** some native refusals happen before the grant is consumed, so nothing is
    written. Examples are preimage drift caught by `revalidate_before_apply` and the
    monotonic `Instant` deadline in `LinuxCodingPendingWrite::execute`. These still come back
    as `RuntimePortFailure::Uncertain`, and the native record reads "effect unknown". That is
    conservative and safe: there is no replay and the result is never presented as no-effect.
  - **Test gap:** the preimage, symlink and root drift test (`boundary_tests.rs:371-412`)
    asserts only `is_err()`. It does not record which failure class or native record is
    produced, so the behaviour is undocumented.
  - **Fix:** assert the returned class and the native `latest` record in that test, and note
    in the guide that pre-consumption refusals are reported as uncertain.
