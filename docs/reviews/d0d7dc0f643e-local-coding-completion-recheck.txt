## Analysis

- **Placement:** In `coordinator_endpoint.rs`, the hook runs after these steps, in order:
  - resource accounting and `ModelCompleted`
  - the `finish == Stop` check and the stop-before-phase check
  - completion-only tool-shape refusal and the `tool_call` refusal
  - the new closed-JSON guard (line ~835)
  - `OwnedEndpointClaim::claim`

  It runs before the Approval/Execution/Verification transitions and before `VerifierRegistry` is
  built. It is a single-use `FnOnce` and is dropped on every earlier exit. This matches the claim.
- **Control:** The coordinator checks its control before and after the callback (the post-check is
  unconditional). The host callback checks both the coordinator control and the original continuous
  `state.control`, before and after `check_completion_validation`. A control failure wins over a
  validation refusal inside the host callback. If the callback refuses while the coordinator is
  stopped, the result is a typed model failure, the same precedence as the existing
  tool-preparation path. Kernel mode 3 asserts this as `runtime.port.invalid`.
- **Who installs the hook:** Only trusted port code installs it. Production installs it at
  `coding_endpoint_edit_generation.rs:196-197` for `Next::Completion`, and that turn is
  `completion_only()`. Model text and wire fields cannot select it or skip it. The closed-JSON
  narrowing is gated on `completion_check.is_some()`, which is trusted state.
- **What the callback reads:** The callback holds only `Arc<Mutex<State>>`. It requires
  `Next::Completion`, `Owner::Ready`, and the existing `check_completion_validation`. It sends no
  new bytes to the model, creates no grant and changes no verifier. Both verification flags and
  verifiers are untouched in the diff.
- **Confinement:** No change to write confinement, the sandbox, network, approvals or push. The

  model or scoreboard file. check.py also confirms that TASKS row lines are unchanged.
