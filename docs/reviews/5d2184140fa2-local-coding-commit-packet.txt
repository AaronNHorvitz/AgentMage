## What holds

- **Exact content.** `Prepared::new` re-runs `verify_local_commit_plan`. It requires matching
  parent and tree widths and a 40-hex v4 fingerprint, and refuses timestamps outside `u32` (so
  negative times or times past 2106 are refused, not truncated). The message is inserted verbatim,
  with no added newline and no CR normalization. The installed-Git comparison test covers both
  formats with a missing final newline, trailing blank lines, CR and Unicode. The kernel validator
  forbids control characters in names and the local part, and a restricted domain charset, so the
  first `\n\n` is always the header/body separator.
- **Signature format.** The header bytes, hashed area, trailer and left-16 bits are correct. The
  digest covers content, hashed metadata and the v4 trailer, with no Git object framing. The
  signing primitive sends `SETHASH 8` (SHA-256) with this complete digest.
- **Strict parsing.** There is exactly one prefix, `(7:sig-val(3:rsa(1:s`. The decimal length has
  no leading zeros and at most 4 digits, and is bounded by 1,024. The value must be followed by
  exactly `)))`, with no trailing bytes. eddsa, a second `s` and `extra` are refused, and every
  truncation is refused. Apart from the leading-zero issue below, the parser never reinterprets
  input or reads out of bounds.
- **Mandatory verification.** `sign_commit_with` checks control before work, after signing and
  after verification. It checks the plan signer against the pinned signer and the public-export
  hash, reconstructs content through `split_signed_commit`, and compares it byte-for-byte with the
  prepared content. Only then does it call the public-only verifier (`run_owned`, no
  repository/keyring/socket projection, `--trust-model always` over the sealed public export).
  Identity comes from a single `VALIDSIG` whose field 1 equals the pinned full signing fingerprint.
  The issuer key ID sits in the unhashed area and is advisory. The tests check that a sign error,
  invalid expression, verify failure, cancellation at every stage, an expired deadline, a changed
  public key and a changed signer all return errors. They also check that `CleanupUncertain`
  survives unchanged, and that verification is never skipped. A deadline cap of 30 s covers both
  stages.
- **Real cryptography.** The disposable RSA primary/subkey test signs and verifies both object
  formats. Changed content and a flipped scalar bit fail, and a different fingerprint fails
  `verify_signature_status`. The labelling is honest: synthetic artifact/plan authority and direct
  component processes, with no native admission, approval or object write.
- **Dormancy.** `packet::sign_commit` has no caller outside its module and tests. No route,
  approval, object write or push is added, and the direct signed-creation adapter is unchanged.
  `fixture_sign` is `#[cfg(test)]` and writes only a disposable key into a temporary home.
- **Public content and IP.** The diff contains no private host path, username, hostname, credential
  or trademark branding. The `/lane/...` bundle paths are lab paths, as in earlier accepted
  increments. The RFC citation names the public specification and incorporates no prose or code.

## Findings

### M-1 (medium, correctness): the RSA parser refuses valid agent signatures that start with a zero octet

- **Location:** `platforms/linux/src/local_commit_packet.rs:125-128` (comment) and `:152`
  (`(scalar[0] != 0).then_some(scalar)`). The tests enshrine this:
  `local_commit_packet_tests.rs:205` asserts that `[0, 128]` and `[0, 255]` are refused. The
  evidence file (paragraph "An earlier focused run…") and the code comment state that the agent
  "emits unsigned RSA scalars without sign padding" and that refusing "redundant leading zeros"
  matches the observed form.
- **Reproduction:** experiment 1 above. The installed foreground agent's RSA `s` is always exactly
  modulus-width (256 octets for rsa2048, in 3,000 of 3,000 signatures). Whenever the signature
  integer is below 2^2040, the first octet is 0x00, which happened in 8 of 3,000 (≈0.27%). For such
  output, `rsa_scalar` returns `None`, so `assemble` fails and `sign_commit` returns
  `PlanDenied` for a correct signature over a valid plan. In production, about one approved signing
  attempt in roughly 250–400 fails non-deterministically, with an error class that blames the plan.
  The disposable test signs 4 times per run, so it fails about 1% of runs, which makes the
  "all six new methods pass" claim intermittently unreproducible. The builder's single probe
  sample (256 octets, first octet 0x9A) does not distinguish "minimal" from "fixed-width". The
  evidence's description of the agent's form is wrong.
- **Impact:** fail-closed, so not a confinement or authenticity break. It is a correctness and
  reliability defect in the exact function this increment introduces, and the evidence makes a
  false claim about the behaviour of the external tool.
- **Fix:** accept leading 0x00 octets, bounded by `MAX_RSA_BYTES`, and preferably also require
  `length` to equal the modulus octet length of the pinned public key, or be no greater than it.
  Strip the leading zeros before computing the MPI bit count and body, because the MPI must be
  minimal. Still refuse an all-zero scalar and an empty length. Change the
  `[0, 128]`/`[0, 255]` cases at tests:205 to expect stripping. Add a deterministic test that a
  `[0, 0x80, …]` expression assembles to the same packet as `[0x80, …]`. Make the disposable test
  sign enough digests to cover a zero first octet, or inject one captured zero-led expression and
  verify it with the real verifier. Correct the code comment and the evidence wording.

### L-3 (low, backlog, same row): identities Git would refuse or normalize are assembled verbatim

- **Location:** `local_commit_packet.rs:49-63`, relying on `kernel/engine/src/local_commit.rs:1297`
  `valid_identity`.
- **Reasoning and reproduction:** experiment 3. The kernel validator accepts names containing `<`
  or `>`, names with leading or trailing whitespace, and `>` in the email local part. The assembler
  writes these verbatim, and the verifier's `verify_raw_commit` agrees, so a signature verifies. But
  Git refuses to write such an object, or (for whitespace and trailing punctuation) its own
  commit-tree would have produced different bytes. With no object write in this increment, the
  effect is a fail-closed refusal at the future write step.
- **Fix:** in the object-write increment, refuse identities containing `<`, `>`, or leading or
  trailing whitespace, either in the assembler or in `valid_identity`. Add one installed-Git
  `hash-object` acceptance test for assembled raw bytes.
