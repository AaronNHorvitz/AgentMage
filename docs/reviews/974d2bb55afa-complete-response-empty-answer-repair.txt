### L4 (low, error-code parity; backlog for T-309): null or missing `content` is classified differently by framing

- Location: `platforms/linux-inference/src/local_chat.rs:337` (`content: String`, so null or absent content fails serde
  with `ChatError::Protocol`). By contrast, the stream codec skips null content (577-584) and then returns
  `Incomplete` at `[DONE]`. My probe shows `complete null/missing content → Err(Chat(Protocol))` against
  `stream no-content → Err(Chat(Incomplete))`. Similarly, an empty complete answer with invalid usage reports
  `Incomplete`, whereas the stream codec would report `Protocol` at the usage event before `[DONE]`.
- Impact: both modes refuse, emit no text and publish no completion, so acceptance is identical and this does not
  reopen M1. Only the code differs (`chat.response.invalid` vs `chat.response.incomplete`). A scoreboard that
  classifies refusals by code could attribute the same backend behaviour to different causes across framings. The
  observed A4B backend sends `""`, not null.
- Fix (backlog): decode `content` as `Option<String>` and map `None`/`""` to `Incomplete`. Alternatively, have the
  collector group both codes as "no visible answer" when comparing framings. This can be folded in with L1.

L1 (null `error` key accepted; still reproduced), L2 (preflight-byte boundary) and L3 (buffer reallocations) are
unchanged and remain T-309 backlog, as the request states.
