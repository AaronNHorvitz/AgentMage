## Findings

### M1 (medium, correctness, claim vs evidence): positional evidence correlation contradicts the coordinator's sorted evidence, so the checker refuses every real run

- Location: `shells/host/src/coding_endpoint_fixed_test_verifier.rs:195` and `:237`
  (`input.evidence[index] != *evidence`). This conflicts with `kernel/engine/src/runtime_loop.rs:4176`
  (`self.evidence.sort_by(evidence_id)` after every admitted tool result).
- Mechanism: the native projections name evidence `native-edit:<digest32>`
  (`platforms/linux/src/coding_repository_endpoint_boundary.rs:382`) and `native-command:<digest32>`
  (`platforms/linux/src/coding_repository_endpoint_command.rs:802`). The coordinator passes its
  sorted `self.evidence` to `verify_completion`. Because `c` sorts before `e`, all command evidence
  precedes all edit evidence. The checker expects the evidence at index 0 to be the first edit's, but
  the coordinator always puts a command's evidence there. Every genuine 1–3-attempt history is
  therefore marked `Failed`.
- Why the tests pass: the fixture names evidence `evidence-call-N` and appends it in tool order
  without sorting. The coordinator probe runs `NoTools` and replaces every record with synthetic
  ones. No test feeds the checker evidence in the order the coordinator actually produces. The
  guide (`docs/guides/coding-validation.md`), the evidence note and TASKS.md say the checker
  "correlates every original attempt … with the coordinator's edit/test observations" and tell
  embedders to wire it through `previews.completion_verifier(verifier)`. On that surface it can
  never accept.
- Reproduction (scratch copy, not committed): I appended
  `reviewer_repro_coordinator_sorted_native_evidence` to the copied test file. It builds
  `Fixture::new(count)` for counts 1–3 and renames each evidence ID to the native form
  `native-{edit|command}:<first 32 hex of payload sha256>` in both `results[i].evidence[0]` and
  `f.evidence[i]`. It verifies once, then sorts `f.evidence` by `evidence_id` as the coordinator does
  and verifies again. The command was
  `CARGO_TARGET_DIR=/lane/state/review-target/repro-c27e2bee3611 CARGO_BUILD_JOBS=2 RUST_TEST_THREADS=4 bash /tools/build-slot cargo test --locked --offline -p agentmage-host --lib -- fixed_test_checker reviewer_repro --nocapture`,
  and the log is `/lane/state/tmp/review-repro-c27e2bee3611.log`. Output:
  - `REPRO count=1 … unsorted=Success coordinator_sorted=Failed`
  - `REPRO count=2 … unsorted=Success coordinator_sorted=Failed`
  - `REPRO count=3 … unsorted=Success coordinator_sorted=Failed`

  The five committed checker tests still pass in the same run.
- Impact: this fails closed, so there is no false acceptance and no confinement issue. However, the
  feature this batch delivers cannot accept any real coordinator run, and the claim that it
  correlates with the coordinator's records is not supported by any test using coordinator-shaped
  input. That is a correctness defect plus an evidence gap, so it is medium.
- Fix: keep positional correlation for tool results and receipt IDs, which the coordinator records in
  tool order. Correlate evidence by identity instead: require `input.evidence` to be exactly the set
  of `result.evidence[0]` values, with each result's evidence present by ID and byte-equal, and keep
  the existing uniqueness and length checks. Add a regression test whose records carry native-form
  evidence IDs sorted by `evidence_id`. Better still, obtain the records from the original
  coordinator through a synthetic tool boundary that returns native-projected edit/test results, so
  the input shape comes from the producer rather than the fixture. Correct the guide, evidence note
  and TASKS.md claim in the same batch.

### L1 (low, usability/honesty): the criterion shown to the person is an opaque digest

`coding_endpoint_fixed_test_verifier.rs:74-81` produces "Observe a complete passing offline test run
for fixed definition SHA-256 <hex> …". The guide tells the embedder to "Show `check.criterion()` to
the person". A digest does not let the person see which command, kind, parser or minimum count they
are approving. Fix: include the readable command, kind, parser and minimum in the criterion alongside
the digest, or have the guide require showing the definition next to the criterion. Backlog.
