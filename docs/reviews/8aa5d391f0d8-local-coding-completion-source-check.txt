## Review of the change

**Production guard placement (correct).** `CodingEndpointEditPreviews::next()` (`shells/host/src/coding_endpoint_edit_previews.rs:224-243`)
now calls `LinuxCodingRepository::check_completion_validation()` whenever `state.next == Next::Completion`. It checks
control before and after that call. `CodingEndpointStrictEdits::prepare` (`coding_endpoint_edit_generation.rs:121`)
calls `next()` before any connection use or framing. `prepare_coding_completion` has exactly one production caller,
the guarded `Next::Completion` arm at line 190. `Next` is internal process state, set only by `execute_scoped` after
a successful original command boundary (line 565). No HTTP or model field selects it or alters the source scope.
A refusal maps to `RuntimePortFailure::Invalid` before any socket use. The new host regression confirms this: zero
model calls, zero tool calls, no accepted connection, the file unchanged, and idempotent terminal events.

**Owner check (correct, typed).** `check_completion_validation` (`platforms/linux/src/coding_repository_validation.rs:116-146`)
does the following, in order:
1. `verify_created` revalidates the authority root, the held and owned descriptors and the root path hashes.
2. It refuses any pending command, edit or apply. These fields are the `Pending*` types; the retained `*_result`
   fields are separate.
3. It requires a series, a `latest` receipt and a final history attempt.
4. It requires `linked_pass_verified()`: attempts equal history length, and the kernel `verify_bounded_validation_history`
   checks every receipt, unique IDs, approvals and transactions, each rerun link, and that the last attempt is a full pass.
5. It requires `latest == final_attempt.validation`.
6. It calls `permits_completion_summary`, which requires all of: the binding's command receipt equals the final
   attempt's command receipt; the binding's sealed input equals that command's `sealed_workspace_input`; the sealed
   record agrees with the binding observation (root, digest, entry count, bytes); the binding's creation and validation
   receipts equal the current ones; and a fresh two-scan `WorkspaceObservation::capture` of the held root equals the
   retained observation.

All of this runs on private typed state; no inspection JSON is parsed. The fresh capture goes through the existing
confined adapter. It counts hidden files and refuses symlinks and replacement between the metadata and content reads.
It has a 2 s deadline and existing bounds. Nothing captured is returned or added to model context; the function
returns `Result<()>`.

**Confinement and escape attempts.** No new path, argument or untrusted input reaches this code. The only new file
access is the existing bounded observation of the already-held worktree. The platform matrix
(`completion_validation_refuses_missing_seals_pending_effects_and_changed_sources`) creates real files and refuses
each of these: a hidden `.config` added, a `tests/` file added, a 0600 mode change, an in-tree symlink, a pending
command, a changed creation receipt, and a legacy run without seals. In each case it checks that no extra dispatch
happens, attempts are preserved and the sentinel bytes are unchanged. The previously reviewed sealed-capture and
command sandbox are unchanged apart from the factored policy helper.

## Findings

No critical, high or medium finding.

### L1 — Low (claim accuracy): the evidence says the framing fixtures "do not bypass" the new check

- Where: `docs/evidence/t303-completion-source-check-2026-11-09.md` (host regression paragraph: "They do not bypass the
  production owner's new validation check or claim a native validation pass").
- Reasoning: `CompletionFramingFixture::prepare` (`shells/host/src/coding_endpoint_edit_cycle_tests.rs:113-141`) never
  calls `CodingEndpointEditPreviews::next()`, so these two tests do skip the check. The intended meaning is that
  production is not weakened, which is true. Coverage of the guarded positive completion path through
  `CodingEndpointStrictEdits` is now absent until a native binding exists.
- Fix: reword to "These fixtures intentionally skip the owner check, which only the production StrictEdits port
  performs; they do not weaken it or claim a native validation pass." Backlog, same row.

### L2 — Low (defence in depth): the completion framer is crate-visible without any proof of the check

- Where: `shells/host/src/coding_endpoint_edit_generation.rs:203` — `pub(super) fn prepare_coding_completion`. Its
  parent is the crate root, so the function is visible crate-wide.
- Reasoning: today there is exactly one production caller, and it is guarded. A future in-crate caller could frame a
  completion turn without the source check, and only a comment warns against that.
- Fix: have `next()` return a non-constructible readiness token for `Next::Completion` (for example,
  `CompletionReady(())` with a private constructor) and require it as a `prepare_coding_completion` parameter. The
  test fixture would then need an explicit `#[cfg(test)]` constructor. Backlog, same row.

### L3 — Low (test gap): some refusal clauses are only asserted as `is_err()` or not exercised

- Where: `platforms/linux/src/coding_repository_command_tests.rs` (the new matrix asserts `is_err()` only) and
  `coding_repository_validation_workspace.rs:57-66`.
- Gap: the matrix does not check per-case error codes, for example `pending-effect` versus `source-binding`. A pending
  edit or apply is not exercised; only a pending command is. The `command_receipt ==` and `sealed_input ==` equality
  clauses of `permits_completion_summary` have no isolated negative case. If any of them were dropped, only the other
  conjuncts would still catch the mismatch.
- Fix: assert the expected code per case, and add pending-edit and pending-apply cases if the fixture can stage them
  without widening fields. Backlog, same row.

Earlier low findings remain same-row backlog as recorded: dc5cb453 L1/L2, a5594787 L1 and 699e99 L1/L3. aabcbaa0 L1
and L2 are resolved by this commit.
