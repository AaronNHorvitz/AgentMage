- **Low L1 (backlog): preflight encoders ignore the configured mode and format.**
  platforms/local-api/src/lib.rs:1074-1077 (`prepare_proposal_messages`) and lib.rs:2095-2098
  (`/v1/chat`) check the size with `encode_chat`/`encode_chat_with_usage`, which always use Stream +
  Text. JSON-object mode adds 41 bytes (`,"response_format":{"type":"json_object"}`) under the
  256 KiB writer ceiling. So for `/v1/chat`, a request within 41 bytes of the ceiling passes
  preflight, sends `200` NDJSON headers, and then fails in `prepare_chat` with an error event
  instead of a clean `400`. Behaviour is fail-closed: there is no upstream connection, and
  proposals still refuse with 400 before dispatch. Fix: preflight through the configured transport's
  `encode_chat_request(.., mode, format)`, or call `prepare_chat` before writing headers. Add a
  boundary test for JSON-object mode.
- **Note (not a finding):** the run-record binding shows the format only through the body hash and
  size; neither mode nor format is an explicit field. This matches how mode is already handled, and
  the measurement policy records both. If explicit fields are wanted, put them in T-309 backlog.
