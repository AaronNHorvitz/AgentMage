  requires the same `run_id` and the stored `request_sha256`.
  - An unsealed edit is refused as `Invalid`.
  - A resealed edit or a foreign id is refused as `NotHeld`.
  - Re-admitting the same id is refused as `AlreadyAdmitted`.
  - The retained coordinator uses its own original request, never the lookup argument.
  - Tested without mutation, with no socket accept and no tool execution.
  - The digest is unkeyed, so anyone who knows the whole request can drive the run.
    Authentication is explicitly out of scope and documented as such.
- **Inert admission.** Only validation and context construction happen before insertion. The
  context and the coordinator are built from the same admission request and registry, so the
  caller cannot mismatch them. A failure consumes no identity. Tested with an invalid source
  budget followed by a correct admission.

## Findings

No critical, high or medium findings.

- **L1 (low, robustness/backlog).** `shells/host/src/coding_endpoint_owner.rs:199`.
  - Problem: the closed-entry latch relies only on the kernel's error latch, which is set on
    `Err` (runtime_loop.rs:2153). If a tool boundary, verifier or transport panics inside
    `advance`, the stack unwinds past both latches. The entry stays `Running` with partially
    advanced state.
  - Failure scenario: a future service keeps the owner after catching the unwind, for example
    behind a non-poisoning lock or `catch_unwind(AssertUnwindSafe(..))`. It could then advance
    again after an effect may already have been committed.
  - Not reachable in this increment, because nothing projects the owner into a service.
  - Fix: before calling, swap the entry into an "advancing/faulted" state and restore `Running`
    only on `Ok` or on an unlatched error (a drop guard works). Otherwise, document that an owner
    must be discarded after any panic during `advance`.
- **L2 (low, correctness/backlog).** `kernel/engine/src/runtime_loop/coordinator_endpoint.rs:283-288`,
  together with owner lines 201 and 234.
  - Problem: after an inner `Complete`, `run_endpoint_until_boundary` can return
    `InvalidBoundaryResult` (endpoint envelope missing or mismatched) without setting the
    reconciliation latch. The owner then leaves the entry `Running` instead of `Faulted`.
  - Consequence: no dispatch is possible, because the outcome is already set. But if the
    envelope is missing, `release` returns `StillRunning` forever and one of the four slots is
    permanently consumed. This needs a broken kernel invariant to happen.
  - Fix: in the owner, also latch `Faulted` when an error is returned and the events already
    contain `RunTerminal`.
- **L3 (low, test coverage/backlog).** `shells/host/src/coding_endpoint_owner_tests.rs:284`.
  - Gap: the capacity test shows that completed entries hold a slot. Nothing asserts that a
    `Faulted` entry also counts toward the four-slot limit and frees its slot only on release.
    The code does this at line 144, but no regression test pins it.
  - Fix: add the check to the existing latch test, with no new sub-row.

Retained backlog from the f1ac4d326c42 report (L1/L2/L3, low) is unchanged and is not
re-reviewed here.
