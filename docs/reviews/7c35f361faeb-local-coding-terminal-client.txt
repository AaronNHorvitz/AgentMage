## Review notes (no finding)

- **API authority:** the optional `settings_revision`/`settings_endpoint` fields can only *refuse*. The
  check runs under the operation lease before scope selection, and a mismatch preserves scope and pending
  state. Omitting the fields preserves the prior contract, which is documented honestly.
- **Typed approvals:** `confirm` requires stdin to be a tty and reads at most 256 bytes from `/dev/tty`.
  An exact challenge is required: `share <revision>`, or `apply <server preview_sha256>`, which the server
  re-checks. There is no `--yes`, environment or stdin path. The `apply` review prints the complete pending
  preview (complete diffs, hashes, expiry, risks) and the verified root.
- **Root identity:** `verify_root` uses the same native O_PATH/NOFOLLOW walk and path+dev+inode hash as
  selection, and grants nothing. It is checked before and after the prompt. The API still enforces its own
  revision, hash and preimage checks.
- **Token routing:** this matches the guide. The control token is used for settings inspection, select,
  revoke and apply/deny only. Tokens go through the existing owner-only, single-link, 0600/0700, no-symlink
  loader (also tested). They never appear in arguments, output or model requests: P7 checks the output, and
  the upstream assertion in `coding_cli.rs:362` checks model requests.
- **Wire framing:** the client accepts only `HTTP/1.1 200`. It refuses duplicate, obs-fold, non-printable,
  chunked, compressed or `Connection` (other than close) headers, mismatched or over-cap lengths, partial
  NDJSON lines, empty streams, and more than 8,192 events or 4 MiB. Reads have a 180 s deadline, and fixed
  literal routes make header injection impossible.
- **Stream failure:** only a `context, text…, proposal` sequence with matching revisions and
  `applied:false, tested:false` leads to preparation. Errors, truncation and length-finish fail first,
  which the tests cover for `length`.
- **No-effect retry:** there is exactly one apply send and no retry loop anywhere. The only polling is
  read-only `/v1/status` for at most 2 s.
- **Privacy/IP:** the added lines contain no private host path, username, hostname, credential, personal
  data, sibling project or third-party product name. Lane-path text appears only inside the retained,
  byte-identical d41 review, as accepted earlier. Cargo.toml/Cargo.lock are unchanged, so there is no new
  dependency, and SPDX headers are present.
- **Evaluation integrity:** frozen tasks, hidden tests, graders, prompts and thresholds are untouched (the
  audit's `git diff` and my diff reading agree). The driver uses only `development_tasks()` and historical
  development events. No held-out content appears, and no score is claimed.
- **Delivery:** there is no new sub-row; it is one runnable, measured client batch. TASKS.md says
  accurately that the batch awaits review and that both parents stay open.

## Findings

No critical, high or medium findings. The lows below go to backlog, with no new rows.

- **L1 (low, credential exposure to a non-API local listener; documentation gap now, design before the
  install kit).** Location: `platforms/local-api/src/coding_cli.rs:35-44` (loopback-only address check),
  `:46-53` and `:84-89` (bearer sent before any server authentication), and `docs/guides/coding-terminal.md:88-92`.
  - **Problem:** the client sends the control token, which the server accepts for every route
    (`lib.rs:378`), to whatever process holds the supplied loopback port.
  - **Scenario:** the API restarts on a new `127.0.0.1:0` port and the person reruns a command with the
    stale port from shell history. Another local OS account listening there receives full API authority.
    Reproduced as P1. With that token the account could select an owner-readable root, prepare its own
    answer and apply it, writing the owner's files.
  - **Mitigating facts:** this needs a second hostile local account plus a stale or mistyped port. The
    pre-existing smoke client has the same exposure. The API guide (`local-chat-api.md:102-106`) documents
    the analogous residual only for the model port.
  - **Fix:** now, document the API-port residual in the terminal and API guides. Before the install kit,
    serve the API on an owner-only Unix-domain socket inside the private auth directory, with a peer
    credential check. Alternatively, have the API record its bound address in that directory and make the
    server prove token possession (for example an HMAC challenge) before the client sends any bearer.
    Add a squatting-listener test.
- **L2 (low, escaping accuracy).** Location: `coding_cli.rs:243-259`.
  - **Problem:** `serde_json` leaves DEL (0x7F) unescaped. `safe()` passes it raw to the terminal,
    although the comment says every control character is escaped (P2d).
  - **Impact:** common terminal emulators ignore DEL on output, so no display spoofing was found.
  - **Fix:** escape `0x7F` as `\u007f` in `safe()` and add it to the unit test.
- **L3 (low, refusal visibility).** Location: `coding_cli.rs:139-141` and `bin/agentmage-code.rs:5-10`.
  - **Problem:** every non-200 reply is discarded unread. After a typed `apply`, the person sees the same
    generic message for `code.write.stale` (no effect, and no record is written) as for a dispatched
    `effect: unknown` failure. The same holds for `code.workspace.settings-stale`.
  - **Mitigating facts:** this is conservative, since the message says to inspect before retrying, and
    `review` shows dispatched records.
  - **Fix:** print the bounded, `safe()`-escaped error JSON for non-200 replies, then exit nonzero.

The earlier lows stay backlog as disclosed: cancellation coverage, conservative unknown-effect labels,
lease release, snapshot validation order, full-file escaped diff usability, campaign grade/candidate
binding and future worktree authority.
