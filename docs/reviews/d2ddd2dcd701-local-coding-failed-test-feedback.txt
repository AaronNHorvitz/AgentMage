## Analysis

- **Kernel gate** (`kernel/engine/src/runtime_loop.rs:4125-4140`): the opt-in applies only when all of these
  hold:
  - no terminal event has been emitted yet;
  - the run is an endpoint run in ControlledWrite mode;
  - the tool is CommandExecute;
  - the outcome is `Failed` with `NotChanged` state;
  - the output is present, its kind is `Report` and there are no artifact candidates;
  - the trusted boundary's hook agrees (the default hook returns `Ok(false)`, `runtime_loop.rs:641`).

  A hook error maps to `Dependency` after the effect and latches reconciliation. The failed output is
  stored through the existing non-success audit-artifact route and charged once. The event stays
  `ToolFailed`/`runtime.tool.failed`, which the event validator accepts mid-turn (`runtime_event.rs:601`).
  Endpoint runs have no checkpoint support (`runtime_loop.rs:1829`), and continuation validation
  (`runtime_artifact.rs:2534`) still refuses non-success results, so no durable path can absorb a failed
  observation.
- **Native binding** (`platforms/linux/src/coding_repository_endpoint_command.rs:497-552`): before any
  feedback is admitted, the boundary:
  - requires the explicit opt-in, `Stage::Spent` and the retained result;
  - checks the elapsed time, then compares the complete execution with a re-projection of the retained
    value;
  - reuses the original `repair_feedback()` checks (eligibility, consumed selection and `attempts < 3`);
  - consumes the selection through the original `consume_repair_feedback`.

  It spends no test attempt and grants nothing. Substituted receipt, receipt hash, call id, evidence,
  schema, payload and elapsed time are all rejected (tested). The owner stays spent, so no second command
  can run (tested).
- **Composition:** the opt-in is only a Rust builder method, `CodingEndpointPrepared::with_failure_observations`
  or the Linux boundary method. No HTTP or model field reaches it (grep finds no non-test callers). An
  Edit-variant boundary returns `Ok(false)`. The next context projects the result with
  `"outcome":"Failed"` under `untrusted_tool_results` (`shells/host/src/coding_endpoint_context.rs:246,343`).
  Untrusted test output can therefore influence only a model proposal, and every effect still needs its
  own exact approval (kernel test plus my probe).
- **Confinement:** the diff does not touch the sandbox, worker, path-resolution, network or grant-issuing
  code. The escape surface this change adds is result substitution, approval replay and selection
  renewal, and I exercised each of those above.
- **Evidence and honesty:** the evidence labels everything as synthetic process/model/creation
  observations and claims no workflow qualification and no score. The counts match my rerun exactly. The
  12-path diff touches no held-out task, hidden test, scorer, pin, threshold, dependency or SBOM, and it

## Findings

No critical, high or medium finding.

- **L1 (low, contract drift): verifier input no longer guarantees successful results.**
  `kernel/engine/src/runtime_loop.rs:1162` still documents `RuntimeVerificationInput::tool_results` as
  "Ordered successful tool results". After this change, admitted `Failed` results reach every verifier. Their
  `ToolOutput` evidence is also merged into the run's grounded `evidence` and resets the no-progress
  counter (`runtime_loop.rs:4167-4189`).

  No in-tree verifier can accept because of this:
  - `CodingCompletionVerifier` rejects any non-success result (`shells/host/src/coding_verifier.rs:130`);
  - `CodingEndpointReadVerifier` checks outcomes (`coding_endpoint_read_verifier.rs:209`);
  - `EvidenceAnswerVerifier` does not check outcomes (`standalone_evidence.rs:1663`), but it can cite only
    `ArtifactResult` fragments, never command receipts.

  However, the prepared serve path takes any trusted-factory verifier `V`, and one written to the stale
  doc could treat the presence of failure evidence as success. Fix:
  - update the doc (as was done for `RuntimeEndpointPreparationInput`);
  - preferably also keep evidence from admitted failures out of grounded `evidence`, or have the kernel
    refuse a `Success` verification while any result in `tool_results` is non-success.
- **L2 (low, coverage): host-layer opt-in and delegation are untested.**
  The host-layer opt-in (`shells/host/src/coding_endpoint_prepared_startup.rs:389,441-447`) and its
  delegation (`:490-501`) have no test, and neither does `serve_coding_endpoint_prepared` with the opt-in.
  The evidence says "Prepared admission can select it", but that is supported only by reading the code. A
  broken delegation would fail closed (default `false`). Fix: add a host test that admits a prepared
  command with the opt-in and asserts:
  - the `Failed` result reaches `CodingEndpointContext` preparation;
  - the Edit variant returns `false`;
  - the default prepared command still stops at the failure.
- **L3 (low, coverage): some kernel guard branches are untested in the repository.**
  The guards for Failed with Changed state, non-endpoint (native) runs and ReadOnly mode are visible in the
  code (`runtime_loop.rs:4128-4131`) but have no committed tests. My scratch probe covers Changed and
  Uncertain; native and ReadOnly remain covered only by reading. Fix: add these cases to the
  `endpoint_failure_feedback_is_explicit...` matrix.
- **L4 (low, design backlog for the open parent): the same-run repair loop cannot reach verified success.**
  Under the current coding verifier, a failed result stays in `tool_results` and that verifier rejects any
  non-success result. So even a later passing validation inside the same run can never be verified
  complete. The builder states that no scheduler is provided. Whoever builds the T-303/T-306 repair
  scheduler must define, explicitly and in a test, how a later full pass supersedes an earlier admitted
  failure without erasing it.

The predecessor's L1-L4 and earlier lows remain same-row backlog. They are not re-reviewed here.
