## Analysis of the production change (`coding_cli_driver.rs`)

- **One clock/latch for ordinary requests.** `run` now wraps the caller's client with
  `deadline = controls.deadline()` and `controls = Some(controls.observer())`
  (`coding_cli_driver.rs:434-439`). `Signals::observer` (`:45-52`) shares the `Arc<AtomicBool>`,
  `started` and `limit` and has an empty `registered`, so its `Drop` unregisters nothing; the
  original `controls` keeps sole ownership of the three handlers. `Client::call` refuses before
  token load, before connect and before each write when stopped, and caps the per-request
  180-second ceiling by the run deadline; `read_until` closes on deadline or latch every ≤100 ms.
  The initial selection GET (`:440`) is covered. My trickle probe confirms a peer that keeps
  sending bytes cannot extend the wait.
- **Post-stop allowlist.** `HttpRuntime::request` (`:241-273`) routes to a grace client only for:
  release (always), and, once stopped, job/declarations/artifact reads, `control` with
  `action == "cancel"` (JobControlAction is `snake_case`, `kernel/engine/src/job_control.rs:88`),
  and `advance` with `response == null` after a successful cancel control. Everything else keeps
  the observer-bearing client, whose `check_running` refuses before dispatch, so after a stop no
  prepare, start, approval-bearing advance or suspend/resume can be sent. Tracing the driver:
  after stop the only reachable sequence is `cancel_run` → `job_status` → cancel `control_job`
  (≤ MAX_JOB_CONTROL_ATTEMPTS, revision-bound) → one response-free `advance` → next loop
  `Controls::poll` returns `Err(Cancellation)` (`coding_cli_driver.rs:166-180`) →
  `best_effort_release`; or, from a terminal step, `finish` reads + release. All are inside one
  2-second deadline set lazily on the first cleanup request and never renewed; the grace client
  has no observer, so a further signal cannot cut it but the deadline does.
  `cancellation_sent` can only become true after a stop, because the driver issues Cancel only
  from `cancel_run`, which follows `Controls::poll` observing the stop.
- **Release once.** `release_sent` (`:405-410`) is set before dispatch, so `finish`'s failed
  release followed by `best_effort_release` (`cli_runtime.rs:300-302`) cannot replay it; a release
  whose grace already expired is never dispatched (reported as an error, uncertain).
- **No success after stop.** `:496-501` refuses to print `verified-outcome` for a SUCCESS/NO_OP
  outcome once stopped. This branch is genuinely exercised: in
  `stalled_terminal_evidence_cannot_be_reported_as_verified_success` the declarations/job cases
  tolerate the aborted optional read, release succeeds within grace and the NO_OP outcome would
  otherwise exit 0; the test asserts non-zero and no `verified-outcome`.
- Confinement, tool execution, approvals, event/revision/artifact verification and the server
  are unchanged; this increment only narrows what the terminal can send after a stop compared
  with the predecessor (which used per-request 180-second deadlines with no latch).

## Findings

No critical, high or medium finding.

- **Low L1 — shared grace can starve the release attempt.** `coding_cli_driver.rs:257-262`: the
  single 2-second deadline is shared by reconciliation reads and the final release, so a stalled
  response-free advance after cancellation consumes all of it and `best_effort_release` is never
  dispatched (the builder's own `cancellation_grace_is_shared_across_job_control_and_next_boundary_reads`
  asserts exactly 6 calls, no release). The host keeps the run held until it reclaims it; the
  client does report an error and says to inspect canonical state, and the guide says
  reconciliation can time out, so this is documented behaviour, not a hidden failure. Suggested
  fix (backlog): reserve a small fixed release slice (e.g. cap reconciliation reads at grace minus
  0.5 s) so the one release attempt is always dispatched, with a test that the stalled advance is
  followed by exactly one release.
- **Low L2 — post-stop allowlist is only tested through the driver.** `coding_cli_driver.rs:245-256`
  is a defence-in-depth guard, but no test calls `HttpRuntime` directly after a stop with an
  approval-bearing advance, a suspend/resume control or a response-free advance without a prior
  cancel to show each is refused before dispatch. The current driver cannot reach those paths,
  so there is no live bypass. Suggested fix (backlog): one in-crate unit test with a stopped
  `Signals` and a listener that asserts zero connections for each disallowed route.

Both lows are same-row backlog, alongside the predecessor's L1/L2 and earlier lows.
