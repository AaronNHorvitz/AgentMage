## Analysis of key checks

- Separation: `sandbox()` gives each role `--unshare-all --unshare-user
  --disable-userns --clearenv --cap-drop ALL`, separate read-only workspace and
  adapter, private tmpfs; only the oracle gets `--bind <results> /output`
  (`scripts/coding_eval_oracle.py:41-56`). The candidate workspace receives the
  submitted files; the oracle workspace receives `evaluation.projection(task)`
  (frozen base) and the hidden module is written only into the oracle adapter
  (`:142-160`). Host closes its copies of the cross pipes (`:88-89`).
- Trust of results: the host reads counts only from the oracle's result mount via
  `read_regular`, validates exact fields, non-negative ints, `tests ==
  expected_tests`, `0 < calls <= 128` (`:126-136`), and passes only with both exits
  0, no timeout/limit, no protocol failure and zero failures/errors/skips/expected
  failures/unexpected successes (`:190-192`).
- Wire parsing: duplicate keys, nonfinite constants, invalid UTF-8, unterminated
  or oversize frames, recursion and big-int conversion errors all map to sticky
  `ProtocolError`; replies must be exactly `{seq, result}` with the expected `seq`
  and a `bool` (not int) or non-empty map of bools
  (`scripts/coding_eval_oracle_worker.py:38-103`). Fresh JSON values cannot alias
  or mutate trusted test objects; arguments are re-serialized per call, so the
  hidden test's in-place mutations are reflected faithfully (seen in wire logs).
- Lifetime: leaders are observed with `WNOWAIT` and reaped only after `killpg`;
  descendants are bounded by bwrap `--die-with-parent` plus PID-namespace teardown
  (demonstrated above). Counts and wire log are published only after
  `case_workspace` cleanup; the cleanup-failure unit test confirms no promotion.
- Admission: `grade` runs `supported_task` (exact registered dict) and
  `require_historical_candidate` before `new_directory`; the CLI accepts only
  `verify`.
- Evaluation integrity: no task, hidden module, selection, threshold or collection
  file changed; fingerprint unchanged; no held-out content exists or is referenced;
  failures are counted, not dropped. Numbers in the evidence trace to runs I
  reproduced (20/58 units, 2 + 30 pairs, 89 tests, 4 and 6 calls, 704 files).
- Public hygiene: the diff contains no private host path, username, hostname,
  credential or sibling-project name, and no third-party product comparison or
  branding. Test literals `/var/home` and `/lane` are generic mount names asserted
  absent.
- Delivery: one sub-row level; the row runs end to end and is measured.
- Disclosure: missing aggregate process-tree quotas (e.g. no process-count limit),
  28 unadapted tasks and the unchanged legacy grader are stated plainly; generated
  scoring remains disabled, so these are not open boundaries for this row.

## Findings

No critical, high or medium findings.

### L1 (low): candidate-side infrastructure failure is accepted as a valid failing base

`scripts/coding_eval_oracle.py:193-197` ranks `protocol` before
`candidate_exit`/infrastructure, and `verify` accepts a base with cause
`protocol` for either task (`:233`). If only the candidate sandbox fails to start,
the oracle sees EOF and records a protocol failure. Reproduced by substituting
`/usr/bin/false` for the candidate command on the frozen dev-015 base:
`{"candidate_kind": "frozen-base", "cause": "protocol", "exit_code": 120,
"candidate_exit_code": 1}`, which `verify` would count as a valid base. The guide
states that "an infrastructure failure … cannot validate either control"; for the
base half this is overstated. Impact is limited because the same run must also
pass the reference, and both frozen bases fail deterministically for the
documented reasons (logs above). Fix before broadening the adapter: pin the
expected base outcome per task (dev-015 `test_failure` with one failure; dev-029
`protocol` with one call), or have the candidate emit a ready frame after the
sandbox starts and before function lookup so launch failure is classified as
`infrastructure`.

### Informational

- dev-029 base oracle exit 120 comes from a broken-pipe flush at interpreter exit
  after counts were written; harmless, could be noted in the guide.
- Candidate `/proc/self/mountinfo` exposes host mount metadata (overlay/ostree
  sources, temp-tree names) to candidate logs only; logs are private and no
  credential or home path is reachable.
