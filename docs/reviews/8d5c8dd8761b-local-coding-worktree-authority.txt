## Findings

No critical, high or medium findings.

- **L1 (low, correctness/usability) — `platforms/linux/src/coding_repository.rs:209`.**
  `destination = owned_root.join("worktree")` hashes the caller's *raw* spelling. Path checks normalise
  `//` and mid-path `/./`, so `/x/./owned` or `/x//owned` pass preparation (probe `dot-component-owned`
  reached the Git trust check). The executor compares the plan's `worktree_path_sha256` with the
  *canonical* `scope.worktree_path()` (`repository_safety.rs:937-942`). On a host with trusted Git, an
  approved creation for such a spelling would therefore consume the durable grant and then fail with
  `linux.git.worktree.destination`. This fails closed and is safe, but the approval is wasted and the
  failure is confusing. Fix: derive the destination from `scope.owned_root().join("worktree")` (already
  canonical and crate-visible), or refuse when the input differs from `canonicalize()`. Add a test.
- **L2 (low, evidence coverage; blocking only at parent acceptance) —
  `coding_repository_tests.rs:396-514`, `coding_repository.rs:285-370`.**
  The positive native branch has never executed in this lane. The executor's own worktree tests are also
  in the T-301 baseline failure set. As written, the positive branch also never exercises the decide-time
  refusals that the evidence and guide describe: root or management-directory replacement, a destination
  that became non-empty, or repository drift between prepare and decide. It also leaves the post-success
  `held_root(destination)` path untested. The labelling is honest and this batch claims no native creation.
  Before T-303/T-306 close, run this test on a host with root-owned Git and add those drift cases.
- **L3 (low, diagnostics) — `coding_repository.rs:366`.** After a durable `Succeeded` receipt, a failing
  `held_root(&pending.destination)?` returns `code.repository.scope`. That code reads like a pre-dispatch
  refusal; the API wraps it as `effect: unknown` and the CLI exits non-zero. Map it to
  `code.repository.uncertain`, as the adjacent post-dispatch revalidations already do.
