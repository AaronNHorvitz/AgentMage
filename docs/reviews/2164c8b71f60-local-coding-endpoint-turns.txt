## Analysis

**Run framing.** `new` re-verifies the sealed request digest/shape (`turn.rs:101`). It refuses any mode
other than `EphemeralReadOnly` and any cursor (`turn.rs:103`), and it refuses a zero or failing clock.
The tests cover model drift, durable mode and a resume cursor.

**Control refactor.** `RuntimePhaseControl::new` now delegates to `for_run_limits` with exactly
`&request.task.task_id` and `request.limits.max_elapsed_ms` (`runtime_loop.rs:160-171`). `observe`
compares the same values (`runtime_loop.rs:202, 222`). Monotonic regression, zero start, exact
schema/task/correlation cancellation matching and stop latching are unchanged. Every `observe` error
latches a stop, so `remaining_ms` closes the component on any failed observation, including clock
failure (test 6).

**Close-first discipline.** `execute_turn` sets `closed = true` before any fallible step
(`turn.rs:191`) and reopens only on full success (`turn.rs:308`). I traced every `?`/early return
between those lines: each leaves the component closed. Re-entry after a failure returns before
touching the port. The tests confirm that the call counters stay unchanged.

**Ledger.** `for_endpoint_run` inserts finite defaults for PlanSteps, ModelCalls, InputBytes
(`max_request_body_bytes × max_context_refreshes`, overflow-checked), OutputBytes and
ElapsedMilliseconds. It takes `min` with any declared packet budget. Duplicate packet budgets, which
would otherwise make `BTreeMap::collect` keep the later and possibly broader value, are already
refused by `work_packet::validate_budgets` (`work_packet.rs:563-570`) inside `validate_common_run_shape`.
Read-only `consume` on an absent budget is unbounded, but all five accounted resources are always
present, so this is not reachable for these resources.

**Envelope before dispatch.** Admission is a clone: planned (+1 PlanStep), then admitted (+input, +1
call), then envelope (+`response_text_limit_bytes`, +`total_timeout` rounded up). The envelope is never
committed. The phase bounds streamed bytes by `response_text_limit_bytes`
(`endpoint.rs:220-223`) and accepted `dispatch_elapsed` by `total_timeout` (`endpoint.rs:240`), so
the post-acceptance `completed.consume` cannot exceed what the envelope proved. The reserved maxima are
not spent (test 5 demonstrates exact 2×50 B / 2×2 ms acceptance at the ceiling).

**Spent vs. rolled back.** `self.resources = admitted` is set before `phase.execute`. It is reset to
`planned` only when the phase reports `dispatch_attempts == 0`, which happens only on a phase-entry
control stop. A failed dispatch (dependency error, bad digest, oversize stream, callback deadline)
keeps the call and input spent (tests 4 and 8). A caught panic keeps them spent and closed (test 12).
A panic inside the phase's own pre-attempt control observation would also keep the reservation. That
is conservative over-counting, and the guide already says a reservation proves no remote execution.

**Results.** `RuntimeEndpointTurnResult` has private fields and no `Deserialize`/`Clone`, so it cannot
be built from wire claims. The run binding comes from the phase's own `for_run` framing.

**Scope.** No tool, write, network socket, credential, event, prompt or proposal interpretation is
added. `grep` shows `RuntimeEndpointTurns` is not used outside its tests, which matches the "not wired"
labelling. The diff touches no evaluation task, hidden test, scorer, threshold, held-out content,
Cargo manifest/lockfile, `#[ignore]`, SBOM or release path.

**Public hygiene.** The added lines contain no home path, username, hostname, credential or private
sibling-project name. The only `/lane/...` sandbox paths are inside the retained predecessor review,
which follows the accepted precedent.

**Confinement.** This increment adds no tool-execution or filesystem/network surface. No traversal,
symlink or environment-leak escape attempt applies to it. Confinement boundaries are unchanged.

## Findings

No critical, high or medium finding.

- **L1 (low, documentation): the guide no longer says that a second instance gets a fresh budget.**
  Location: `docs/guides/runtime-endpoint-runs.md:56-92`, `kernel/engine/src/runtime_loop/endpoint/turn.rs:97`.
  Nothing prevents a caller from constructing a second `RuntimeEndpointTurns` from the same sealed
  request. That instance gets a fresh clock and ledger and repeats the same correlation and turn IDs.
  The previous guide said explicitly, "Creating a second phase does not establish a fresh run budget."
  The replacement text says only that the component "cannot retry or renew its ledger" and leaves
  exclusive ownership open.
  Fix: add one sentence saying that constructing another instance for the same run is not prevented
  here, gives no fresh run budget, and must be excluded by the eventual coordinator's exclusive
  ownership. Not exploitable today because nothing outside the tests constructs the type.
- **L2 (low, delivery backlog): the endpoint turn path is still not reachable from any surface.**
  Location: `TASKS.md:5-9`.
  Context admission, run admission and now turns are all unwired kernel components. They are
  correctly labelled non-closing, no sub-row is added, and the component runs and is tested. The next
  increment should wire it into the existing coordinator and a live surface, with a development
  scoreboard entry, rather than adding another standalone component.
