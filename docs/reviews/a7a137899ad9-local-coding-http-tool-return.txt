## Review

**Authorization.** Release still requires the control credential. `observation` matches only
`GET /request` and `POST /events` (`coding_endpoint_api.rs:335-342`), so `DelegateObservations` cannot
release. The run binding (run_id plus request_sha256) is checked before the lock is taken. No wire input selects
the disposition: `TerminalToolDisposition` is fixed by which public function trusted startup calls. No route,
port, deserialized authority, admission change or grant renewal is added.

**Terminal checks.** The `Return` path calls the original host `release_with_tool_boundary`. That method:
- refuses `Released` (NotHeld), `faulted` (Faulted) and live runs (StillRunning);
- moves the coordinator out and calls the kernel's `try_into_endpoint_tool_boundary`, which has the uncertainty
  and publication checks reviewed at b62f35cf;
- on refusal, restores the entry (ToolNotRecoverable).

A successful release sets `Held::Released`, so a repeated release returns NotHeld. Later `events` and `advance`
calls also return NotHeld, and the test asserts all three.

**Ownership and lifetime.** The boundary sits in `Session.returned` under the mutex. After `serve_connections`
returns Ok, the function calls `session.into_inner()`. `serve_connections` uses `thread::scope` and joins every
worker first, so no HTTP worker can outlive the hand-back.

Handler errors are discarded (`let _ = handler(...)`, `lib.rs:400`). A client that disconnects after a
successful release therefore does not lose the retained owner.

On any service error (accept failure or worker panic), the `?` drops the session and the tool. This fails
closed, and the documentation states it ("Service errors may drop process-held state").

A stop without a release returns `None`, as tested for both unstarted and cancelled-but-unreleased runs.

**Ordinary entry points.** `serve_admitted_coding_endpoint` routes through the same inner function with
`Discard` and maps the result to `()`. The release arm in `Discard` is byte-identical to the previous code. The
only addition is `into_inner`, which can fail only after a poisoning panic, and such a panic already surfaces as
a join error. The existing HTTP tests in the same target pass.

**Tests.** The tests use real loopback HTTP and upstream sockets. They check:
- the same heap allocation (`Box<u8>` address and value) and the same `Arc` counter across two fresh services;
- that the previous run's request and approval response are refused (409);
- delegated release (403), a substituted digest (409) and single-use release;
- uncertain and faulted runs: repeated 409, unchanged event page, unchanged terminal or fault state, no
  redispatch and `None` on shutdown;
- explicit release after a pre-dispatch cancellation, with zero tool calls and zero upstream connections.

The fixture's earlier development failure (approval casing, cleanup double panic) is fixed in test code only.
The `let _ = tx.send(...)` tolerates a dropped receiver, and a serve error still makes `recv_timeout(..).unwrap()`
fail. I found no weakened production check.

- Location: `platforms/local-api/tests/support/coding_endpoint_tool_return.rs:273`.
- The uncertain and faulted release refusals assert `.0 == 409` and not the error code. Mutation M4 (host
  `Faulted` arm removed) still passes, because a lower layer also refuses.

**L2 (low, claim precision; backlog): "requires fresh approvals" is partly a fixture property.**

  approval".
