## Findings

### M2 (medium): a lone CR is neither a line terminator nor refused, so a data line is silently dropped and a truncated answer still completes

Location: `platforms/linux-inference/src/local_chat.rs:309-313` (only LF ends a
line, and only one CR directly before that LF is removed). Line 329 then
takes the folded line as a comment, and lines 335-341 take it as an inert field
name (`_ => {}`) or as an `id`/`retry` value. This behaviour predates the repair
(identical at f18838af) and the repair does not address it.

In the event-stream format, a CR on its own is a valid line terminator. Here an
embedded CR not followed by LF stays inside the line, so the next field joins
the current line and is swallowed. Reproduced on HEAD and base, both returning
exactly this:

| Body (`A`, `B`, `C` are text events; tail is stop + `[DONE]`) | Result |
| --- | --- |
| `A`, `"\r"`, `data: {…"B "…}\n\n`, `C`, tail | `Ok([Text("A "), Text("C"), Finished(Stop)])`, `end = Ok(())` |
| `A`, `":hb\r"` + `data: {…B…}\n\n`, `C`, tail | same; B is lost inside a comment |
| `A`, `"id: 7\r"` + `data: {…B…}\n\n`, `C`, tail | same; B is lost inside the `id` value |
| `A`, `"retry: 5\r"` + `data: {…B…}\n\n`, `C`, tail | same |

This is the M1 failure mode again: text missing from the middle (or, with a
leading `"\r"`, the start) of the answer, reported as a verified `Stop`.
It contradicts the guide's claim at `docs/guides/local-chat-protocol.md:47-48`
("No closed connection or partial output can imply success"). It also
contradicts the repair's stated aim that misplaced framing "cannot silently
hide a data field". The refusal added for non-ASCII names does not cover it,
because CR is ASCII. Review 1 recorded "lone CR → `Protocol`, fail-closed".
That holds only when the CR falls inside a JSON `data` value. I am correcting
that observation here.

It is rated medium, not high. It needs a spec-valid but unusual terminator from
the local server, and it has no confinement, execution or credential impact.
It does break the row's core correctness claim on a valid input.

Fix: the guide already says only LF and CRLF are supported. After the single
trailing CR is removed (line 313), refuse any line that still contains `b'\r'`
with `ChatError::Protocol`. Alternatively, treat a lone CR as a terminator, but
fail-closed refusal is simpler and matches the documentation. Add a
regression test that puts a lone CR at line start, after a comment, after
`id:`/`retry:`/unknown fields and inside `data:`. Test every two-way split and
byte-at-a-time delivery, and assert `Protocol` with `end() == Err(Failed)`,
never a shortened `Finished`. Then state in the guide that a lone CR is refused.

### L6 (low): other ASCII-malformed field names are silently ignored

Location: `local_chat.rs:335-341`. Probes: `"\x00data:…"`, `" data:…"`,
`"\tdata:…"`, `"\x7fdata:…"`, `"DATA:…"` and `"data :…"` before the first text
event each give `[Text("second"), Finished(Stop)]`, `end = Ok`. The format
says unknown fields are ignored, so a conforming parser drops them too. This
needs a malformed server rather than a valid one, so it is backlog. Consider
refusing field names outside `[a-z]` (or outside the known set plus
lowercase letters) at T-309. The guide's sentence is accurate as written: it
promises only that a misplaced mark cannot hide data.
