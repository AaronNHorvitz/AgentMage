## Findings

No critical, high or medium findings.

- **L1 (low, documentation and reachability):** `docs/guides/runtime-endpoint-runs.md:214` says
  "Trusted hosts can expose it through the dedicated endpoint API". The doc comment at
  `platforms/local-api/src/coding_endpoint_api.rs:126` still says that function "Hosts one ephemeral
  configured-endpoint run". No test in this commit drives a controlled-write run, meaning a write or
  command challenge plus its Allow/Deny response, through `serve_coding_endpoint`. The adapter is
  generic and mode-agnostic, so I found no defect. With `DelegateObservations`, ordinary-credential
  holders would now also see write and command tool events. Fix: add one local-API test using a
  synthetic write boundary, or reword the guide sentence to "library composition only". Also update
  the adapter's doc comment to cover controlled-write runs and the meaning of delegated observations.
- **L2 (low, test strength; backlog note):** the synthetic boundary in
  `runtime_loop_endpoint_coordinator_tests.rs:256-298` issues the same `approval_id` and `grant_id`
  for every Ask, so write and command challenges differ only by challenge digest. The binding is
  still exercised, and I confirmed it with my repeated-write probe. Distinct per-operation
  identities would additionally show that a mismatched approval or grant identity is refused across
  operations. Separately, the existing state-change rule treats a *successful command reporting
  Changed* as a boundary fault that latches reconciliation
  (`runtime_loop_endpoint_write_tests.rs:306-310`). That is unchanged native semantics. The future
  native test-command owner must report NotChanged or fit this rule; note it for the activation row.

The two predecessor lows (L1 release slice within the cancellation grace, L2 direct post-stop
allowlist probes) and earlier lows remain backlog, unchanged.
