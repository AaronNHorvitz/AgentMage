## Code review

**The main walk (repair_fixture_permissions, lines 433-521):**

- Frames are packed into `array('Q')`, and names into a NUL-separated bytearray with a cursor.
- Each directory is scanned once. Ascent opens `..` and checks the frame's recorded
  (st_dev, st_ino).
- At depth 256 the subtree is handed to `detached_fixture_walk`. A host `..` lookup therefore never
  happens deeper than 256 levels, and there is no reopening from the root.
- `finally` clears both buffers and closes the single current descriptor.

**`detached_fixture_walk` (lines 333-430):**

- The stage is a random-named 0o700 sibling of candidate-tmp inside the private case root. It is
  never bound into a worker: `sandbox()` binds only workspace, adapter, output and candidate-tmp.
- Every moved inode is verified with `stat(..., follow_symlinks=False)` against its pinned identity.
- chmod goes only through the host's own `/proc/self/fd/N` of an `O_PATH|O_DIRECTORY|O_NOFOLLOW`
  descriptor. Files and symlinks are never chmodded or moved, and are unlinked only in removal mode.
- Restoration runs in reverse BFS order into parent labels that have been identity-checked.
- Cross-directory renames then have both parents inside the shallow stage, so kernel
  ancestor-check costs stay constant.
- Descriptors stay constant. Records are cleared in `finally`.

**The remove walk** stages at the same depth, and its existing parent/child inode checks are
unchanged. **The workers** are always terminated in `exchange`'s `finally` before
`candidate_temporary` cleans up. **The only caller** is `candidate_temporary`.

## Findings

No critical, high or medium findings.

### L1 (low, backlog): deep staging keeps uncompact per-directory records

Location: scripts/coding_eval_oracle.py:344, 379 and 401.

- `records` is a Python list of 4-tuples holding a str name and int identity. It is never trimmed
  in removal mode, although deleted entries are no longer needed.
- `entries = list(scan)` materialises every entry of one directory, files included.

Measured cost: about 250 B per staged directory and about 150 B per file in one directory. The
shallow walk costs about 12 B per name. This is linear and far from v25's quadratic growth, so it
does not reopen M1.

Combined with the carried L2, a candidate that spends its whole budget on a deep tree could still
push host cleanup to GB-scale RSS and minutes of runtime. This is an extrapolation from the
measured 137k dirs/s build rate and 250 B/dir, not a run.

The evidence sentence "frames and names occupy compact primitive buffers" is true of the main walk
only.

Fix:

- Pack staging records into `array('Q')` (parent index, st_dev, st_ino, name offset) plus a
  bytearray of names.
- Drop processed records in removal mode.
- Unlink non-directories while iterating, instead of listing them.
- Qualify the evidence sentence.

### L2 (low, carried backlog): no aggregate scratch quota and no host cleanup deadline

The host-backed candidate `/tmp` still has no aggregate disk or inode quota, and host cleanup has no
deadline. While an in-namespace process survives, the staged walk keeps following the directories
it creates (p4 "grow"). The guide (line 575) and the evidence (line 131) disclose this, and both
note it is required before generated scoring.
