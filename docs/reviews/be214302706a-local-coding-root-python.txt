## Findings

No critical, high or medium findings.

**L1 (low): root discovery runs model-writable test modules under `src/`.**

- Location: `shells/host/src/coding_development_runtime.rs:2058-2089` (`python_project_paths`) combined with
  `:2117` (`-s .`). The disclosure gap is in `docs/guides/coding-runtime-api.md` ("Root-level Python tests").
- Problem: in a src-package layout (`src/__init__.py` present), the root selection discovers and executes
  `src/test*.py` and tests in nested `src` packages. The same files are inside the exact writable source
  scope, because every parsed `src/**.py` file is writable. The package selection (`-s tests`) never runs
  `src/` modules as tests. So in root mode the model can satisfy "The exact approved Python project tests
  pass" by editing the assertions themselves.
- Reproduction: I made a temp repo with `src/__init__.py`, `src/calc.py` (bug) and `src/test_calc_in_src.py`.
  `env -i /usr/bin/python3 -I -B -m unittest discover -s . -t . -v` gives `FAILED (failures=1)`, exit 1.
  After rewriting only `src/test_calc_in_src.py` (a file inside the scope) to `pass`, the same command gives
  `OK`, exit 0.
- Why it is low:
  - Confinement and the grant set are unchanged.
  - Decision 0155 says the approved runner is trusted and this is not independent grading.
  - Editable `src` code can already tamper with the runner in either layout.
  - The frozen scorer, not this output, decides coding scores.
  - Every write remains individually visible.
- Fix:
  - In the root layout, refuse startup when any writable path's basename matches the discovery pattern
    `test*.py`, or exclude such paths from `exact_files`.
  - Add a unit test next to `python_project_definition_enters_existing_profile_with_no_test_write_scope`.
  - State the rule in the guide.
- This must be resolved before any root-layout run is cited as coding-success evidence.

**L2 (low): the root validation definition is labelled as the package selection.**

- Location: `shells/host/src/coding_development_runtime.rs:2024-2027`. The sealed definition JSON hard-codes
  `"selection":"python-project"` for both layouts.
- Impact: identities still differ through the embedded command, so this is not a collision. But the sealed
  record misdescribes the root layout to anyone auditing it.
- Fix: derive the label from the scenario (`python-root-project`) in a future change that already re-seals.
  It is not worth a standalone identity change.
