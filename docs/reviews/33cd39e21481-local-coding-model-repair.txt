## Review notes (what was verified)

Authorization and consent

- Both routes check `req.control` before taking the lease or parsing the body
  (`coding_repair_api.rs:34`). Body parsing uses `deny_unknown_fields` plus `object_json`: arrays,
  unknown, duplicate and non-boolean fields refuse (tested).
- `prepare_repair` requires `approve_failure_disclosure`, the current settings revision and endpoint,
  a selected workspace whose root identity equals the held worktree's, the existing endpoint-bound
  model-context approval (`workspace_sources(..., true)`), and held creation provenance
  (`select_created_sources`). Settings and workspace replacement need the same single operation lease,
  so they cannot race the check.
- The CLI shows the exact preview, settings, selection, model and budgets through `safe()` (JSON with
  every non-ASCII and DEL character escaped; serde escapes C0 controls). So test output cannot inject
  terminal escapes into the consent screen. The challenge is bound to `feedback_sha256`, and the root is
  re-verified before and after consent. The server recomputes the preview and refuses a hash or receipt
  mismatch. Failure disclosure, read consent, exact write approval and fresh test approval stay separate
  (synthetic terminal tests cover decline, root replacement and incomplete answers).

Budget and recovery

- `consume_repair_feedback` sets `repair_requested` under the held owner mutex after all
  pre-admission checks and before network admission. No error path resets it. Only `consume_validation`
  creates a new series, which needs a separately approved fresh test attempt. Edits do not touch the
  series. `attempts >= MAX_ATTEMPTS` refuses, and eligibility uses the kernel's
  `plan_failed_test_rerun`. The native test exercises fail, consume, edit, still spent, fresh fail,
  consume, third fail, refused.
- Lock order: the repair path holds repository then state; every other path takes and releases
  state before locking the repository, and every competing repository route fails `begin()` with 409
  before trying the repository mutex. No deadlock. Status and cancel use only the state mutex.

Untrusted input and confinement

- Diagnostics come only from the native owner's normalized result. Each channel keeps the whole
  output or the first and last 512 raw bytes, decoded lossily with that labelled. Failed names are
  capped at 16 × 256 characters with a truncation flag. Successful results keep no excerpts.
- The commands that produce the output run under bwrap with `--unshare-all`, `--clearenv` and the
  worktree mounted at `/work`. Diagnostics therefore don't contain host paths or the host environment.
  `worktree_root_sha256` includes device and inode identity, so it can't be guessed offline from a path.
- The repair request adds no tools (asserted). Diagnostics sit in a separate JSON user message under
  `untrusted_test_observation`, and their serialized bytes plus the extra instruction are reserved from
  the same ≤32 KiB ceiling. The strict edit checker rejects `../escape`. A proposal is inert:
  `applied: false`, `tested: false`, and no write or command is reachable without the existing exact
  approvals. No new write, command or network path is added.
- The ordinary proposal path is unchanged when `feedback` is `None`: same two messages and the same
  context event. Command 7 confirms this externally for all 30 development contexts.

## Findings

No critical, high or medium finding.

- **Low L1: the pre-consumption encode check does not test the exact request.**
  `platforms/local-api/src/coding_repair_api.rs:140-158` validates `encode_chat` on the ordinary
  two-message prompt. After consumption, `lib.rs` encodes the three-message repair prompt (extended
  system instruction plus diagnostics message). I found no reachable failure: model-name and token
  checks are identical, total content is ≤32 KiB, and worst-case JSON escaping stays far below the
  256 KiB `MAX_REQUEST_BYTES`. But the guarantee that invalid input refuses before consumption rests on
  this implicit size argument. Fix: build the actual repair message set once in a shared helper, call
  `encode_chat` on it in `prepare_repair`, and pass the encoded messages or helper into
  `coding_proposal_with_feedback`. Backlog.
- **Low (retained backlog, unchanged):** no test exercises the positive `handle_repair` path from a
  successful `prepare_repair` through consume to stream against a real native owner. The shared renderer
  and owner are each tested, but not joined over HTTP. This is the disclosed "native positive HTTP
  coverage" item, which the lane's executable-trust refusal blocks. The other disclosed low backlog
  items are unchanged.
