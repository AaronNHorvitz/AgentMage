## Method: what I verified beyond the harness

**Closed worker session (`repository_commit_io.rs`).**
- `CommitIoSession::new` re-runs `verify_local_commit_plan` (sealed hash, all authority flags false, network
  false). It also binds `plan.repository_sha256` to the scope's path identity and captures the
  already-reviewed `LinuxRepositoryMutationScope`.
- `perform` (lines 111–184) enforces Branch → Commit → Update(object) → Terminal. Any error sets
  `Stage::Terminal` (lines 104–108), so there is no retry.
- Commands are built from the plan, not from caller strings:
  - `rev-parse --verify <task_branch>`, with output that must equal `parent\n` exactly;
  - `cat-file commit <object>`, where the object must be lowercase hex, the same length as the parent and not
    all zeros, so `--help`-style option injection is refused (tested);
  - `update-ref --no-deref <task_branch> <read object> <parent>`, with output that must be empty.
- `task_branch` must start with `refs/heads/agentmage/tasks/` (kernel `valid_task_branch`), so the default
  branch is unreachable. The test covers `refs/heads/main`.
- The update target is the object that was read, not one the caller supplies again. The only caller
  (`local_commit.rs:424–492`) runs update after `verify_raw_commit` and `verify_signature_status` both pass.
- Dispatch goes through `run_worker`: the reviewed closed offline supervisor, systemd/bwrap/seccomp,
  `LaunchOwner::RepositoryGit`, with limits on both streams. The worker uses `candidate_environment()` with no
  GNUPGHOME and no index file.
- Roots are revalidated before and after dispatch.
- A result is refused if it is incomplete, unsuccessful, oversized, truncated (`total != retained.len()`),
  cancelled or past the deadline.
- The 30 s deadline is fixed at construction and shared with the direct signer runner.

**Raw content verification (`local_commit.rs:765–801`).**
- It requires exact header order: tree, a single parent, author, committer, then
  `gpgsig -----BEGIN PGP SIGNATURE-----`.
- Every following header line must be a space-prefixed continuation line ending in the END armor line.
  Any extra parent, tree, identity, `encoding` or other header refuses.
- Headers must be UTF-8, and the message bytes must match exactly.
- I reproduced this with installed Git 2.56.0 and GnuPG 2.4.9, using a throwaway key in a throwaway
  GNUPGHOME and repository under /tmp, deleted afterwards. A real signed SHA-1 commit created from stdin `msg`
  has exactly that header layout, and its message is `b'msg'` with no final newline added. This confirms the
  corrected stdin-byte assumption.

**Signature status (`local_commit.rs:803–833`).**
- With a primary-key signature, real `verify-commit --raw` output goes to stderr only (stdout 0 bytes). Its
  VALIDSIG record has 11 fields, and field 1 is the full fingerprint, so the parser accepts it.
- The parser refuses:
  - prose or `warning:` prefixes;
  - GOODSIG without VALIDSIG;
  - a longer fingerprint that shares the pinned prefix;
  - duplicate VALIDSIG records;
  - NUL bytes;
  - any listed failure, revocation or expiry record.

## Findings

No critical, high or medium findings.

**L1 (low): SHA-256 repositories can never pass raw verification.**
- Location: `platforms/linux/src/local_commit.rs:792`.
- The verifier hard-codes the `gpgsig` header. Installed Git 2.56.0 writes `gpgsig-sha256` in a
  `--object-format=sha256` repository, which I reproduced with a fake signing program.
- The kernel plan, the worker and `object_output` all accept 64-hex objects. In a SHA-256 repository the
  adapter would therefore create a signed object and then always refuse it as `verification_failed`. The
  result is an unreferenced object, a Failed/uncertain result and no ref move.
- This fails closed and is not a regression: the old `starts_with("gpgsig ")` check had the same gap.
- Fix: choose the header from the object length (40 → `gpgsig`, 64 → `gpgsig-sha256`). Refuse the other
  name. Add a SHA-256 case to the installed-Git encoding test.

**L2 (low): a signing subkey makes a primary-key pin always fail.**
- Locations: `platforms/linux/src/local_commit.rs:819` and `:442`.
- The status check compares VALIDSIG field 1, which is the fingerprint of the key that actually signed.
  Signing uses `-S<fpr>` without `!`, so GnuPG picks the newest signing subkey. Inspection (`:299–318`,
  pre-existing) accepts any `fpr` in the listing.
- I reproduced this with GnuPG 2.4.9: after adding a signing subkey, VALIDSIG field 1 became the subkey
  fingerprint, and the primary moved to field 10. A primary-key pin would always be refused.
- This fails closed and is not a security issue.
- Fix: before activation, either sign with `-S<fpr>!` and keep the field-1 equality, or have inspection
  resolve and pin the exact signing-capable key and compare field 1 to it (optionally also field 10 to the
  primary).

**Retained backlog.** L1 and L2 from the base review are unchanged and remain same-row backlog: scratch
retained after a failed post-claim constructor, and descriptor binding from claim to capture. The pre-activation
prerequisites stated by the builder also remain open: signer confinement, whole-unit descendant cleanup and
the inherited output-pipe limitation.
