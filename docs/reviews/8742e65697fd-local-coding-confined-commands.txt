## Review of the requested areas

- **Native owner and authorization.** All four routes check `req.control` (403 otherwise; tested) and
  serialize through `begin()`. Preparation needs `self.created`, which is set only in `decide` after an
  observed `Succeeded` receipt (`coding_repository.rs:376-392`). There is no caller-path adoption
  (API test: `code.command.worktree-required`). Restart drops `created` and `command` (tested).
  A model reply or source selection cannot reach these routes. Consent is a client-side typed challenge
  on `/dev/tty`. As in the prior accepted batch, the server's guarantee is control-token plus exact
  preview digest.
- **ExactEffect extraction.** It preserves the previous worktree composition: the same policy shape,
  session parent, single derived operation, registry, call, context and `execute_effect`. The tool ID now
  comes from the tool definition (`TOOL` for worktrees, `local-coding-command` for commands), version
  1.0.0 on both sides. Only the rollback text changed. Commands use `GrantOperation::CommandExecute`,
  the held worktree root as target, the kernel preview SHA as plan SHA, and network, credential and
  publication scopes deny-all.
- **Post-success ownership.** Prior L1 is repaired: the destination is now derived from `scope.owned_root()`
  (`coding_repository.rs:223`). Prior L3 is repaired: a post-success `held_root` failure maps to
  `code.repository.uncertain` (`:379`). Prior L2 is not addressed by this batch and is carried:
  positive native creation and decide-time drift on an admitted host are still required before parent
  acceptance. `verify_created` revalidates both held roots by identity before preview, before
  consumption and after execution; my real-directory and mid-execution swap probes confirm this.
- **Command module.** Digest mismatch preserves the preview; denial, expiry and attempted dispatch consume
  it. A monotonic deadline is checked at take and at dispatch, with the dispatch clock advanced by
  monotonic elapsed time. Output is accepted only if `verify_command_receipt` and the retained byte
  counts agree (the corrupt-output test and my probes confirm). `test_suite_verified:false` is always
  present, and there is no retry or replay.
- **Confinement, via the unchanged native runner and kernel contract.** The worktree is bound read-only
  by descriptor at `/work`, so there is no path TOCTOU. Other mounts: tmpfs `/tmp`, read-only
  `/usr/lib*`, `/lib*` and `ld.so.cache` only; no `/usr/bin`, `/etc`, home or main repository.

## Findings

No critical, high or medium findings.

- **L1 (low, honest labelling) — `docs/guides/coding-commands.md:62-63`.** The guide says
  "Shell/interpreter entry points remain prohibited by the kernel command contract". The kernel refuses
  only exact basenames (`kernel/engine/src/command_runner.rs:1124`). It refuses `-c`/`-e` only as exact
  tokens or `-c=`/`-e=` forms (`:1098`). On this host, `/usr/bin/python3.15 -cprint(1)`,
  `/usr/bin/perl5.44.0 '-eprint 1'`, `tclsh9.0` and `gawk` all seal and pass `command_registry` (probe
  above). The sandbox is still the boundary, and the approval shows the exact executable and arguments,
  so nothing escapes. But the sentence overstates a defence-in-depth property that a reviewer of an
  approval might rely on. Fix: reword to "a fixed list of shell and interpreter names and exact inline
  evaluation flags is refused; other interpreters, including versioned names, run inside the same
  sandbox". Alternatively harden the kernel check in its own row (pre-existing behaviour) to cover
  version suffixes and attached short-option forms.
- **L2 (low, test coverage) — `platforms/linux/src/coding_repository_command_tests.rs:264-282`.**
  `command_scope_and_bounds_cannot_expand_the_native_contract` mutates sealed specs without resealing,
  so every case also fails the kernel digest check. Deleting all six composition bounds at
  `coding_repository_command.rs:252-260` leaves this test passing (mutation run above). Fix: build each
  case with `CommandSpec::seal`/`CommandBounds::new` at values above the composition limit but within the
  kernel limit, for example 120 001 ms or 65 537 B, and assert `code.command.bounds` specifically.
- **L3 (low, test fidelity) — `platforms/local-api/tests/coding_worktree.rs:591,654`.** The synthetic
  command-consent peer serves a worktree-shaped preview (`plan.branch_ref`) and asserts that branch ref
  appears. It never shows that the executable, arguments, environment and bounds of a command preview
  reach the consent transcript. Fix: serve a command-shaped preview (`operation: execute-command`,
  `command.executable`, `command.arguments` including non-ASCII) and assert those fields appear escaped.
- **L4 (low, diagnostics) — `platforms/linux/src/coding_repository.rs:597-697`.** Inside the shared
  `ExactEffect::execute`, command-path policy, parent, grant, tool, request and transaction errors
  surface as `code.repository.*`, for example `code.repository.uncertain` after a command dispatch,
  instead of `code.command.*`. This is conservative and safe, but the label is misleading. Fix: carry a
  code prefix in `ExactEffect`.
- **L5 (low, same-user window) — `platforms/linux/src/coding_repository.rs:378`.** Post-success
  ownership opens `pending.destination` by path, not relative to the held management-directory
  descriptor. A same-user process that swaps `<owned>/worktree` between native creation and this open
  would have the swapped directory adopted. Later checks are self-consistent with the swap, and exposure
  is read-only inside the sandbox. Fix: open the child via the held `owned` descriptor, or bind the held
  identity to the native receipt's observed object.

Carried, not new: prior review L2 (positive native creation and decide-time drift on an admitted host)
and the unmeasured positive native command branch both remain required before T-303/T-306 acceptance.
