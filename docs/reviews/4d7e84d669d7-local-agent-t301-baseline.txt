## Findings

### M1 (medium): checks outlive a terminated gate and keep holding the shared build reservation

Location: `scripts/local_agent_fast_gate.py:128-148`. The guide's claim at
`docs/guides/local-agent-development.md:45-47` holds only for the gate's own timeout.

Problem:

- `execute()` starts every check with `start_new_session=True`. Cleanup happens only
  when the gate itself observes `TimeoutExpired` or `KeyboardInterrupt`.
- Nothing handles SIGTERM or SIGHUP, and nothing ties the child to the gate's
  lifetime.
- The new session takes the check out of the caller's process group. So the usual
  way development tooling and harnesses stop a job — signalling or killing its
  process group — no longer reaches the check.

Reproduction (in-process `gate.execute()` running a 30-second sleeper):

1. Send SIGTERM to the gate process. The gate dies. The check survives with PPID 1,
   in its own session.
2. Start the gate under `setsid`, then `kill -KILL -- -<gate pgid>`. The gate dies.
   The check survives with PPID 1.

Consequence:

- Rust checks run under `/tools/build-slot`. That wrapper holds the shared
  heavy-build lock on fd 9 and runs the command as a child, so the lock fd passes
  down to cargo and every test process.
- An orphaned `cargo test` therefore keeps the reservation shared by all lanes
  until it finishes on its own. The gate's `--timeout` no longer applies, so a hung
  test holds the reservation indefinitely.
- Separately: when a check exits normally, leftover descendants in its process
  group are never signalled.

This is a resource-bound and descendant-cleanup defect in the T-301 deliverable.

Fix:

- Install SIGTERM and SIGHUP handlers that take the existing TERM→wait→KILL
  process-group path.
- Make the leader die with the gate: for example `PR_SET_PDEATHSIG` set in the
  child before exec, or a subreaper that kills the group.
- After every check, including normal exit, `killpg(SIGKILL)` the group, ignoring
  `ProcessLookupError`.
- Add behavioural tests showing that SIGTERM to a gate subprocess, and SIGKILL of
  the gate's process group, leave no descendant running. If the gate cannot
  guarantee cleanup for an uncatchable kill, document that residual limit.

### M2 (medium): the Rust gate path is structurally red here, and the baseline does not classify why

Locations:

- `docs/evidence/t301-baseline-2026-10-25.md:22-24` and `:66-72`
- `docs/evidence/t301-baseline-failures-2026-10-25.md:10-11`
- `docs/guides/local-agent-development.md:51-55`

**The gate cannot pass for most crates in this lane.** T-301 asks to "reconcile and
baseline" and to "pass a minutes-scale gate for … touched-crate unit/integration
tests". The batch's gate passed only because it selected no crate. Applying
`affected_packages()` to the real workspace metadata, a change in any of 8 of the
10 crates selects `agentmage-host` or `agentmage-platform-linux` through reverse
dependencies:

- knowledge, read-only, repository-map
- contracts, engine
- linux-inference, linux
- host

Those two packages contain all 72 inherited failures, so the gate is guaranteed red
in this lane for essentially every Rust change T-302 onward will make. Only
`agentmage-platform-windows` and `agentmage-xtask` can pass. I confirmed the xtask
case end to end.

**The 72 failures are environmental, but the baseline does not say so.** Decision
0151 ("Consequences and truth") requires new evidence to distinguish environmental
failures. The baseline says only that the comparison is "not proof that every
failure has one cause", and mentions the lane's user mapping without connecting it
to the failures. From my own run:

- Every panic in the failing tests is a trust or manifest refusal:
  - `LinuxSandboxError { kind: InvalidManifest }` (test sandbox and verified worker
    manifests)
  - `LinuxRepositoryError { kind: InvalidGitArtifact }`
  - `LinuxSecretServiceError` and `LinuxCommandRunnerError { kind: InvalidManifest }`
  - one `LinuxLocalCommitError { kind: ArtifactDenied }`
- The one exception is a parent assertion (`linux_coding_runtime.rs:7221`, exit
  101 ≠ 93). Its spawned child failed with `InvalidManifest`.
- The refusals come from root-ownership checks such as
  `platforms/linux/src/platform.rs:851` (`metadata.uid() == 0`) and
  `platforms/linux/src/repository_safety.rs:1317` (`verify_root_owned_path`).
- In this lane, the single-user ID mapping makes `/usr/bin/bwrap`,
  `/usr/bin/systemd-run`, `/usr/bin/git` and `/usr/bin/bash` appear owned by the
  overflow UID (65534). The checks are refusing correctly.

This is evidence for environmental cause, not proof for every test. The boundaries
are behaving as designed; there is no sign of a product regression.

Fix:

- Record this classification in the baseline, with the grouped refusal kinds and
  the ownership mechanism.
- State in the guide which crate selections are guaranteed red in this lane.
- Record, as Decision 0151 item 9 provides, either:
  - an explicit owner-action blocker (a lane where system executables are
    root-mapped, or a native run), or
  - a reviewed acceptance route that reports the exact inherited identity set and
    any new failure, while keeping the gate's result FAIL. Never use an allowlist,
    a skip or a weakened trust check.

Without this, T-302 onward has no honest path to a passing touched-crate gate.

### L1 (low): non-Rust files inside crate directories are accepted with Rust-only checks

Location: `scripts/local_agent_fast_gate.py:92-96`. The guide
(`docs/guides/local-agent-development.md:38`) correctly says "outside a crate". The
request's wording ("refuses unknown types") is broader than the code.

`plan()` treats any path under a crate root as covered. I confirmed that
`shells/host/assets/app.js`, `shells/host/web/index.html` and
`shells/host/web/style.css` plan only fmt, Clippy and test for `agentmage-host`.
Decision 0151 item 2 puts the mission UI in packaged assets served by the Rust
runtime, which is likely inside `shells/host`. No such files exist yet.

Fix: inside crate roots, accept only an explicit set of file types (`.rs`, `.toml`,
`.json`, `.sql`, `.txt`, `.md` and today's extensionless files). Refuse anything
else until UI checks exist, with a test.

### L2 (low): Python changes run only the same-named test module, not importers

Location: `scripts/local_agent_fast_gate.py:80-90`.

The Rust path includes reverse dependents; the Python path does not:

- 168 modules under `scripts/` are imported by other test or script modules. For
  example, `scripts/evidence_core.py` has 60 importers, but a change to it runs only
  `tests/test_evidence_core.py`.
- `shells/host/tests/native_read_cancellation.rs:160` executes
  `scripts/coding_harness.py`. That test is currently ignored.
- The guide (`:28-30`) describes the mapping but does not say that importers are not
  run.

Fix: compute importers with a static `ast` scan of `scripts/` and `tests/` and add
their test modules, or state the omission in the guide.

### L3 (low): whitespace check skips untracked files

Location: `scripts/local_agent_fast_gate.py:178`.

`git diff --check <base> --` does not see untracked files. In a clone, an untracked
`release/xtask/notes.txt` with trailing spaces left `git diff --check` at exit 0.
Markdown and Python files are covered by their own linters; other untracked files
are not. The guide (`:26`) says "across the selected Git diff".

Fix: run `git diff --no-index --check /dev/null <file>` for each untracked path (a
nonzero exit is expected because the file differs; parse the output), or scan
untracked text files in Python. Add a test.
