## Findings

No critical, high or medium findings.

**L1 (low): API answer cap and active-operation settings refusal lack committed regressions.**
`platforms/linux-inference/src/local_chat_api.rs:627-631` (the 64 KiB `oversized` path producing
`code.proposal.limit`) is not exercised by `platforms/linux-inference/tests/local_chat_api.rs`. The
transport's own text cap is 1 MiB, so this route-level cap is the effective bound. Settings
PUT/DELETE refusal during an active proposal (claimed in coding-proposals.md, "Events and
cancellation") is also not tested for this route. My scratch probes show both behave correctly
today. Fix: add a synthetic-upstream test that streams more than 64 KiB and asserts the terminal
`code.proposal.limit`, no proposal and the activity outcome. Extend
`coding_cancellation_remains_available_and_inert` to assert 409 for settings PUT/DELETE while
active.

**L2 (low): the campaign audit does not bind grades to candidate bytes.**
`/lane/state/tmp/t303-proposals/audit.py` (private, line ~101) uses `scored['passed']` without
asserting `report['candidate_sha256'] == row['candidate_sha256']`. I verified the binding
independently (60/60 match), so the published scores stand. Fix: add that assertion, plus
`report['task_sha256']`, to the audit used for the row-closing scoreboard.

**L3 (low, forward-looking): `valid_path` is a display-path check, not a write guard.**
`capabilities/repository-map/src/coding_proposal.rs:137-148` accepts case-colliding paths
(`A.py` + `a.py`), `...` and `a/.git.`. That is harmless here because paths are never resolved.
Fix (T-306): do not reuse `valid_path` as worktree confinement. Re-validate every proposed path
through the kernel/worktree authority (no symlink following, case-collision and Git-internal
refusal) before any apply.
