## Analysis

- **Narrowing only, inert.** `PreparedEndpointChat::with_response_text_limit`
  (platforms/linux-inference/src/local_chat_transport.rs:298-311) does the following:
  - It refuses `0` and anything above the current `response_text_limit_bytes` with `Configuration`.
  - It does no I/O. The test asserts `accept()` returns `WouldBlock` after all borrowed and shared
    cases.
  - It rebuilds the descriptor through `from_prepared_body`, using the same transport's
    `model_selection(model)` (the same `endpoint.base_url()`) and cloned context and body
    fingerprints. Only the text limit changes.
  - It leaves `self.body` (the zeroized frozen bytes) and `self.transport` (the borrowed or shared
    credential owner) untouched.
  - `verified_input_tokens` is reset to `None`, but it is always `None` at preparation (contracts
    endpoint_model.rs:91), so the descriptor is unchanged otherwise. The test compares the full
    serialized binding with only `response_text_limit_bytes` changed, and equal-cap identity.
- **Enforced in the transport before the callback.** `chat_encoded` (local_chat_transport.rs:612-663)
  now takes the binding and checks the cumulative `value.len()` (UTF-8 bytes of the decoded `String`)
  with `checked_add(...).filter(<= limit)` before `text(&value)`. Overflow returns `Limit`, which drops
  the wire and socket, and no `EndpointModelResult` is produced. The 1 MiB codec bound and the 4 MiB
  stream bound remain. At the default ceiling the new check equals the codec's, so ordinary chat
  behaviour is unchanged. The codec uses `provider_usage_requested` and `requested_max_output_tokens`
  from the binding, which equal the values previously passed by argument.
- **Kernel admission.** `RuntimeEndpointModelPhase::for_run` (kernel/engine/src/runtime_loop/endpoint.rs:142-177)
  refuses `response_text_limit_bytes > run.limits.max_output_bytes`. That check explains the old
  `ResourceExhausted` refusal for runs under 1 MiB. Narrowing now happens before `for_run`
  (shells/host/src/coding_endpoint_edit_generation.rs:121-130), so the phase admits the actual frozen
  envelope. The phase's `port.request() != &self.request` check compares the narrowed descriptor on
  both sides, and its independent per-fragment count (endpoint.rs:220-226) stays in force. The
  `min(64 KiB)` happens before the `as usize` cast, so nothing truncates. A zero `max_output_bytes`
  refuses as `Preparation(Invalid)`.
- **Strict collector.** It now uses the frozen `answer_limit` (coding_endpoint_edit_generation.rs:183,193).
  With a real transport the transport refuses first, so this bound remains as defence in depth.
  `prepare_preview` still requires `!oversized && Ok(result) && finish == Stop` before any read.
- **Tests match their claims.** The host test streams 8 KiB fragments, which exercises
  multi-fragment accounting at the 64 KiB cap. It covers 4 KiB, 64 KiB and 2 MiB runs, borrowed and
  shared connections, at and one byte over the cap. In each case:
  - Overflow gives `Dependency(Limit)`, completed counts `None`, preview `Incomplete`, and the prior
    pending preview and source bytes unchanged.
  - An exact answer prepares a one-file native diff without writing.
  The cancellation assertions are now exact. In the callback-cancel case,
  `Dependency(OperationStopped(Cancelled))` comes from the transport's `control.remaining()` after the
  callback, ahead of the phase's later check, and preview returns `Incomplete`. Cancelling after EOF
  gives `Preparation(Cancelled)`. No production cancellation code changed.
  The test that previously asserted `ResourceExhausted` for a 4 KiB run now asserts successful
  preparation at 4096. Other `ResourceExhausted` coverage, such as the content-budget case, remains.
- **Confinement and authority.** The change adds no route, tool, grant, executor, retry, recovery or
