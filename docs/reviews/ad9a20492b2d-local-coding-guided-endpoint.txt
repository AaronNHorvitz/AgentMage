## Analysis

Consent and confinement:
- `guided` (coding_cli_endpoint.rs:136-181) only builds an Allow response from a challenge that this
  process just got back from `advance`. That challenge has already passed `check_challenge` in `advance`
  (signature/seal, run id, task id and visible tool/version). Before any approval is sent, the exact
  `allow <challenge_sha256>` confirmation (:165) and then the `share <request_sha256>` disclosure
  confirmation (:105) must both succeed. If either is declined, the client returns Err without
  sending a Deny, so the challenge stays pending on the service. The `deny-at-2` case (approval
  held, disclosure declined, 2 calls, no response object sent) and the live first-terminal decline
  (0 executions, same challenge later) cover this.
- The tool arguments are decoded with `decode_exact` and must be a JSON object, as in
  `endpoint-approve`. All review text goes through `safe()`, which escapes non-ASCII and DEL, and
  serde escapes control characters. The live PTY test asserts that no ESC byte reaches the terminal,
  so model-controlled challenge text cannot inject terminal escape sequences.
- Bounds: with N = `max_tool_calls`, the loop runs N+1 times; a repeated approval id or an
  (N+1)th distinct challenge returns Err before any prompt. I traced the N=0 and N=1 tests (1 and 3
  prompts, 2 and 2+N calls) and the repeat test (5 prompts, 4 calls); they match the code. A
  self-inconsistent authenticated peer cannot make the client loop.
- Interruption: `workflow::bounded` installs the existing SIGINT/SIGTERM/SIGHUP latch and deadline.
  `check_running` runs each iteration and inside every `call`. The driver confirm returns Stopped on
  the latch. Tests cover a signal at a prompt, deadline at a prompt, a stalled header with the deadline
  and a stalled body with SIGINT after an approval was sent. In each case no further request is made.
  `test_peer_disconnected` confirms the socket was closed, not retried.
- `advance` now uses `client.confirm`. For the single-shot commands (`endpoint-step`/`approve`/`deny`)
  the client has no controls, so the call falls through to the unchanged `confirm`. Their behaviour
  does not change.
- No new tool, route, model transport, file read or grant is added. Workspace, sandbox and network
  confinement stay with the unchanged service. I found nothing in this diff that would let a
  prompt-injected tool call skip the per-operation exact approval.

## Findings

No critical, high or medium findings.

L1 (low) — the disclosure token is the same at every step, and pending terminal input is not flushed.
`platforms/local-api/src/coding_cli_endpoint.rs:105` uses `share <request_sha256>` for every advance.
That digest is fixed for the run and is already on the command line. `driver::Signals::confirm`
(`coding_cli_driver.rs`) reads from /dev/tty without discarding queued input. The single-shot commands
already had this design. With `endpoint-run`, several disclosure prompts now come in one process, so a
line typed ahead or pasted twice (`share <digest>\n`) is silently used by the next disclosure prompt
once the user has approved a tool. That prompt is meant to be a fresh decision. The tool approval itself
is still unique per challenge, so no unapproved tool operation can result. Fix: bind the disclosure
token to the step, e.g. `share <request-digest> <challenge-digest|start>` or a step counter, and/or
`tcflush(TCIFLUSH)` before each prompt. Add a PTY test that pre-queues two share lines and expects the
second disclosure prompt to block or decline. Same-row backlog.

Inherited lows L1/L2 from the d580df2cdf3e private-record review, and earlier inherited lows, remain
same-row backlog as the evidence states.

Observation, not a finding: exit 0 for a FAILED or CANCELLED terminal envelope is a deliberate,
documented choice (decision 0180, the guide and the evidence) and is labelled in the output. A later
increment may want a distinct exit code for non-success terminal states for scripting consumers.
