## Verification of the requested properties

- **Ownership/no adoption.** `prepare_apply`/`decide_apply` take neither root nor receipt from the
  caller. Both roots come from `self.created`. That field is set only in the successful-receipt
  branch of creation (`coding_repository.rs:404-425`), or directly by in-crate tests. The API
  structs use `deny_unknown_fields` plus `object_json`. The API test shows that injected
  `root`/`worktree`/`creation_receipt_sha256`/`answer` fields, duplicate keys, positional arrays and
  wrong types are refused with 400. Restart (`open`) restores no `created`, `apply` or
  `apply_result`; a test covers this.
- **Lineage.** Only `decide_edit` with `outcome == "committed"` extends `created.edits`. Lineage
  keeps the first `before_sha256` and the latest `after_sha256`. Pending paths are removed before
  dispatch, so an uncertain or failed write leaves no stale postimage. The 16-path cap is checked
  over the union. Path keys are canonical: `select` refuses `.`/`..`/empty segments, non-
  `[A-Za-z0-9._/-]` bytes, `.git` in any case, and case aliases. My probe confirmed refusal of
  `./one.py`, `x/../one.py`, `/one.py`, `one.py/`, a trailing newline or space, and `ONE.py`.
- **Source/root/receipt drift.** Prepare checks that the worktree bytes hash to the lineage
  postimage. The native `prepare_write` checks original bytes against the first preimage. Decide
  rechecks the creation receipt, both held roots (path plus device/inode identity), the lineage
  entry and the worktree postimage before dispatch, and both roots again after it. The tests cover
  substitutions of either root or the management directory, and creation-receipt drift.
- **All original preimages before replacement.** The multi-file test changes `two.py` after
  preparation. Nothing is written: `one.py` stays `first\n`. The existing transaction resolves and
  checks every leaf before replacing any of them.

- **Consumption, denial, expiry, clock rollback.** A foreign digest returns `code.apply.stale` and

### L1 (low, backlog): the JSON decode cap leaves the original L1 defect for in-bounds native sources

Location: `shells/host/src/coding_context_retrieval.rs:74` (`excerpt.len() <= 65_536`). Related
claims: `docs/guides/coding-runtime-api.md:263-265`, evidence line 42 ("Its low L1 is fixed here"),
and the TASKS.md T-303 row ("Low L1 production JSON body matching is repaired").

The producer admits sources up to 64 KiB (`coding_development_runtime.rs:830`). Each newline and
tab becomes two bytes in the envelope, so legitimate native excerpts often exceed 65,536 bytes.
Those excerpts skip decoding and fall back to plain matching, which is exactly the pre-repair L1
behavior: `\trefund` scans as `trefund` and `\nrefund` as `nrefund`. My Python port of
`matches`/`body_matches` on production-shaped envelopes gave:

| Source | Content | Envelope | Path | Body matches (decoded would be) |
| --- | --- | --- | --- | --- |
| Tab-indented Go, `\trefund := 1` | 42,036 B | 66,216 B | plain fallback | 0 (1) |
| Python, `refund = 2` at column 0 | 63,971 B | 65,787 B | plain fallback | 0 (1) |
| Small tab-indented Go | 36 B | 216 B | decoded | 1 (1) |

Tab-indented code was the main case of the original L1, so the repair is incomplete and the
"cannot hide source words" statement is not true for every in-bounds source. This affects ranking
only; no authority or confinement boundary is involved.

Fix: drop the envelope-length guard, since the excerpt is already bounded by the producer and
`matches` already scans at most 64 KiB of decoded content. Alternatively, derive the guard from the
producer bound (worst-case escaping of 64 KiB plus overhead). Add a regression at the source upper
bound with tab indentation. Resolve before any T-311 measurement attributes a change to this
ranking.

### L2 (low, backlog): lineage bookkeeping now refuses legitimate worktree edits, and the edit guide does not say so

Location: `platforms/linux/src/coding_repository_edit.rs:49-75` (`code.edit.lineage`,
`code.edit.lineage-limit`). Guide: `docs/guides/coding-owned-edits.md` (only its last paragraph
changed).

Before this commit, owned worktree edits had no per-session path cap and no chain requirement.
Now:

- After 16 distinct committed edited paths, an edit of any new path is refused until the user
  transfers to the original (builder test `transfer_lineage_is_bounded_across_disjoint_edit_batches`).
- After any out-of-band change to an edited worktree file, every later edit of that path is
  refused. My probe shows `code.edit.lineage` with the true preimage and `code.write.input` with the
  recorded one. The only recovery is restoring the exact prior bytes, or a fresh worktree.

The refusal adds no safety. Transfer eligibility already depends on the lineage, and the native
writer rechecks original preimages. Commands mount the worktree read-only, so the agent's own test
step cannot trigger the second case. The 16-path cap, however, is reachable in an ordinary
multi-file loop that never intends to apply to the original.

Fix: on a chain mismatch or cap overflow, accept the worktree edit and mark those paths
non-transferable (or drop their lineage). If refusal is kept deliberately, document both codes and
the recovery in `coding-owned-edits.md`.

### L3 (low, backlog): read consent names root digests that the server does not bind

Location: `platforms/local-api/src/coding_cli.rs:466-495` and
`platforms/local-api/src/coding_repository_api.rs` (`PrepareApply`).

The terminal asks for `read <original-root-digest> <worktree-root-digest>`, but the POST body
carries only `paths`/`task`/`approve_read`. The server then reads whatever roots it holds at that
moment. Suppose another trusted control client completes a separately approved new worktree
creation during the prompt. The read then covers roots the person did not name. The effect is
limited to reading eligible files into an inert preview returned to the same trusted caller. The
write is still bound to the preview's root identity and to the original-root check at
`original-apply`.

Fix: add the two expected root digests (identities, not paths) to `PrepareApply` and refuse a
mismatch in `prepare_apply`. This keeps the rule that "the body accepts no root".
