## Analysis

**Context admission**
- File: `kernel/engine/src/runtime_loop/endpoint/context.rs:46-87`.
- Roles are a closed three-variant enum.
- Admission refuses an empty list, more than 256 messages, a list that does not end with a user
  message, and any empty content (`Invalid`).
- The content-byte sum is capped at 256 KiB with checked addition before serialization.
- The JSON array goes through `ContextFingerprint`. Its `write` (`:107-117`) checks the cumulative
  ceiling before `hash.update`, so no byte beyond 256 KiB is hashed.
- No plaintext buffer is retained. `serde_json::to_writer` streams escaped slices.
  `RuntimeEndpointMessage` derives neither Debug nor Deserialize.
- The packet's fields are private, and it has no Default and no Deserialize. The module is private,
  and only the re-exported types are public, so `from_messages` is the only constructor.

**Phase binding**
- File: `endpoint.rs:79-108`.
- `new` now requires the packet, and it compares the whole `EndpointModelContext` (count, bytes, digest)
  before any resource framing. The descriptor-only constructor is gone. I confirmed by grep that every
  caller passes a packet.

**Equivalence with the transport**
- The transport fingerprints `serde_json::to_writer(messages)` over `ChatMessage { role, content }`
  with lowercase roles.
- The kernel serializes `RuntimeEndpointMessage { role, content }` with the same field order and the
  same lowercase role names, so their bytes are identical.
- Any future divergence, such as an added field, fails closed: the phase refuses before dispatch.
- The synthetic repair upstream test (`coding_repair_api.rs:510-523, 596-599`) extracts the actual
  received `"messages"` array from the wire body. It checks that the array's length and SHA-256 equal
  the kernel packet, and that `content_bytes` equals the independently measured content size. This is
  real end-to-end discrimination, not a tautology.

**Live call sites**
- All three routes (snapshot, workspace, repair) go through `prepare_endpoint_coding_proposal`
  (`lib.rs:1079-1134`).
- That function builds the packet from the same `messages` vector later passed to `prepare_chat`.
  Only references are copied into the role-mapped vector.
- In the repair route, `prepare_repair` returns before `admit_repair_proposal` calls
  `consume_repair_feedback` (`coding_repair_api.rs:65-75, 91-103`). Context admission therefore
  precedes receipt consumption, as claimed.

**Ordering change**
- Context admission now runs before the `428 api.endpoint-choice-required` check.
- Proposal messages are always nonempty and end with a user message. Upstream bounds also apply:
  `max_message_bytes ≤ 32768`, the repair budget is ≤ 32768, and the transport limits the whole request
  body to 256 KiB (`MAX_REQUEST_BYTES`).
- So no request that was previously valid can now be refused, and the existing 428 test still passes.
- The 256 KiB ceiling does not enlarge any existing limit, as the guide says.

**Tests**
- The four new methods discriminate the claims:
  - Exact wire bytes, with escapes and `λ`.
  - The exact-cap boundary at `cap - overhead`, and `+1` refusal by the writer.
  - Escape-only overflow: `"\n" × cap/2` is under the content limit but over the JSON limit.
  - UTF-8 byte counting: `"λ" × cap/2` would pass if characters were counted.
  - 256/257 messages.
  - Count, length, digest, role, content and order drift, all refused before phase admission.
- All twelve previous phase/stream methods keep their cases and now take an admitted context.
- The workspace API test now also calls `assert_endpoint_runtime_observation`.
