## Assessment

- **The production diff reaches both branches.** It is exactly one argument: `env={}` at
  `scripts/coding_eval.py:782`. Python and Rust share this `Popen` (`rust` only selects the command
  and `preexec_fn`). The regression drives the real `grade()` → `grade_case()` path for each
  language and asserts that exactly one `/usr/bin/bwrap` launch occurred, with `env == {}`.
- **The frozen regressions still run after the probe.** The driver is `probe + task_driver(task)`.
  The report must be `passed`, with `tests == expected_tests` and `candidate_kind ==
  "frozen-reference"`, and stdout must contain the probe marker. A probe that failed or
  short-circuited could not pass. In the Rust case the original driver compiles and executes the
  hidden test target; I observed this in my own probe run.
- **Test construction.** Patching `os.environ` with `clear=True` calls `putenv`/`unsetenv`, so the
  base launcher really inherits the synthetic sentinels; my negative control confirms this. If the
  test fails, it prints only assertion labels, not environment data. `runtime_paths` is resolved
  before the environment substitution and then mocked with the real resolved paths, so production
  toolchain resolution is unaffected. Patching `subprocess.Popen` affects the module globally, but
  the test filters on `/usr/bin/bwrap`, so git/rustup calls are excluded.
- **Exact inputs and unchanged tests.** The test diff only adds one method; no existing method
  changes. The eight related files are byte-identical to the base. `audit.json` source digests for
  `scripts/coding_eval.py` (6101e2ac…) and `tests/test_coding_eval.py` (5550578b…), and for the
  oracle and Rust files, match `sha256sum` at HEAD. No hidden test, task pin, threshold, resource or
  mount option, statement, `SUPPORTED` or historical-controls-only guard changed. The collection
  version stays v9.
- **Evaluation integrity.** The diff contains no held-out content, tuning, model run or GPU use.
  Base failures and reference passes are both counted (30/30 and 15/15), and no failure is dropped.
  The builder retained the failed pre-fix run and the failed first docs lint.
- **Evidence bindings.** All 13 private artifact digests in the public evidence match `sha256sum`
  of the retained files. The public evidence numbers (38, 59, 116, 30/89, 15/18/160, 30/15/15,
  720 Markdown files) match my runs.
- **Claims.** The guide's statements match my observations: `--clearenv` alone leaves
  `/proc/1/environ` readable, both branches pass `env={}`, the worker environments are explicit,
  and mount metadata and arguments are not hidden. The oracle guide's update is accurate. The TASKS
  row is unchecked and correctly states that it awaits this review.
- **Public hygiene.** The committed diff contains no host home path, username, hostname or

## Findings

No critical, high or medium finding.

- **L1 (low; carried from T-311.18, disclosed, deferred).** In both legacy branches, host
  bind-mount sources (home path and user name) remain visible inside the namespace through
  `/proc/1/cmdline` (bwrap arguments) and `/proc/self/mountinfo`. I reproduced this above. The
  documentation states it accurately (`docs/guides/coding-evaluation.md:320-321`). It still needs
  the recorded disposition before generated scoring: stage the case, toolchain and registry roots
  under a neutral path with opaque names, or pass the binds as descriptors, or record explicit
  acceptance.
- **L2 (low; out of scope, backlog for T-312).** `scripts/coding_model_lab.py:270` starts the
  model-server bwrap sandbox (`sandbox_command`, `:170-197`, which uses `--clearenv`) through
  `subprocess.Popen(command, …)` without `env={}`. The server's namespace PID 1 therefore exposes
  the operator's environment, the same gap this row fixes in the grader. That process is a trusted
  llama-server binary, not a candidate, so this does not affect T-311.19. Apply the same `env={}`
  and a PID 1 environment check before T-312 runs model-produced content near that process.
