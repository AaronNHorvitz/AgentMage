## Security and correctness analysis

Kernel callback (`coordinator_endpoint.rs:634-705`):
- The callback is reached only after full accounting. Input bytes and model calls are charged
  before dispatch; output bytes and elapsed time are charged after a completed result; then
  `ModelCompleted` is emitted, and `finish != Stop` is refused before the callback. Failure,
  limited and overflow responses return through `finish_model_failure` or `finish_phase_stop`
  earlier. The kernel test confirms this in modes 5-7 (interpreted count 0).
- `tool_budget_exhausted` runs before the callback. Mode 8 (`max_tool_calls = 0`) confirms the
  callback is never entered.
- The identities passed to the callback match what `request_tool` later derives: operation
  `tool_call_count+1`, endpoint-call `turn_count`, action `tool_call_count+1`. The kernel test asserts
  each one.
- The callback runs under a `RuntimePhaseControl` over the original clock, start time and
  cancellation probe, with `check()` before and after. A deadline crossed inside the callback is a
  phase stop, and the proposal is discarded (mode 2, no execution).
- Callback `Err` goes to `finish_refused_proposal("runtime.proposal.preparation-refused")`. When a
  callback is set there is no path to raw text, the tool-call envelope or completion parsing:
  `interpreted` is `Some` or the function has already returned. A callback-produced proposal still
  goes through `is_model_proposable`, registry-owned schema and encoding, `validate_arguments`,
  `request_tool` input charging, the attempt guard and the permission boundary.
- No wire or model field can construct the callback. It is set only by process-local
  `with_tool_preparation`.

Host pair (`coding_endpoint_edit_previews.rs`):
- The constructor requires that the repository's created workspace equals the startup workspace,
  and that visible tools equal the edit registry.
- `response()` re-checks the startup digest and the edit context. The callback re-checks that the
  request equals the startup request, checks both controls before and after, requires
  `Owner::Ready`, and runs the existing strict `prepare_edit_proposal`: fresh reads, complete
  preimages, mutable and protected paths, native diff. It then binds through the unchanged
  `into_endpoint_edit`.
- The native binding requires the exact registry-encoded bytes and digest of `{"preview": ...}`,
  the exact definition, and an action ID in range. The boundary's `check` requires
  `call == self.edit.call` and the exact request, and `evaluate_scoped` requires the exact
  operation ID. A coordinator-side re-encoding that differed in any byte would therefore fail
  closed.
- The owner is retired (`take`) before handoff. Binding refusal restores the same repository
  without a grant.
- Tool-side `evaluate`, `resolve` and `execute` (the unscoped variants) refuse. The scoped variants
  delegate only when the owner is `Pending`.
- Only `OperationOutcome::Succeeded` returns the owner to `Ready`. An execute `Err` propagates with
  the owner still `Pending`. A panic while the lock is held poisons it, and later locks refuse with
  `Unavailable`.
- Approval IDs derive from each preview's change-set ID. The host test asserts that the second
  approval ID differs and that the earlier approval and a tampered approval leave events
  unchanged.

Confinement reproduction. This commit adds no new filesystem, network or command primitive. It

## Findings

No critical, high or medium findings.

- **L1 (low, portability), `shells/host/src/lib.rs:52`.** `pub mod coding_endpoint_edit_previews;`
  is the only module in this region without `#[cfg(target_os = "linux")]`. It imports
  `agentmage_platform_linux` (declared only under `[target.'cfg(target_os = "linux")'.dependencies]`
  in `shells/host/Cargo.toml:46-47`) and the Linux-only modules `crate::coding_endpoint` and
  `crate::coding_endpoint_prepared_startup`. A non-Linux build of `agentmage-host` therefore cannot
  resolve those paths, which is a regression from the base, where every such module is gated. I
  reasoned this from the cfg and dependency declarations and did not run a cross-target build. No
  current gate builds non-Linux, and the mission is Linux-only, so this is low. Fix: add
  `#[cfg(target_os = "linux")]` and a `///` doc line above the module, as its neighbours have.
- **L2 (low, test coverage), `shells/host/src/coding_endpoint_edit_previews.rs:251`.** The
  "failed/uncertain remain held" rule (only `Succeeded` returns the owner to `Ready`) has no direct
  regression. No host case approves a write that then fails natively (for example, the source is
  changed after the challenge and before the Allow response) and then reaches a later strict turn.
  Cases 8 and 10 end before execution, and case 5 is refused at preview time. If the line were
  mutated to return the owner on any outcome, every existing case would still pass. A later write
  would still need its own exact approval, so this is not a confinement gap. Fix: add one case to
  the existing method that modifies `one.py` between the first challenge and Allow. Assert that the
  native outcome is not success, that the second strict turn is refused with no second challenge,
  and that `two.py` is unchanged. Related backlog: `response()` does not check owner readiness when
  the turn is prepared, so a turn after a non-successful effect still spends one accounted model
  call before the callback refuses.
- **L3 (low, test precision),
  `kernel/engine/src/runtime_loop_endpoint_coordinator_tests.rs:634`.** For modes 1-8 the kernel
  method asserts only `Complete`, the interpreted count and zero executions. It does not assert the
  terminal state or reason codes: `preparation-refused`, deadline stop, `tool-not-offered`,
  `arguments-invalid`, model failure and tool-budget exhaustion. Fix: assert
  `outcome.outcome.state` and the reason code for each mode.

All three are same-row backlog and block nothing.
