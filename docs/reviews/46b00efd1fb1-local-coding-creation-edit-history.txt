## Analysis

- **Manual path** (`coding_repository_edit.rs:168-180`, `:232-234`):
  - The guard is raised before `applied_write.take()` and before dispatch whenever
    `created.edits` holds a creation marker (`created_mode` or zero preimage). The marker is
    sampled before the edited paths are removed.
  - Every early return after dispatch leaves the guard raised: native error, uncertain root, or an
    `Ok` outcome other than `committed`. Panic unwinding also leaves it raised.
  - It is lowered only in the committed branch, and only to the pre-dispatch value. That requires
    the earlier proof to have been retained and the composed `applied_write` to be `Some`.
  - Denial, staleness and expiry return before history is taken. I checked this in the code and
    the gate's inert-choice test passes.
- **Runtime path** (`coding_repository_runtime.rs:379-382`, `:405`, `:293-300`):
  - The mirrored logic applies. `attempted` is taken before the completion checks, so a rejected
    completion cannot restore the guard.
  - A dropped driver or `publish=false` leaves the guard raised.
  - The owner stays locked by the driver's `MutexGuard` between `apply` and `complete`, so the
    captured previous value cannot go stale.
  - A failed candidate (lineage or shape) returns before history is taken and before native apply.
- Creation markers carry forward through successful edits. `prepare_edit` and runtime `apply` copy
  `before_sha256` and `created_mode` from the prior entry. The at-risk predicate therefore still
  sees a creation after chained edits.
- Original transfer clears `applied_write` without changing the guard. Any remaining creation
  entry then makes the next edit set the guard, because no earlier proof was retained.
