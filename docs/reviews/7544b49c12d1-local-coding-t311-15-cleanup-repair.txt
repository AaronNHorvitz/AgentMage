## Findings

### M1 (medium): permission repair is path-based; candidate-controlled depth still defeats cleanup and hides outcomes

Location: scripts/coding_eval_oracle.py:248-263 (`repair_fixture_permissions` builds full host paths
`root/…/entry` and calls `lstat`/`chmod`/`scandir` on them). Called at scripts/coding_eval_oracle.py:282.

Reproduction (see the table above): a dev-017 candidate builds a directory chain whose host path is
longer than PATH_MAX. In the sandbox this is easy with relative `mkdir`/`chdir`.

- Repair raises ENAMETOOLONG. `candidate_temporary` re-raises it, and grade drops the observed oracle
  record: infrastructure, tests/calls null.
- A correct answer, which passed before this repair because rmtree handles any depth, becomes an
  infrastructure failure.
- A natural wrong mode answer combined with the chain becomes infrastructure plus cleanup-failed. A
  `cleanup.json` recovery record is written and the case workspace is left on disk with candidate data.
  In this run rmtree had already removed `oracle-adapter/test.py`; whether the hidden copy survives
  depends on removal order.

These are the same consequences that review 1 M1 found and this row was reopened to fix: an obscured
cause, retained residue and a candidate failure indistinguishable from a harness fault. The trigger is
now deliberate rather than natural. Attempts stay counted as failed, so this is not high.

Fix: walk with directory file descriptors instead of paths.

1. Open the root with `os.open(root, O_RDONLY | O_DIRECTORY | O_NOFOLLOW)`.
2. For each directory entry named `name` under `parent_fd`:
   - check `os.lstat(name, dir_fd=parent_fd)` is a directory;
   - call `os.chmod(name, 0o700, dir_fd=parent_fd, follow_symlinks=False)`;
   - open the child with `os.open(name, O_RDONLY | O_DIRECTORY | O_NOFOLLOW, dir_fd=parent_fd)`;
   - check that its `st_dev`/`st_ino` match the lstat;
   - list it with `os.scandir(fd)`.
3. Keep an explicit stack of fds, or close and reopen them by (parent fd, name), so open-fd limits are
   not exceeded.

Path length then never grows. Add a sandbox regression for a chain deeper than PATH_MAX, with both a
correct and a 0o555 wrong answer, asserting the observed cause, no `cleanup.json` and no residue.

### M2 (medium): the repair's safety rests on a "workers are reaped, no race" guarantee that does not hold, and the evidence states it as fact

Locations:

- scripts/coding_eval_oracle.py:249-253, the docstring: "exchange has terminated and reaped both
  namespaces … no candidate can rename an ancestor".
- docs/evidence/t311-15-cleanup-review-repair-2026-11-03.md:16-17: "Both workers have terminated and
  been reaped before this traversal; candidate code cannot race it."
- The guide, docs/guides/coding-evaluation-oracle.md:288.

`terminate` (line 150-157) sends SIGKILL to the outer bwrap's process group and reaps only the outer
bwrap. The sandboxed processes die later and asynchronously, through `--die-with-parent` and teardown
of the PID namespace. The liveness probe shows candidate filesystem changes landing in the writable bind
after `terminate()` returned (up to 261 new entries).

The path-based walk resolves every intermediate component at use time. A rename or symlink swap of an
already-scanned ancestor in that window would make `lstat`/`chmod 0o700`/`scandir` act on host
directories outside candidate-tmp. Examples are any host-user-owned tree reachable by an absolute or
`/proc/self/cwd` symlink, such as the repository.

`shutil.rmtree`, which this walk now precedes, is fd-based precisely to resist this. Of the builder's
tests, the symlink test only covers a static tree, and the interruption test does not run concurrent
mutation. I did not achieve an escape in 70 attempts, and the window I measured is short. That is why
this is medium and not high.

The repair still:

- weakens a host-side confinement property from structural to timing-dependent;
- publishes an untrue security claim;
- is unacceptable once generated (untrusted) candidates are admitted.

Fix:

- Use the fd-relative walk from M1, which makes ancestor renames irrelevant. Alternatively, perform the
  permission repair inside a fresh bwrap that binds only candidate-tmp, so any symlink resolves inside
  that sandbox.
- Correct the docstring, evidence and guide to state the actual guarantee.
- Add a regression that runs repair while a live process keeps swapping a scanned ancestor for a
  symlink to a sentinel. A direct `sandbox` + `terminate` harness like my `race_direct.py` is enough.
  Assert that the sentinel is never changed.
