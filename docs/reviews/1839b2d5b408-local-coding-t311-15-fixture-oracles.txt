## Findings

### M1 (medium): a candidate-controlled directory mode defeats cleanup of the new writable mount

Location: scripts/coding_eval_oracle.py:258-262 and 141-142 (new host-backed `candidate-tmp` bound
writable at candidate `/tmp`), cleaned only by `shutil.rmtree` in scripts/coding_eval.py:640-652.
The claims are in docs/guides/coding-evaluation-oracle.md (the "File modes and extraction helper calls"
section: "is removed through the existing cleanup before reports publish"; "uninspectable … entries fail as
sticky adapter policy") and docs/evidence/t311-15-fixture-oracles-2026-11-03.md ("The existing cleanup
removes that mount's backing tree before counts publish").

Before this row, the independent oracle's candidate had no writable host-backed mount: `/tmp` was a
private tmpfs. dev-017 now gives it a host directory. dev-017 is a task about directory permission bits,
so a candidate that leaves any directory without owner write or search permission breaks the host
`rmtree`. Then `case_workspace` raises `evaluation.cleanup-failed`, `grade` drops the oracle record
(`tests`/`calls` null) and reports `cause: infrastructure`. The private workspace stays on disk,
including candidate-written content, the trusted projection and the hidden test copy in
`oracle-adapter/test.py`.

Reproduced on this commit:
- Adversarial case: the reference implementation plus an extra 0o500 directory either in `/tmp` or
  inside the fixture root. The oracle's own record showed the hidden test passing. The published report
  was infrastructure; `cleanup.json` named a leftover `agentmage-eval-*` workspace.
- Honest wrong answers: directories set to 0o555, everything set to 0o644, or `nested` set to 0. Each
  was reported as infrastructure/cleanup-failed instead of test_failure or adapter_policy, and each
  left residue.

Attempts are still counted as failed, so this is not a high denominator-integrity break. It does
contradict the row's published cleanup and cause claims. A natural model output becomes indistinguishable
from a harness fault, which a later scorer or rerun policy might exclude. Candidate-controlled data
persists outside the case lifetime, and for future protected inputs hidden-test bytes would persist too.

Fix:
1. Before `rmtree` (or in a dedicated `remove_candidate_tmp` step inside `grade_case`, while the
   workspace still exists), walk `candidate-tmp` from the trusted host side without following symlinks
   (`os.walk(..., followlinks=False)` top-down or fd-relative traversal). Apply `os.chmod(path, 0o700)`
   to every real directory before descending, then remove the tree.
2. Keep the oracle record and cause when only the candidate mount needed permission repair.
3. Add real-sandbox tests: 0o500/0o000 directories in `/tmp` and in the fixture root, and all-0o555 /
   all-0o644 wrong answers. These must yield test_failure or adapter_policy, no `cleanup.json`, and no
   leftover `agentmage-eval-*` directory.
4. Correct the guide and evidence sentences.

### L1 (low, backlog): the candidate `/tmp` for dev-017 is now host-disk-backed

Same location. The candidate can write an unbounded number of files of up to 32 MiB each to the host
filesystem until the timeout, where earlier it wrote to a RAM tmpfs. The evidence already states that
aggregate disk quotas are unavailable and that generated scoring stays disabled. Before generated
scoring, use a size-limited tmpfs or a quota-backed directory for this mount.

### L2 (low, backlog): dev-019 input types are normalised to Path

scripts/coding_eval_oracle_worker.py `command_proxy` and `command_result` send `str(package)` and
`str(root)`, and the candidate always receives `Path` objects. This matches the frozen dev-019 method,
which passes Paths, so grading is faithful today. The guide does not say so, and reuse for a fixture that
passes str would silently change candidate inputs. State this in the coverage text, or carry the input
through the same tagged codec.
