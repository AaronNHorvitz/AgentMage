# Durable run action histories in the operational store — verification

Date: 2026-09-30. Source: `cd6d368a2c434372d27aa28c35bec1e797772a36`.
[Decision 0129](../decisions/0129-durable-run-action-histories.md) implements AMR-05.9.6. Each coding
run's three action histories are kept in the authenticated operational store, so they survive the
host process. They replay against their stored heads and can be read back, shown and exported for an
ended run through the host and CLI.
The [retained record](durable-run-action-histories-2026-09-30.json) is generated by
`scripts/verification_batch.py` from its
[specification](../../artifacts/verification-logs/durable-run-action-histories-2026-09-30/record-spec.json),
9 retained stages and a compact binding inventory. It regenerates with
`python3 scripts/verification_batch.py record --spec <spec> --check <record>`.

## Change

The kernel store:

- Operational store migration 22 adds run action history roots, records and heads, keyed by run and
  chain (`effects`, `job-control` or `routes`). Triggers keep roots immutable, records append-only
  except for the change from kept to expired, and heads forward-only. A head's complete flag can
  only be cleared, its closed flag only set, and a closed head never changes again. The migration
  verifies the prior history first and stays retryable at version 21.
- The new store module creates and attaches chains, appends to them, marks them incomplete, closes
  them and reads them back, under the chain's recorded owner. Every append replays the stored chain
  and commits its record with the advanced head in one immediate transaction that names the head it
  read. Every read and every store open replays every chain. A tampered, rolled-back or
  non-canonical chain fails as an integrity error and poisons the store. A chain holds at most 512
  positions. Retention keeps only the places of a closed chain's expired entries.

The host:

- Each recorder keeps an entry in memory and then in the store. A store refusal of an entry memory
  kept leaves both incomplete.
- When it composes a new run, the development factory creates the effects and route chains. It
  stores the route entry before it builds any model; to do so it now opens the store right after
  routing.
- The live service keeps the job control chain. It releases every store handle before an in-host
  continuation opens the store again. Dropping an ended run's session closes all three chains, and
  releasing the run drops it.
- A run resumed after a restart marks its effects and job control chains incomplete. Its route chain
  stays complete, because each route entry is stored before its model is built.
- IPC wire version 11 adds a read of an ended run's stored histories. The host serves it only while
  it holds no run, applying retention to each closed chain first. The development CLI's
  `--ended-run RUN_ID` replaces the objective. It shows each chain with whether it was closed and
  whether it is complete, and exports a requested range with `--action-history-export`. The harness
  has an `ended-run` subcommand for it.
- The nine Sprint 11 store producers, their tests and two documents name schema 22.
